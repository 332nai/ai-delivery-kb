**Definition**

A vector database is specialised storage for embedding vectors that supports fast nearest neighbour search. Popular options include Pinecone (managed SaaS), Weaviate (open source, self hosted or cloud), Qdrant (open source, fast), Chroma (lightweight, developer friendly), and pgvector (a Postgres extension that adds vector search to a database you might already have).

**Why it matters in delivery**

Vector database choice is a frequent over engineering trap. Teams default to Pinecone for a 500 document proof of concept, when a list in memory would have worked. Or they pick pgvector for a 100 million document system that needs specialised infrastructure. Knowing the trade offs saves money, time, and migration headaches.

**How it works**

| Option | Type | Best for | Watch out |
|---|---|---|---|
| In memory (numpy, FAISS) | Library, no DB | Prototypes, under 10K chunks | Loses everything on restart, no concurrent access |
| pgvector | Postgres extension | Teams already using Postgres, under 5M chunks | Slower than purpose built DBs at large scale |
| Chroma | Lightweight DB | Local dev, small projects | Less mature for production |
| Qdrant | Open source, self hosted or cloud | Mid size production, performance sensitive | Requires DevOps to run self hosted |
| Weaviate | Open source, managed option available | Hybrid search built in, mid to large scale | More complex, schema heavy |
| Pinecone | Fully managed SaaS | Large scale, want zero ops, willing to pay | Cost scales with vectors stored, vendor lock in |
| Cloud native (Azure AI Search, AWS OpenSearch) | Managed, part of cloud stack | Clients already in that cloud, procurement easy | Often less specialised than purpose built |

A rough rule: under 10K chunks, in memory is fine; 10K to 5M, pgvector or Qdrant; over 5M, a purpose built vector DB.

**PM decision points**

- How many vectors will the system actually hold in 12 months, not at launch?
- Does the client have an existing database the team can extend (pgvector)?
- Is the team comfortable operating a self hosted vector DB, or do we need managed?

**Watch outs**

- Vendor lock in is real, embedding format and metadata schemas do not always transfer cleanly
- Many cloud providers now bundle vector search into existing services, check before adding a new vendor
- Vector DB cost scales with both storage and queries, model both

**Takeaway: pick the simplest vector store that handles your real scale. Most projects do not need Pinecone, some need more than pgvector.**

**Qantas story**

Vector database selection at Qantas, or any large Australian enterprise, is dominated by procurement and operational considerations more than by technical benchmarks. The shortlist for most projects narrows to options that work with existing cloud agreements and have Sydney region presence.

A typical scoping conversation goes through the following filters quickly. Is the workload large enough to need a purpose built vector DB, or would pgvector on existing Postgres suffice? For a focused use case with under 5 million chunks, the answer is often pgvector, which adds zero new vendors and zero new operational burden. The team running Postgres already has the skills, the monitoring, and the backup procedures.

For larger workloads or for use cases that need specialised features like hybrid search built in, the conversation moves to AWS OpenSearch (available on existing AWS agreement), Azure AI Search (available on existing Microsoft agreement), or a managed service like Pinecone or Qdrant Cloud. Each requires a procurement amendment but no greenfield contract.

Self hosting open source options like Weaviate or Qdrant on Kubernetes is possible but rarely justified. The operational overhead of running a stateful database at airline reliability standards is real, and the team has many higher value places to spend that capacity. The strong default is "use what is already in the cloud agreement."

The interesting failure mode is over engineering at the wrong end of the scale curve. A team building a proof of concept over 800 internal policy documents (about 6,000 chunks) might be pushed by an architect toward Pinecone for "scalability." Six months later the system is still 6,000 chunks and the team is paying for capacity they will never use. Conversely, a team that grew an internal knowledge platform on pgvector to 80 million chunks discovers latency problems that should have prompted migration two years earlier.

For AI delivery, the lesson is that vector database choice is rarely the most important architectural decision in a RAG project, but it is one of the easiest to over engineer. The discipline is to size for actual scale (not theoretical scale), pick the lightest option that meets requirements, and revisit the decision when the workload genuinely outgrows the current choice. The clients who appreciate this approach are the ones who have been burned previously by architectural choices made for hypothetical futures that never arrived.

**定义**

Vector 数据库是一种专门的存储,用来放 embedding 向量,并支持高速的最近邻搜索。常见的选项包括 Pinecone (托管 SaaS)、Weaviate (开源,可自托管或上云)、Qdrant (开源,快)、Chroma (轻量、对开发者友好)、还有 pgvector (一个 Postgres 扩展,给你已经在用的数据库加上向量搜索能力)。

**为何在交付中重要**

Vector 数据库选型是一个非常常见的过度工程陷阱。团队会为了一个 500 个文档的 PoC 默认上 Pinecone,而其实一个内存里的 list 就够了。或者反过来,他们会给一个 1 亿文档量级、需要专门基础设施的系统选了 pgvector。把这里面的权衡搞清楚,能省下钱、时间、还有迁移时候的麻烦。

**运作原理**

| 选项 | 类型 | 适合谁 | 注意 |
|---|---|---|---|
| 内存中 (numpy、FAISS) | 库,不是 DB | 原型,1 万 chunks 以下 | 重启就丢,不支持并发访问 |
| pgvector | Postgres 扩展 | 已经在用 Postgres、500 万 chunks 以下 | 到大规模时比专用 DB 慢 |
| Chroma | 轻量 DB | 本地开发、小项目 | 生产成熟度还不够 |
| Qdrant | 开源,可自托管或上云 | 中型生产,对性能敏感 | 自托管要 DevOps 撑得起来 |
| Weaviate | 开源,有托管选项 | 内置 hybrid search,中到大规模 | 更复杂,schema 偏重 |
| Pinecone | 完全托管 SaaS | 大规模,想要零运维,愿意付钱 | 成本随存储的向量量增长,有厂商锁定 |
| 云原生 (Azure AI Search、AWS OpenSearch) | 托管,属于云栈的一部分 | 客户已经在那朵云上,采购顺手 | 通常不如专门做 vector 搜索的那么专业化 |

经验法则: 1 万 chunks 以下,内存里就够;1 万到 500 万,pgvector 或 Qdrant;500 万以上,上专门的 vector DB。

**PM 决策点**

- 12 个月之后,系统真的会存多少向量?不是发布那一天的数字,是稳态。
- 客户那边有没有现成的数据库可以借力 (比如 pgvector)?有的话,这是最省事的路径。
- 团队有没有能力运维一个自托管的 vector DB?如果没有,直接走托管。

**注意事项**

- 厂商锁定是真实的。Embedding 格式和元数据 schema 在不同厂商之间没法干净地搬。
- 现在很多云厂商把向量搜索捆进了已有的服务里。加新供应商之前,先看看现有的云协议里有没有。
- Vector DB 的成本随存储和查询两头扩展,要对两头都建模。

**要点总结: 选择能处理你真实规模的最简单的 vector store。大部分项目不需要 Pinecone,有一些项目也不能停在 pgvector。**

**Qantas 案例**

Qantas 或者任何澳洲大型企业在选 vector 数据库的时候,主导因素是采购和运营,不是技术 benchmark。大部分项目的候选清单很快就被缩到"跟现有云协议能对上的、悉尼 region 有服务的"那几个选项。

典型的需求确定对话快速过几道过滤器。工作负载够不够大,大到需要一个专门的 vector DB,还是现有 Postgres 上的 pgvector 就够了?对于 500 万 chunks 以下的聚焦用例,答案通常是 pgvector,因为它不引入任何新供应商、也不增加运营负担。已经在跑 Postgres 的团队,技能、监控、备份程序都是现成的。

对于更大的工作负载,或者需要专业化能力 (比如内置 hybrid search) 的用例,对话转向 AWS OpenSearch (走现有 AWS 合同)、Azure AI Search (走现有 Microsoft 合同),或者 Pinecone、Qdrant Cloud 这类托管服务。每一条都需要一次采购变更,但不是从零谈一份新合同。

在 Kubernetes 上自托管 Weaviate 或者 Qdrant 这种开源选项,理论上可以,但实际很少能站得住脚。在航空业的可靠性标准下,运营一个状态化数据库的开销是真实的,而团队的精力可以花在更有价值的地方。强默认是"用云合同里已经有的"。

有意思的一个失败 pattern,是在规模曲线的错误那一端做过度工程。一个团队在 800 份内部政策文档 (约 6000 chunks) 上做 PoC,可能会被某个架构师推去用 Pinecone,理由是"为了 scalability"。六个月之后,系统还是 6000 chunks,团队一直在为永远用不上的容量付钱。反过来,另一个团队在 pgvector 上把内部知识平台养到 8000 万 chunks,延迟问题在两年前就该让他们启动迁移,但他们没动。

往大了说,这件事给 AI 交付的启示是: vector 数据库选型很少是一个 RAG 项目里最重要的架构决策,但它是最容易被过度工程的决策之一。纪律是: 按真实规模 (不是理论规模) 算容量,选满足要求的最轻量的方案,等工作负载真的把当前方案撑爆了再去重选。会真正欣赏这种做法的客户,通常是之前因为"为一个永远没来的假设未来做过架构选择"而吃过亏的那些。
