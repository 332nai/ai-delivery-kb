**Definition**

RAG is the default for many enterprise AI projects, but not all. There are use cases where RAG adds complexity without value, and where simpler alternatives (long context, SQL, APIs, tool use) work better. Recognising these cases is as important as knowing when RAG is right.

**Why it matters in delivery**

Building RAG when it is not needed wastes weeks of engineering, locks in operational overhead (vector DB, embeddings, reranking), and often produces worse results than a simpler approach. PMs who can challenge a default RAG scope save real time and money.

**How it works**

| Situation | Better alternative | Why |
|---|---|---|
| Corpus is small (under 50 docs) | Stuff entire corpus into context | Modern context windows fit it, no retrieval needed |
| Data is structured (database, spreadsheet) | Text to SQL or direct query | Retrieval over rows loses precision, SQL is exact |
| Data is real time (prices, stock, news) | API or tool call | RAG indexes are stale by definition |
| Data is dynamic and small (today's specials) | API call to the source | Avoid syncing pipelines |
| Single source of truth changes constantly | Direct integration | Re indexing race conditions |
| Need exact calculation (financial, scientific) | Tool use, calculator, code execution | LLMs are bad at exact math, retrieval does not fix that |
| Long context is feasible (under 200K tokens) | Send full document, skip retrieval | Simpler, sometimes higher quality |

**PM decision points**

- Is the data text, structured, or real time? Each suggests a different architecture
- How big is the actual corpus in tokens, and would it fit in a long context model?
- Is the user actually asking semantic questions, or exact lookups?

**Watch outs**

- "We need RAG" is often shorthand for "we need to use our data," challenge the assumption
- Long context can be cost effective for small corpora, especially with prompt caching
- Mixed architectures (RAG plus SQL plus tool use) are common in mature systems

**Takeaway: RAG is the right tool when data is unstructured, large, and semantically queried. For everything else, simpler architectures often win.**

**Qantas story**

Not every Qantas AI use case is a RAG use case, even though the default scoping reflex often pushes that way. A useful example is a hypothetical pricing question assistant for revenue management teams. The naive scoping says "RAG over fare rule documentation." The better answer is different.

Revenue management at Qantas runs on structured data, not documents. Fares, fare rules, inventory, booking patterns, competitor pricing, and historical performance live in databases and structured data warehouses. The information a revenue manager actually needs comes from queries against these systems, not from retrieving document chunks. A query like "what is the average fare for SYD MEL Y class on Wednesday departures in November compared to October" is a SQL question with a complex but tractable query. RAG over fare rule documents does not answer it.

The right architecture is text to SQL, where the AI translates a natural language question into a structured query against the relevant data warehouse, executes the query, and returns the result. The model never reads fare data, it reads schema and generates queries. The result is precise (exact numbers from the actual data), traceable (the query is the audit trail), and current (the data warehouse is the source of truth).

Another example is real time disruption status. An assistant answering "is QF1 on time today" should call the operational system's API, not retrieve from a document index. The document index is stale within minutes, and stale information about an active disruption is worse than no information.

A third example is small corpora. A pilot AI assistant for a specific niche team might cover 30 well written internal documents totalling 70,000 tokens. That fits comfortably in a single context window of a modern model. Building a RAG pipeline for 30 documents is engineering overhead for no benefit. The cleaner architecture is to send the whole corpus in the system prompt, take advantage of prompt caching, and avoid the retrieval layer entirely.

For AI delivery, the broader insight is that RAG is the right answer when the data is text, large, and benefits from semantic query. When the data is structured, when it changes in real time, or when the corpus is small enough to fit in context, simpler architectures win. The discipline is to ask "what is the data, what is the query pattern, and what is the simplest architecture that serves both" rather than defaulting to RAG because it is the well known pattern. Clients respect the practitioner who can sometimes say no to RAG when simpler tools fit better.

**定义**

RAG 是许多企业 AI 项目的默认,但不是全部。有些用例 RAG 增加复杂性而无价值,更简单的替代方案 (长上下文、SQL、API、工具使用) 工作更好。识别这些情况与知道何时 RAG 是正确的同样重要。

**为何在交付中重要**

在不需要时构建 RAG 浪费数周工程时间、锁定运营开销 (vector DB、embeddings、reranking),并且经常产生比更简单方法更糟的结果。能够挑战默认 RAG 范围的 PM 节省真正的时间和金钱。

**运作原理**

| 情况 | 更好的替代方案 | 为什么 |
|---|---|---|
| 语料库小 (50 个文档以下) | 将整个语料库塞入上下文 | 现代上下文窗口适合它,无需检索 |
| 数据是结构化的 (数据库、电子表格) | 文本转 SQL 或直接查询 | 行上的检索失去精度,SQL 是精确的 |
| 数据是实时的 (价格、股票、新闻) | API 或工具调用 | RAG 索引按定义是过时的 |
| 数据是动态和小的 (今天的特价) | 对源的 API 调用 | 避免同步 pipeline |
| 单一真相来源不断变化 | 直接集成 | 重新索引竞争条件 |
| 需要精确计算 (财务、科学) | 工具使用、计算器、代码执行 | LLM 在精确数学上很差,检索不修复那个 |
| 长上下文可行 (200K tokens 以下) | 发送完整文档,跳过检索 | 更简单,有时质量更高 |

**PM 决策点**

- 数据是文本、结构化还是实时的?每种暗示不同的架构
- 实际语料库以 tokens 计有多大,它能适合长上下文模型吗?
- 用户实际上在问语义问题,还是精确查找?

**注意事项**

- "我们需要 RAG"经常是"我们需要使用我们的数据"的速记,挑战假设
- 长上下文对小语料库可以成本效益高,特别是带 prompt 缓存
- 混合架构 (RAG 加 SQL 加工具使用) 在成熟系统中很常见

**要点总结: 当数据非结构化、大、且语义查询时,RAG 是正确的工具。对于其他一切,更简单的架构经常获胜。**

**Qantas 案例**

并非每个 Qantas AI 用例都是 RAG 用例,即使默认需求确定反射经常那样推动。一个有用的例子是收益管理团队的假设定价问题助手。天真的需求确定说"在票价规则文档上的 RAG"。更好的答案是不同的。

Qantas 的收益管理运行在结构化数据上,而不是文档上。票价、票价规则、库存、预订模式、竞争对手定价,以及历史性能存在于数据库和结构化数据仓库中。收益经理实际需要的信息来自针对这些系统的查询,而不是从检索文档 chunks。"11 月与 10 月相比,周三起飞 SYD MEL Y 舱的平均票价是多少"这样的查询是一个 SQL 问题,带一个复杂但可处理的查询。票价规则文档上的 RAG 不回答它。

正确的架构是文本转 SQL,AI 将自然语言问题翻译成针对相关数据仓库的结构化查询,执行查询,并返回结果。模型从不读取票价数据,它读取 schema 并生成查询。结果是精确的 (来自实际数据的精确数字)、可追溯的 (查询是审计追踪),以及当前的 (数据仓库是真相来源)。

另一个例子是实时中断状态。回答"QF1 今天准时吗"的助手应该调用运营系统的 API,而不是从文档索引检索。文档索引在几分钟内是过时的,关于活跃中断的过时信息比没有信息更糟。

第三个例子是小语料库。特定小众团队的试点 AI 助手可能涵盖 30 个写得很好的内部文档,总共 70,000 tokens。这舒适地适合现代模型的单一上下文窗口。为 30 个文档构建 RAG pipeline 是工程开销而无好处。更干净的架构是将整个语料库发送到 system prompt 中,利用 prompt 缓存,完全避免检索层。

对 AI 交付来说,更广泛的洞察是当数据是文本的、大的,并且受益于语义查询时,RAG 是正确的答案。当数据是结构化的、当它实时变化时,或当语料库足够小可以适合上下文时,更简单的架构获胜。纪律是问"数据是什么、查询模式是什么、什么是最简单的架构服务于两者",而不是因为它是众所周知的模式而默认到 RAG。客户尊重有时可以为不需要 RAG 的工具说不的从业者。
