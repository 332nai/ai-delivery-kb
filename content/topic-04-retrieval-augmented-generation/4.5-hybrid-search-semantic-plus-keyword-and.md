**Definition**

Hybrid search combines two retrieval methods: semantic search (vector similarity, finds chunks with related meaning) and keyword search (BM25, finds chunks with exact word matches). Reranking is a second pass that takes the top 20 to 50 results from initial retrieval and reorders them using a more accurate but slower model.

**Why it matters in delivery**

Pure semantic search misses exact term matches like product codes, names, and identifiers. Pure keyword search misses paraphrases and synonyms. Real users do both kinds of queries, so production systems need both. Reranking is the cheapest way to materially improve retrieval quality without rebuilding the pipeline.

**How it works**

| Method | Strength | Weakness | Example query |
|---|---|---|---|
| Semantic only | Handles paraphrases, synonyms, intent | Misses exact terms, codes, names | "How do I cancel my plan" finds "membership termination process" |
| Keyword only (BM25) | Exact match, codes, names, jargon | Misses semantic equivalents | "Form HW 100" finds the exact form mention |
| Hybrid (semantic + keyword) | Best of both | Slightly more complex, needs weighting | Handles both query types |
| Hybrid + reranker | Highest quality, near production grade | Adds latency, adds cost | Used by most serious RAG systems |

A typical hybrid flow:

1. Run semantic search, get top 25 chunks
2. Run keyword search, get top 25 chunks
3. Merge into a candidate set of 30 to 50 unique chunks
4. Run a reranker model (e.g. Cohere Rerank, Voyage Rerank) on the candidates
5. Take top 5 to 10 reranked chunks, send to LLM

Reranking adds 100 to 500ms latency and a small cost per query, in exchange for significantly higher answer quality.

**PM decision points**

- Do users ever search for exact terms, codes, names, or identifiers? If yes, hybrid is needed
- Has the team measured the lift from adding a reranker, or assumed it is not worth it?
- What is the latency budget, and how much does reranking eat?

**Watch outs**

- Hybrid search weighting (how much semantic vs keyword) needs tuning, defaults rarely work
- Rerankers are a separate model, often a separate vendor, with their own cost and rate limits
- Some vector DBs offer built in hybrid search, others require manual orchestration

**Takeaway: hybrid plus rerank is the modern RAG default. Pure semantic search alone is a 2023 architecture.**

**Qantas story**

Qantas content has both kinds of query patterns that motivate hybrid search. Customer service agents ask natural language questions ("what happens if a passenger misses their connecting flight due to a delay on the first sector") and they ask exact term queries ("FBN 0001 conditions" or "QF1 schedule"). Pure semantic search handles the first beautifully and the second badly. Pure keyword search handles the second beautifully and the first badly. Hybrid covers both.

The keyword search component is essential for airline content because so much of the operational vocabulary consists of codes, identifiers, and proper nouns that semantic models treat poorly. Fare basis codes (FNRT01), city pairs (SYDLHR), aircraft types (A380, B787), and tail numbers (VH OEB) are all things customer service teams and engineers reference constantly. Semantic search interprets these as gibberish or as semantically meaningless tokens. Keyword search finds exact matches.

Adding a reranker on top of hybrid retrieval lifts answer quality further. The reranker, typically a smaller cross encoder model, looks at each retrieved chunk in the context of the actual query and reorders by relevance. The cost is a few hundred milliseconds of latency and a modest per query fee, depending on the reranker provider. The benefit is measurable: in real evaluations, rerankers typically improve top three retrieval accuracy by 10 to 20 percentage points.

The interesting practical question at Qantas scale is how to weight semantic versus keyword in the hybrid retrieval. The right answer depends on the corpus and query mix. A 70 percent semantic, 30 percent keyword weighting works well for general customer service knowledge. A 50 50 split works better for engineering content where exact codes matter more. A weighting that varies per query type, with a small classifier deciding the mix, is the most sophisticated answer but adds complexity. Most production systems pick a single weighting per corpus and tune it against an eval set.

For AI delivery, the lesson is that hybrid plus rerank is the modern RAG default for any system with meaningful query volume or content complexity. Pure semantic search is a 2023 architecture that still ships in many projects today, and it consistently underperforms. The mature delivery posture is to include hybrid and reranking from the first version, even if initial tuning is rough. Adding them after launch is harder because the system already has user expectations baked in.

**定义**

Hybrid search 把两种检索方式结合起来用: 语义搜索 (基于向量相似度,找意义相关的 chunk) 和关键词搜索 (BM25,找精确词匹配的 chunk)。Reranking 是检索的第二轮,在初始检索拿到的前 20 到 50 个结果上,用一个更准确但更慢的模型重新排序。

**为何在交付中重要**

纯语义搜索抓不住产品代码、人名、标识符这种精确术语匹配。纯关键词搜索又抓不住改写过的句子和同义词。真实用户两种查询都会做,所以生产系统必须两种都覆盖。Reranking 是在不重构 pipeline 的前提下,大幅提升检索质量最便宜的办法。

**运作原理**

| 方法 | 强项 | 弱点 | 例子 |
|---|---|---|---|
| 纯语义 | 处理改写、同义词、意图 | 抓不住精确术语、代码、人名 | "我怎么取消我的计划" 能找到 "会员终止流程" |
| 纯关键词 (BM25) | 精确匹配、代码、人名、行话 | 抓不住语义等价的表达 | "Form HW-100" 能精准匹配到表格名 |
| Hybrid (语义 + 关键词) | 两者的优点都有 | 稍微复杂一点,需要加权 | 两种查询类型都能处理 |
| Hybrid + reranker | 最高质量,接近生产级 | 加延迟、加成本 | 大部分严肃 RAG 系统都在用 |

一条典型的 hybrid 检索流程:

1. 跑语义搜索,拿前 25 个 chunk
2. 跑关键词搜索,拿前 25 个 chunk
3. 合并去重,得到 30 到 50 个候选 chunk
4. 在这些候选上跑 reranker 模型 (比如 Cohere Rerank、Voyage Rerank)
5. 取重排后前 5 到 10 个 chunk,送给 LLM

Reranking 会增加 100 到 500ms 延迟和每查询的一点点成本,换来的是显著更高的答案质量。

**PM 决策点**

- 用户会不会去搜精确术语、代码、人名、标识符?如果会,hybrid 是必须的。
- 团队真的测过加 reranker 之后的提升幅度,还是凭感觉觉得"不值得"就跳过了?
- 你的延迟预算是多少?reranking 在里面吃掉多少?这两件事是绑在一起的。

**注意事项**

- Hybrid 搜索的权重 (语义和关键词各占多少) 是需要调的,默认值很少能用。
- Reranker 是一个独立的模型,通常来自一个独立的供应商,有自己的成本和速率限制。
- 有些 vector DB 内置了 hybrid 搜索,其他的需要你自己手动编排。

**要点总结: Hybrid + rerank 是现代 RAG 的默认。纯语义搜索是 2023 年的架构。**

**Qantas 案例**

Qantas 的内容里两种查询 pattern 都存在,这也正是 hybrid 搜索能起作用的地方。客服坐席会问自然语言问题 ("如果乘客因为第一段延误而错过中转,接下来会怎样"),也会查精确术语 ("FBN-0001 conditions" 或者 "QF1 schedule")。纯语义搜索把前者处理得很漂亮,把后者处理得一塌糊涂。纯关键词搜索反过来。Hybrid 把两边都覆盖了。

关键词搜索这条路对航空内容尤其关键,因为运营词汇里有大量代码、标识符、专有名词,语义模型对这些表征得很糟糕。票价基础代码 (FNRT01)、城市对 (SYDLHR)、机型 (A380、B787)、机尾号 (VH-OEB),这些都是客服团队和工程师每天都在引用的东西。语义搜索看这些东西就像看一堆乱码,或者一堆语义上没有意义的 token。关键词搜索能精确匹配。

在 hybrid 检索之上加一个 reranker,答案质量还能再上一层。Reranker 通常是一个更小的 cross-encoder 模型,它会在"实际查询"的上下文里看每一个被检索回来的 chunk,按真实相关性重新排序。代价是几百毫秒的延迟,加上每次查询一点点费用 (看 reranker 供应商怎么算)。收益是可量化的: 在真实评估里,reranker 通常能把前三检索准确率拉高 10 到 20 个百分点。

在 Qantas 这种规模上,一个有意思的实战问题是: hybrid 检索里语义和关键词的权重该怎么配。正确答案要看语料和查询组合。70% 语义、30% 关键词,对一般的客服知识效果不错。50/50 对工程内容更合适,因为那里精确代码更重要。最精致的做法是按查询类型动态加权——用一个小分类器决定该用什么比例。但这一层会引入额外复杂度,所以大部分生产系统的做法是: 每个语料库选一个固定权重,然后用 eval 集去调。

往大了说,这件事给 AI 交付的启示是: 对任何有真实查询量或者内容复杂度的系统,hybrid + rerank 都是现代 RAG 的默认架构。纯语义搜索是 2023 年的架构,今天还有很多项目在交付它,但它的表现一致地低于 hybrid。成熟的交付姿态是从第一版就把 hybrid 和 reranking 包进来,即使一开始调得粗糙也行。上线之后再加这两层会更难,因为那时候用户预期已经在系统里固定下来了。
