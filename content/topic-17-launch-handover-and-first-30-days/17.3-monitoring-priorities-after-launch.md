**Definition**

Monitoring an AI system in production is different from monitoring a conventional software system. Conventional systems are mostly monitored for availability and latency: is it up, is it fast? AI systems need those plus three additional signals that are unique to LLM-powered products: cost (because the per-call cost is variable and can balloon), refusal rate (because the model can decide not to answer, which is invisible to traditional monitoring), and user feedback (because output quality is the actual product, and only users can judge it). This item is about which signals to prioritise, how to set them up, and what to do when they go bad.

**Why it matters in delivery**

A team that monitors an AI system the same way it monitors a conventional system will miss the issues that are unique to AI. The classic example: an AI assistant deployed to production, monitored for uptime and latency, both green for six weeks. In week seven, the cost is 10x the budgeted amount because an upstream change caused user inputs to be longer than expected, and nobody was watching the token usage. By the time the bill arrives, the project is over budget and the team is in crisis. The cost signal was the leading indicator, and nobody was looking at it.

The priority order matters because monitoring everything equally is the same as monitoring nothing. Teams that try to track 20 signals end up tracking none with attention. The order below reflects what tends to go wrong, in what order, in real AI deployments.

**How it works**

The four signals, in priority order:

| Signal | Why it matters | What to track | Alert threshold (typical) |
|---|---|---|---|
| Latency | UX impact, user trust | p50, p95, p99 response time | p95 above 5 seconds for streaming, 10 seconds for non-streaming |
| Cost | Budget control, sustainability | Cost per request, daily total, projected monthly | Daily cost above 130 percent of budgeted run rate |
| Refusal rate | Hidden quality signal | Percentage of requests that produce refusal or empty output | Above 5 percent baseline, alert at 2x baseline |
| User feedback | Actual quality signal | Thumbs up/down, explicit reports, support tickets | Thumbs down rate above 10 percent, or sudden spike |

Each signal has a different dashboard, a different alert threshold, and a different response playbook. Trying to combine them produces a dashboard nobody understands.

**Latency in detail**

Latency in AI systems is dominated by the model call, which is variable and depends on input size, output size, and model availability. The metrics to track:

Time to first token (for streaming systems): how long before the user sees anything. Users perceive this as responsiveness. Target: under 2 seconds for streaming.

Total response time: how long until the full response is delivered. Target depends on use case, typically under 10 seconds for chat, longer for agentic flows.

p50, p95, p99: the median, 95th percentile, and 99th percentile. The p99 reveals the worst cases that affect a small but real number of users.

What to do when latency degrades: check the model provider's status page first, then check if the recent change altered prompt length or output length, then check if rate limits are being hit. The fix depends on the cause.

**Cost in detail**

Cost in AI systems is per token, multiplied by call volume, with input tokens cheap and output tokens expensive. Cost can run away in four ways: more calls than expected, longer inputs than expected, longer outputs than expected, switching to a more expensive model accidentally. The metrics to track:

Cost per request: the average cost of a single user interaction. Track this and watch for drift.

Daily total cost: useful for catching volume spikes.

Projected monthly cost: extrapolate from current run rate, compare to budget.

Cost by tier or use case: if the system handles multiple types of requests, break out the cost to find which tier is consuming budget.

What to do when cost degrades: identify which of the four causes is in play (volume, input length, output length, model choice), then apply the targeted fix. Often the fix is at the prompt level (shortening the prompt) or at the routing level (sending more queries to a cheaper model).

**Refusal rate in detail**

Refusal rate is the percentage of requests where the model decides not to answer, returns an error, or returns a very short or empty response. It is one of the highest-signal but least-watched metrics in AI deployments. A spike in refusal rate often precedes user complaints by hours or days.

The metrics to track:

Overall refusal rate: percentage of requests returning empty, short, or refusal-pattern outputs.

Refusal rate by query type: if some categories of query are being refused at higher rates, that is informative.

Refusal rate trend: is it increasing, decreasing, or stable?

What to do when refusal rate spikes: check if a recent change altered the system prompt or model. Check the model provider for content filter changes. Sample the refused queries and see what they have in common.

**User feedback in detail**

User feedback is the actual quality signal. The system can have green latency, green cost, green refusal rate, and still be producing bad outputs that users dislike. Feedback is the only signal that catches this.

The metrics to track:

Thumbs up/down rate: if the system has a feedback mechanism, this is the primary signal.

Explicit reports: users emailing or messaging about issues.

Support ticket volume related to the system.

Survey results if conducted periodically.

What to do when feedback degrades: sample the negative feedback to identify patterns, run the patterns through the eval set to see if they are captured, add eval rows for new failure modes, iterate on prompts.

**Setting up the monitoring stack**

A reasonable monitoring stack for a production AI system has three layers. Infrastructure monitoring (latency, errors, uptime) using whatever the client's standard is. Application monitoring (cost, token usage, refusal rate, model performance) using a combination of provider tools and custom dashboards. User feedback (thumbs, surveys, support tickets) using the product's own feedback mechanism plus the client's support ticketing system.

The dashboards should be visible to both the operating team and the delivery team for the first 30 to 90 days, and then primarily to the operating team. The transition from "delivery team watches" to "operating team watches" should be deliberate.

**PM decision points**

- Are all four signals being monitored, with thresholds set, or am I only watching latency and uptime?
- Does the operating team know what each signal means and how to respond?
- Is the cost signal being watched daily, not just monthly when the bill arrives?

**Watch outs**

- Cost is the signal most likely to be ignored until it becomes a crisis. Watch it daily.
- Refusal rate is the signal most likely to be missed entirely. Many teams do not even instrument it.
- User feedback is the signal most likely to be collected but not acted on. The metric is useless without a process to investigate negative feedback and feed it back into the eval set.

**Takeaway: monitor four AI-specific signals in priority order: latency, cost, refusal rate, user feedback. Each has its own dashboard, threshold, and response playbook. Watch cost daily. Investigate refusal spikes promptly. Feed negative user feedback back into evals. The operating team should own this within 30 to 90 days.**

**Qantas story**

Imagine launching a Qantas AI project, an internal assistant for the call centre that helps agents look up customer policy information. The system is live, the call centre team is using it, and the delivery team is in the first month of post-launch support. The temptation is to watch latency and call it sufficient.

The PM insists on the full four signal monitoring setup. Latency is on the existing Qantas infrastructure dashboard. Cost is on a custom dashboard built during the project, showing daily spend, cost per query, and projected monthly. Refusal rate is on the same custom dashboard, showing percentage of empty or short outputs. User feedback is collected through a thumbs up/down on each agent interaction, with a comments field for negative feedback.

In week two of production, the cost signal goes red. The daily cost has jumped from the budgeted 200 dollars per day to 340 dollars per day. The PM and the technical lead investigate. The cause is not volume (queries per day are stable), it is input length: a recent update to the agent interface added context about the customer's previous interactions, which doubled the average input length. The fix is to summarise that context before sending it to the model, which restores the input length. The cost returns to budget within two days.

Without the cost signal being watched daily, the monthly bill would have arrived showing 70 percent overage, the operations team would have been in crisis, and the project would have lost credibility. The signal caught it within 48 hours of the change, and the fix took half a day.

In week four, the refusal rate signal goes red. Refusals jump from a baseline of 2 percent to 6 percent. The PM samples the refused queries. The pattern: agents are asking the assistant about a new product line that was launched the previous week, which is not in the assistant's knowledge base. The model is correctly declining to answer because it does not know, but the experience is poor. The fix is to add the new product information to the knowledge base. The refusal rate returns to baseline within a day.

Without the refusal signal being watched, the agents would have continued to experience high refusal rates on the new product, complained to their manager, and the manager would have escalated to the operating sponsor with "the new AI system does not work for our new product line". The signal caught it before complaints accumulated.

In week six, the user feedback signal goes red. Thumbs down rate jumps from 8 percent to 15 percent. Sampling negative feedback reveals the pattern: agents are dissatisfied with response length, specifically that responses are too long when they need a quick answer. The fix involves adjusting the prompt to default to shorter answers, with longer answers available on request. The thumbs down rate returns to 8 percent within a week.

Latency stays green throughout. If the team had been watching only latency, they would have concluded the system was healthy and missed three real issues that each required a fix.

The interesting comparison is with another Qantas AI project that monitored only latency and uptime. The cost overage was discovered at end of month and was 60 percent over budget. The refusal rate issue was discovered through a complaint from a department head three weeks after it started. The user feedback issue was discovered through a survey conducted at the end of the first quarter, by which time several agents had stopped using the system. The team spent the second quarter recovering from problems that monitoring would have caught early.

The lesson for AI delivery is that AI systems need AI-specific monitoring. The four signals are not optional. They are leading indicators that catch problems before they damage trust. The investment in setting them up is small, the leverage is enormous, and the discipline of looking at them daily is what makes the difference between a system the operating team trusts and a system the operating team merely tolerates.

**定义**

监控生产里的 AI 系统跟监控传统软件系统不一样。传统系统主要监控可用性和延迟: 还活着吗、快吗? AI 系统需要这些, 加上三个对 LLM 驱动产品独有的信号: 成本 (因为每次调用成本可变, 会膨胀)、拒绝率 (因为模型能决定不答, 这对传统监控不可见)、用户反馈 (因为输出质量是实际产品, 只有用户能评判)。这一节是关于哪些信号优先、怎么设置、信号变差时做什么。

**为何在交付中重要**

把 AI 系统按传统系统的方式监控的团队, 会错过 AI 独有的 issue。经典例子: 一个 AI 助手部署到生产, 监控可用性和延迟, 六周都绿。第七周, 成本是预算的 10 倍, 因为上游一次变化让用户输入比预期的长, 没人在看 token 使用。账单到达时, 项目超预算、团队在危机中。成本信号是先行指标, 没人看它。

优先级顺序重要, 因为对所有东西平等监控等于什么都不监控。试图追踪 20 个信号的团队, 没一个被认真追踪。下面的顺序反映了"在真实 AI 部署里, 什么倾向于出错, 按什么顺序"。

**运作原理**

四个信号, 按优先级:

| 信号 | 为什么重要 | 追踪什么 | 告警阈值 (典型) |
|---|---|---|---|
| 延迟 | UX 影响、用户信任 | p50、p95、p99 响应时间 | 流式 p95 超过 5 秒, 非流式超过 10 秒 |
| 成本 | 预算控制、可持续性 | 每请求成本、每日总额、月预测 | 每日成本超过预算 run rate 的 130% |
| 拒绝率 | 隐藏质量信号 | 产出拒绝或空输出的请求百分比 | 高于 5% 基线, 在基线 2 倍时告警 |
| 用户反馈 | 实际质量信号 | 点赞/点踩、明确反馈、支持工单 | 点踩率超过 10%, 或突然飙升 |

每个信号有不同的 dashboard、不同的告警阈值、不同的响应 playbook。试图合并它们产出没人懂的 dashboard。

**延迟详解**

AI 系统的延迟主要由模型调用支配, 它是可变的, 取决于输入大小、输出大小、模型可用性。要追踪的指标:

First token 时间 (流式系统): 用户看到任何东西之前的时间。用户把这感知为响应性。目标: 流式低于 2 秒。

总响应时间: 完整响应交付之前的时间。目标按用例变, 聊天典型低于 10 秒, agentic 流更长。

p50、p95、p99: 中位数、95 分位、99 分位。p99 揭示影响少数但真实用户的最坏情况。

延迟降级时做什么: 先看模型厂商的状态页, 然后看最近的变化是否改了 prompt 长度或输出长度, 然后看是否在打限流。修复看原因。

**成本详解**

AI 系统的成本是按 token 计算, 乘以调用量, 输入 token 便宜、输出 token 贵。成本会以四种方式失控: 调用比预期多、输入比预期长、输出比预期长、意外切换到更贵的模型。要追踪的指标:

每请求成本: 一次用户交互的平均成本。追踪这个, 注意漂移。

每日总成本: 对抓住量飙升有用。

月预测成本: 从当前 run rate 外推, 跟预算对比。

按 tier 或 use case 的成本: 如果系统处理多种请求, 按类别拆开成本, 找哪个 tier 在吃预算。

成本降级时做什么: 识别四种原因里哪个在场 (量、输入长度、输出长度、模型选择), 应用靶向修复。经常修复在 prompt 层 (缩短 prompt) 或路由层 (把更多查询发到更便宜的模型)。

**拒绝率详解**

拒绝率是模型决定不答、返回错误、或返回非常短或空响应的请求百分比。它是 AI 部署里信号最高但最少被看的指标之一。拒绝率飙升经常比用户投诉早几小时或几天。

要追踪的指标:

整体拒绝率: 返回空、短、或拒绝 pattern 输出的请求百分比。

按查询类型的拒绝率: 如果某些类别的查询被以更高率拒绝, 这有信息量。

拒绝率趋势: 在涨、降、还是稳?

拒绝率飙升时做什么: 看最近的变化是否改了 system prompt 或模型。看模型厂商的内容过滤是否变化。采样被拒绝的查询, 看它们有什么共同点。

**用户反馈详解**

用户反馈是实际质量信号。系统能延迟绿、成本绿、拒绝率绿, 还在产出用户不喜欢的差输出。反馈是唯一抓得到这个的信号。

要追踪的指标:

点赞/点踩率: 如果系统有反馈机制, 这是主要信号。

明确反馈: 用户邮件或消息提 issue。

跟系统相关的支持工单量。

如果定期做, 调研结果。

反馈降级时做什么: 采样负反馈识别 pattern, 把 pattern 跑过 eval set 看是否被捕捉, 给新失败模式加 eval 行, 迭代 prompt。

**搭监控栈**

一个生产 AI 系统合理的监控栈有三层。基础设施监控 (延迟、错误、可用性) 用客户的标准。应用监控 (成本、token 使用、拒绝率、模型表现) 用厂商工具加自定义 dashboard。用户反馈 (点赞、调研、支持工单) 用产品自己的反馈机制加客户的支持工单系统。

Dashboard 在前 30 到 90 天对运营团队和交付团队都可见, 之后主要对运营团队可见。从"交付团队看"到"运营团队看"的过渡应该刻意。

**PM 决策点**

- 四个信号都在被监控、阈值设好了吗, 还是我只在看延迟和可用性?
- 运营团队知道每个信号意味着什么、怎么响应吗?
- 成本信号每天都在看吗, 不是只在月底账单到时看?

**注意事项**

- 成本是最可能被忽略直到变成危机的信号。每天看。
- 拒绝率是最可能被完全错过的信号。很多团队甚至没埋点。
- 用户反馈是最可能被收集但不被行动的信号。指标没有"调查负反馈、反馈给 eval set"的流程, 就没用。

**要点总结: 按优先级监控四个 AI 特有的信号: 延迟、成本、拒绝率、用户反馈。每个有自己的 dashboard、阈值、响应 playbook。每天看成本。及时调查拒绝率飙升。把负的用户反馈反馈给 evals。运营团队应该在 30 到 90 天内拥有这些。**

**Qantas 案例**

设想你上线一个 Qantas AI 项目, 一个给呼叫中心的内部助手, 帮坐席查客户政策信息。系统在跑, 呼叫中心团队在用, 交付团队在上线后第一个月的支持期。诱惑是看延迟就够了。

PM 坚持完整的四信号监控配置。延迟在现有 Qantas 基础设施 dashboard 上。成本在一个项目期间建的自定义 dashboard 上, 显示每日花费、每查询成本、月预测。拒绝率在同一个自定义 dashboard 上, 显示空或短输出的百分比。用户反馈通过每次坐席交互的点赞点踩收集, 负反馈带评论字段。

生产第二周, 成本信号变红。每日成本从预算的每天 200 美元跳到 340 美元。PM 和技术负责人调查。原因不是量 (每日查询稳定), 是输入长度: 坐席界面最近一次更新加了客户之前交互的上下文, 让平均输入长度翻倍。修复是把上下文发给模型之前总结一下, 恢复输入长度。两天内成本回到预算。

没有每日看成本信号, 月度账单会到达, 显示超支 70%, 运营团队会在危机中, 项目会失去可信度。信号在变化 48 小时内抓住, 修复用半天。

第四周, 拒绝率信号变红。拒绝从 2% 基线跳到 6%。PM 采样被拒绝的查询。Pattern: 坐席在问助手前一周发布的新产品线的事, 那不在助手的知识库里。模型在正确拒绝因为它不知道, 但体验差。修复是把新产品信息加到知识库。拒绝率一天内回到基线。

没有看拒绝信号, 坐席会继续在新产品上经历高拒绝率, 跟经理抱怨, 经理升级到运营 sponsor "新 AI 系统在我们新产品线上不工作"。信号在投诉累积之前抓住。

第六周, 用户反馈信号变红。点踩率从 8% 跳到 15%。采样负反馈揭示 pattern: 坐席对响应长度不满, 具体是他们需要快速答案时响应太长。修复涉及调 prompt, 默认更短答案, 按需提供更长答案。点踩率一周内回到 8%。

延迟全程绿。如果团队只在看延迟, 会结论说系统健康, 错过三个真实的、各自需要修复的 issue。

有意思的对照是另一个只监控延迟和可用性的 Qantas AI 项目。成本超支在月底被发现, 超预算 60%。拒绝率 issue 通过部门负责人的投诉被发现, 在开始三周后。用户反馈 issue 通过第一季度末的调研被发现, 那时几个坐席已经停止用系统。团队花第二季度从"监控本能早抓住"的问题里恢复。

AI 交付的启示是, AI 系统需要 AI 特有的监控。四个信号不可选。它们是先行指标, 在问题损害信任之前抓住。搭建它们的投资小, 杠杆大, 每天看它们的纪律是"运营团队信任的系统"和"运营团队只是容忍的系统"的区别。
