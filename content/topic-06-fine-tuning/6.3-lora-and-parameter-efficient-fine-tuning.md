**Definition**

LoRA (Low Rank Adaptation) is the most common form of parameter efficient fine tuning. Instead of updating all the weights of a large model during training, LoRA freezes the original weights and trains a small set of additional weights, typically 0.1 to 1 percent of the total. The result behaves like a fine tuned model but is far cheaper to train and serve.

**Why it matters in delivery**

Full fine tuning of a large model is expensive, slow, and produces a separate full copy of the model that you have to host. LoRA changes the economics. You can fine tune large open weight models on a single GPU in hours instead of weeks on a cluster. You can also stack multiple LoRA adaptations for different clients on top of the same base model, dramatically lowering serving costs. This is the technique that makes self hosted fine tuning practical for most teams.

**How it works**

| Method | What gets trained | Training cost | Serving cost |
|---|---|---|---|
| Full fine tuning | All model weights | Very high (cluster, days to weeks) | Full size model |
| LoRA | Small adapter matrices (0.1 to 1% of weights) | Low (single GPU, hours) | Base model plus tiny adapter |
| QLoRA | LoRA on a quantised (compressed) model | Lowest (consumer GPU possible) | Even lower memory |
| Prefix tuning | Trained virtual tokens prepended to input | Low | Adds tokens to context |

Visually, full fine tuning is like rewriting the model. LoRA is like attaching a small "personality module" that modifies the model's behaviour at inference time without changing the underlying weights.

The serving benefit is huge: you can swap LoRA adapters per request, so one base model can serve dozens of fine tuned variants without loading separate models into memory.

**PM decision points**

- Is the project doing open weight fine tuning where LoRA applies, or closed API fine tuning where the provider handles it?
- Will the system serve multiple fine tuned variants, where LoRA's adapter swapping shines?
- Has the team tested LoRA against full fine tuning, the quality gap is often negligible?

**Watch outs**

- LoRA quality is excellent for style and tone, slightly weaker for teaching genuinely new knowledge
- LoRA adapters are model specific, switching base models means redoing the work
- Closed API fine tuning often uses LoRA under the hood without telling you, which is fine

**Takeaway: LoRA makes fine tuning practical. Use it as the default for self hosted fine tuning unless there is a clear reason to go full parameter.**

**Qantas story**

If Qantas were to operate fine tuned models in production at scale, LoRA would almost certainly be the right approach. The economics make the difference between fine tuning being a curiosity and being a practical production pattern.

Consider the hypothetical Qantas customer service classification use case from earlier. The team needs a fine tuned model that classifies inbound customer interactions across roughly 80 categories (rebooking, refund, lost baggage, status query, dietary request, special assistance, frequent flyer issue, codeshare issue, and so on). Full fine tuning of a 70B model would require multiple GPUs, days of training time, and produce a 70B parameter copy of the model that needs its own deployment infrastructure. The cost is real and the operational overhead is significant.

LoRA changes the math. The team can fine tune a small adapter (maybe 0.5 percent of the model parameters) on a single GPU in a few hours. The base model stays the same. The adapter modifies behaviour at inference time without changing the underlying weights. Serving the fine tuned model means loading the base model into GPU memory and applying the adapter, which adds essentially zero latency.

The bigger win is that LoRA enables multiple fine tuned variants on the same base model. Qantas could have one base 70B model in production, with separate LoRA adapters for customer service classification, marketing copy generation, internal knowledge search, and a few other use cases. Each adapter is small, can be swapped in per request, and runs on the same underlying infrastructure. The GPU footprint is one base model, not five separate ones.

The cost saving at airline scale would be substantial. A naive architecture with five separate full fine tuned models might cost AUD 400K per year in inference infrastructure. The LoRA architecture might cost AUD 80K for the same capability. The quality difference, on the specific narrow tasks the adapters were trained for, is typically within a percentage point of full fine tuning.

The interesting operational question is who manages the adapters. They are not the same as model deployments. They have lifecycle considerations (when does a Q3 trained adapter get retired, what regression testing applies to a new adapter version). The MLOps discipline for adapter management is newer and less standardised than for full model deployments. Teams that grow into this without thinking about governance end up with adapter sprawl.

For AI delivery, the lesson is that LoRA is what makes self hosted fine tuning practical for enterprise scale. The technical primitive is mature, the economics work, and the operational patterns are emerging. The mature delivery posture is to assume LoRA as the default for any open weight fine tuning, and to design for adapter portfolio management from day one rather than discovering it later.

**定义**

LoRA (Low Rank Adaptation) 是参数高效 fine tuning 里最常见的一种。LoRA 不在训练时更新大模型的全部权重,而是把原始权重冻住,只训练一小组额外的权重,通常只占总参数的 0.1 到 1%。最终效果跟一个完整 fine tune 过的模型差不多,但训练和服务两端的成本都低得多。

**为何在交付中重要**

大模型的完整 fine tuning 又贵又慢,而且会产出一份你必须自己托管的完整模型副本。LoRA 把这套经济学改了。你可以在几小时内、在单张 GPU 上 fine tune 一个大型 open weight 模型,而不需要跑一个集群、花几周。你还可以在同一个基础模型之上叠加多个 LoRA 适配,服务成本一下子就下来了。LoRA 是让"自托管 fine tuning"对大多数团队真正可行的那项技术。

**运作原理**

| 方法 | 训练什么 | 训练成本 | 服务成本 |
|---|---|---|---|
| 完整 fine tuning | 模型的全部权重 | 非常高 (集群、几天到几周) | 完整大小的模型 |
| LoRA | 一组小的适配器矩阵 (权重的 0.1 到 1%) | 低 (单 GPU、几小时) | 基础模型 + 一个很小的适配器 |
| QLoRA | 在量化 (压缩过) 模型上的 LoRA | 最低 (消费级 GPU 都能跑) | 内存占用更低 |
| Prefix tuning | 把训练好的虚拟 token 前置到输入 | 低 | 上下文里多占一些 token |

形象一点说: 完整 fine tuning 像把模型重写一遍。LoRA 像给模型挂上一个小"性格模块",在推理时修改它的行为,但不动底层权重。

服务侧的收益是巨大的: 你可以按请求换 LoRA 适配器,所以一个基础模型能服务几十个 fine tune 过的变体,而不用把每个变体单独加载到内存里。

**PM 决策点**

- 这个项目是在做 open weight 的 fine tuning (LoRA 适用),还是 closed API 的 fine tuning (厂商在背后处理)?
- 系统会不会服务多个 fine tune 过的变体?如果是,LoRA 的"适配器热切换"能力是非常大的杠杆。
- 团队有没有把 LoRA 跟完整 fine tuning 做过对比测试?质量差距通常小到可以忽略。

**注意事项**

- LoRA 在教风格和语气上效果很好,在教真正"新知识"上稍弱。
- LoRA 适配器是绑模型的。换基础模型,意味着所有训练要重做。
- Closed API 的 fine tuning 经常在引擎盖下就是用 LoRA,虽然厂商不告诉你,这没什么问题。

**要点总结: LoRA 让 fine tuning 真正实际可行。除非有清楚的理由要做完整参数训练,自托管 fine tuning 都默认走 LoRA。**

**Qantas 案例**

如果 Qantas 要在生产规模上跑 fine tune 过的模型,LoRA 几乎肯定是对的方法。这里经济学的差异,就是"fine tuning 是好奇心实验"和"fine tuning 是真正的生产 pattern"之间的差距。

回到之前那个假设的 Qantas 客服分类用例。团队要一个 fine tune 过的模型,能把进来的客户交互分到大约 80 个类目里 (改签、退款、行李丢失、状态查询、餐饮请求、特殊援助、Frequent Flyer 问题、代码共享问题等等)。一个 70B 模型完整 fine tuning,需要多张 GPU、几天的训练时间,产出的是 70B 参数的一份完整副本,这份副本还要有自己的部署基础设施。成本是真实的,运营开销也很大。

LoRA 把这套数学改了。团队可以在几小时内、用单张 GPU、fine tune 一个小的适配器 (可能就是模型参数的 0.5%)。基础模型保持不变。适配器在推理时修改行为,不动底层权重。服务这个 fine tune 过的模型,意思就是把基础模型加载到 GPU 内存,然后应用适配器,延迟几乎不增加。

更大的收益是: LoRA 让"同一个基础模型上叠加多个 fine tune 过的变体"成为可能。Qantas 可以在生产里只跑一个基础 70B 模型,然后在它之上分别挂客服分类、营销文案生成、内部知识搜索等几个用例的独立 LoRA 适配器。每个适配器都很小,可以按请求热切换,跑在同一套底层基础设施上。GPU 占用是一个基础模型,而不是五个独立模型。

在航空规模上,省下来的钱是相当可观的。一种天真的架构,五个独立的完整 fine tune 模型,每年在推理基础设施上可能要花 40 万澳元。同样能力,LoRA 架构每年可能只要 8 万澳元。质量差距,在每个适配器训练针对的那个具体窄任务上,通常跟完整 fine tuning 差距不到一个百分点。

有意思的运营问题是: 谁来管这些适配器。它们跟模型部署不是同一件事。它们有自己的生命周期考虑 (一个 Q3 训练的适配器什么时候退休?新适配器版本要跑什么回归测试?)。适配器管理的 MLOps 纪律,比完整模型部署更新、更不标准化。一头扎进去没想治理的团队,最后会被适配器爆炸搞到崩溃。

往大了说,这件事给 AI 交付的启示是: LoRA 是让自托管 fine tuning 在企业规模上真正可行的那项技术。底层技术成熟,经济学算得过来,运营 pattern 也在快速成形。成熟的交付姿态是: 任何 open weight fine tuning 默认走 LoRA,从第一天起就为"适配器组合管理"做设计,而不是等到后面才发现这件事。
