**Definition**

Model tiering is the practice of routing different queries to different models based on difficulty. Simple queries go to a small fast cheap model. Hard queries go to the flagship. The routing can be hardcoded (per workflow), classifier based (a small model decides), or rule based (keywords, context size, user tier).

**Why it matters in delivery**

Sending every query to the flagship model is the single most common cost mistake in production AI. Most production traffic does not need the smartest model. Tiering can cut cost by 60 to 90 percent with little or no quality loss. PMs who push for tiering early ship products with sustainable unit economics.

**How it works**

| Routing strategy | How it works | Best for |
|---|---|---|
| Hardcoded by workflow | Specific tasks always use specific models | Clear separation of simple vs complex workflows |
| Classifier router | A small model classifies query difficulty, picks the right model | Mixed traffic with varied difficulty |
| Rule based | Query length, presence of code, user tier, document size | Predictable patterns |
| Cascading | Try cheap model first, escalate to expensive if it fails | Reasoning quality varies per query |
| Tier by user | Free users get cheap model, paid users get flagship | Consumer products with tiered offers |

A typical production pattern: 70 percent of queries handled by small/mid tier, 25 percent by mid tier, 5 percent by flagship for the genuinely hard ones.

**PM decision points**

- Has the team profiled real traffic to see what percentage of queries actually need the flagship?
- Is the router itself a cost or latency burden, especially classifier based ones?
- How is quality monitored per tier, are cheap tier failures escalating correctly?

**Watch outs**

- Classifier routers can get the difficulty wrong, leading to silent quality drops on the cheap tier
- Tier changes break evals, you need separate eval sets per tier
- Over engineering routing for a use case that does not have varied difficulty wastes time

**Takeaway: most production traffic does not need the flagship. Route by difficulty, monitor per tier, accept that 5 percent of queries justify the expensive model.**

**Qantas story**

Model tiering is one of the most underutilised cost optimisations in enterprise AI, and Qantas at scale would benefit substantially from disciplined tiering.

Consider a hypothetical Qantas customer service AI handling 80,000 customer interactions per day. The naive architecture sends every query to Claude Sonnet, which produces consistently good quality but at meaningful cost. The monthly bill for this workload at typical pricing comes to roughly AUD 50K.

A traffic analysis reveals the underlying distribution. Roughly 50 percent of queries are simple lookups (where is my booking, what time is my flight, what is my points balance). 35 percent are moderate complexity (rebooking after a delay, fare rule explanations, status match questions). 15 percent are genuinely hard (complex multi sector itinerary changes, accumulated frequent flyer disputes, special service requests with multiple constraints).

The tiered architecture routes by complexity. Simple lookups go to Haiku, which handles them well at roughly one tenth the cost of Sonnet. Moderate complexity goes to Sonnet, which is the workhorse for typical queries. Hard queries go to Opus, where the additional reasoning capability is justified by the complexity.

The new cost math is different. Simple queries at one tenth the cost. Moderate queries unchanged. Hard queries at three times the cost but only on 15 percent of traffic. Net effect: monthly bill drops from AUD 50K to roughly AUD 18K. Same overall quality on evals because each tier was selected for the queries it actually handles. Saved AUD 384K annually.

The routing layer is where the work is. The simple option is hardcoded routing by query type, which works when query types are clearly bounded. The more sophisticated option is a classifier model that decides difficulty, which handles ambiguous cases better but adds its own cost and latency. Most production systems start with hardcoded routing and add classifier based routing only where workflow boundaries are genuinely unclear.

The interesting failure mode is routing errors. A hard query routed to Haiku gets a thin answer, and the customer is poorly served. The defence is a confidence check: if the model on the lower tier expresses uncertainty or refuses to answer, escalate to the higher tier rather than ship the weak answer. This adds latency for the escalated cases but protects quality.

The other consideration is quality monitoring per tier. The eval set needs to include examples appropriate to each tier and the metrics tracked per tier. Lumping all tiers into a single quality metric obscures cases where the lower tier is silently underperforming on edge cases.

For AI delivery, the lesson is that model tiering is rarely the most visible architectural decision but often the one with the highest financial impact. Clients are usually unaware of how much they can save by tiering, because their mental model is "use the best model." Walking them through the math during scoping, ideally with their actual traffic distribution, makes the case directly. Most accept tiering when they see the numbers.

**定义**

模型分层是有意将工作流路由到不同模型尺寸的实践,匹配模型成本/能力到任务难度。简单任务路由到便宜小型模型 (Haiku, Gemini Flash, GPT nano)。中等任务路由到中层模型 (Sonnet, GPT mid, Gemini Pro)。困难任务路由到旗舰模型 (Opus, GPT large, Gemini Ultra)。

**为何在交付中重要**

模型分层是任何 AI 项目中最高杠杆的成本优化。它需要设计 (路由层,每层 eval),但收益是 5 到 10 倍的成本减少而没有显著的质量损失。理解模型分层是项目预算可以发布与不能发布之间的区别。

**运作原理**

路由模式:

| 模式 | 它如何工作 | 适合 |
|---|---|---|
| 静态路由 | 不同工作流硬编码到不同模型 | 当工作流是分离的并且边界已知时 |
| 基于复杂性的路由 | 分类器决定每个请求的难度,路由相应 | 当一个工作流跨越难度时 |
| 升级路由 | 从便宜模型开始,如果它失败,升级到更昂贵的模型 | 当大多数请求容易但有些需要更多 |
| 双 LLM 路由 | 小型模型路由器决定哪个旗舰模型 | 当复杂工作流需要不同的旗舰功能 (推理 vs 长上下文) |
| 自我路由 | 模型决定它是否能处理或转交 | 实验性,质量参差不齐 |

简单基于复杂性的路由器示例:

```
def route(user_query):
    classifier_output = haiku.classify(user_query, categories=["simple", "complex"])
    if classifier_output == "simple":
        return haiku.generate(user_query)
    else:
        return opus.generate(user_query)
```

分类调用本身在便宜模型上几乎免费。它将昂贵模型调用减少 60 到 80%,因为大多数生产流量实际上是简单的。

**PM 决策点**

- 我们的流量混合是什么? (在严肃地构建路由之前剖析它)
- 我们如何处理路由错误? (路由器有时会出错,有回退)
- 我们如何评估路由器决策的质量?

**注意事项**

- 路由器本身需要 evals,糟糕的路由器使整个系统更糟
- 输出 token 价格意味着即使便宜模型可能贵,如果它产生太多输出
- 当提供商发布新层时,重新审视路由,经济学经常转移

**要点总结: 不要默认旗舰为所有事情。设计为合适使用便宜模型的层级路由。**

**Qantas 案例**

模型分层是为 Qantas 假设的客户服务 AI 助手交付可持续经济学的核心架构决定。它将每年 $4.3M 转为每年 $300K,如前所述。

实际路由模式将看起来如下。一个分类层 (Haiku 或类似小型模型) 看每个入站查询并按复杂性标记它。简单查询 (例如,"我的航班号是什么?", "我的预订时间是几点?") 路由到 Haiku 与紧凑的检索上下文。中等查询 (例如,"我可以使用积分升级吗?", "什么是行李津贴?") 路由到 Sonnet,具有更丰富的检索上下文和更宽松的 prompt 指导。复杂查询 (例如,"我有一个复杂的多段行程问题", "我有一个特殊援助需求") 路由到 Opus。

路由器本身使用 Haiku 评估每个查询的复杂性。这成本几乎为零 (Haiku 上每查询微分),但它将昂贵的 Opus 调用减少到所需的 5 到 10%。

分布大致看起来如此:
- 70% 简单 -> Haiku, $0.0024 per call
- 20% 中等 -> Sonnet, $0.009 per call
- 10% 复杂 -> Opus, $0.045 per call

加权平均成本: $0.007 per call。比纯 Opus 便宜 6.5 倍。比纯 Sonnet 便宜 30%。质量在 95% 以上的客户互动上保持不变,因为复杂查询仍然得到旗舰处理。

路由层添加它自己的复杂性。它需要为路由准确性自己的 eval。它需要回退,当分类不确定。它需要在工作流随着新功能添加而演变时维护。但它是工程的工作合理的。

更有趣的杠杆是分层的不同形状。"双模型路由"模式生成两个候选响应 (来自不同模型),然后使用第二次 LLM 调用来决定哪个更好。这增加质量但成本翻倍,所以它在特定高风险场景中赢得位置。"升级路由"从 Sonnet 开始,如果输出质量分数低 (来自启发式或评判模型) 升级到 Opus。这本质上是相同思想,但反应性而不是先验。

对 AI 交付来说,启示是模型分层是范围确定中可以推荐的最有影响力的架构选择之一。客户经常默认到"使用最佳模型为一切",并对成本计算感到惊讶。能够在范围确定时呈现层级路由架构,具有现实的成本和质量预测,引导客户到他们可以实际负担的产品。这就是 AI 项目以可持续经济学发布的方式。
