**Definition**

Caching reuses previous results to avoid repeated computation. Prompt caching reuses portions of long prompts (system prompt, retrieved docs) across requests at a discount from the provider. Semantic caching matches new queries to similar past queries and returns the cached answer. Output caching stores full responses by input hash for exact repeat matches.

**Why it matters in delivery**

Caching is the highest leverage cost optimisation after model tiering. Done well, it cuts input cost by 60 to 90 percent and latency by similar amounts. Done badly, it serves stale answers and breaks trust. PMs who understand the three types and their trade offs design systems that scale economically.

**How it works**

| Cache type | What it does | Hit rate typical | Risk |
|---|---|---|---|
| Prompt caching (provider) | Reuses cached prefix of input (system prompt, RAG context) | Very high on stable prefixes | Low, provider handles freshness |
| Semantic caching | Returns past answer for semantically similar query | 10 to 40 percent depending on traffic | Medium, similar query may need different answer |
| Output caching | Returns exact past answer for exact input | High in FAQ workloads | Low, but limited applicability |
| RAG result caching | Caches retrieval results for repeated queries | Medium to high | Low, but retrieval index changes invalidate |

**Worked example, prompt caching impact**

System prompt: 800 tokens. Tool definitions: 1,200 tokens. Retrieved context: 2,000 tokens. User query: 100 tokens. Total input: 4,100 tokens.

Without caching, you pay full rate for all 4,100 tokens every call. With prompt caching, the first 4,000 tokens (system + tools + context) are cached. Subsequent calls pay full rate only on the changing portion (user query, ~100 tokens). At a 90 percent cache discount, input cost drops by roughly 88 percent. Latency to first token also drops substantially.

**PM decision points**

- Is prompt caching enabled and structured to maximise hits, e.g. stable prefixes before variable user input?
- Is semantic caching appropriate for the workload, or does every query genuinely differ?
- How is cache invalidation handled when content changes upstream?

**Watch outs**

- Semantic caching can return wrong answers when "similar" queries actually mean different things
- Cache TTLs need to match data freshness requirements, real time data should not be cached
- Prompt caching has minimum size thresholds, very short prompts may not qualify

**Takeaway: prompt caching is the cheap win, structure prompts to maximise it. Semantic caching is powerful but risky, validate hit quality.**

**Qantas story**

Caching at Qantas scale produces some of the biggest cost wins available, and the strongest cache patterns are often invisible to product teams that have not actively designed for them.

Consider a hypothetical Qantas customer service AI assistant with a large system prompt (about 2,500 tokens of role, tone, refusal patterns, and tool descriptions) plus retrieved content per query (typically 4,000 to 6,000 tokens of relevant policy and product information). User queries themselves are usually short (50 to 200 tokens).

Without prompt caching, every query pays full token rate on the entire input, even though the system prompt is identical across all queries and the retrieved content is often similar across users asking about the same topic. The input cost per query is dominated by content that does not change.

With provider prompt caching, the system prompt is cached after the first call and reused at a significant discount on subsequent calls. The retrieved content for popular topics also caches, since the same documents are retrieved for many users asking similar questions. The effective per query input cost drops by 70 to 85 percent for typical traffic patterns.

The cost math is striking. At 80,000 queries per day with 2,500 token system prompt plus 5,000 token average retrieved content, the input token volume is 600 million tokens per day. Without caching, this is the headline cost driver. With caching, most of this volume is at the cached rate, and the effective input cost drops substantially.

Semantic caching is the next layer. Many customer service queries are near duplicates ("when does my flight leave," "what time does my flight depart," "what is my flight time"). All three queries semantically match the same answer. A semantic cache returns the previously generated answer without calling the model at all. Hit rates of 15 to 25 percent are common on FAQ heavy workloads.

The interesting design considerations around semantic caching are about freshness and correctness. A cached answer for "what time does my flight leave" is correct for one specific flight at one specific time, and becomes wrong the moment the flight is delayed. The cache needs to invalidate or be scoped tightly enough that staleness is bounded. Many production systems use semantic caching only for genuinely stable content (policy explanations, product information) and not for real time data.

Output caching for exact repeat queries works on the most predictable traffic. Common questions like "what is the international baggage allowance" appear hundreds of times per day with essentially identical phrasing. A simple input hash based cache returns the answer for free on the duplicates.

For AI delivery, the lesson is that caching is the single highest leverage cost optimisation after model tiering. The technical work is well understood. The discipline is in designing prompts to maximise cache hits (stable prefixes, variable user content at the end), invalidating caches appropriately when underlying content changes, and instrumenting cache hit rates so the team knows whether the discipline is paying off. Clients are often surprised by the impact of caching, and walking them through it during scoping anchors realistic cost expectations.

**定义**

缓存是把之前的计算 (响应、prompt 前缀、检索结果) 存起来,需要的时候直接复用而不是重新计算。在 AI 系统里,主要的缓存类型是: prompt 前缀缓存 (在 LLM 调用之间复用稳定的 prompt 部分)、完整响应缓存 (同样的输入返回同样的输出)、语义响应缓存 (语义相近的输入返回同样的输出)。

**为何在交付中重要**

缓存能给高量工作负载砍掉 50 到 90% 的成本和延迟。但设计不好的缓存会制造静默的正确性 bug——比如用户上下文变了,系统还在返回旧响应。理解缓存策略,就是知道"什么时候它是合适的优化、什么时候它是 bug 的来源"。

**运作原理**

| 类型 | 怎么工作 | 收益 | 风险 |
|---|---|---|---|
| Prompt 前缀缓存 | 跨多次调用保存稳定的 system prompt + 上下文 | 输入处理减少 70 到 90% | 低,厂商在管 |
| 完整响应缓存 | 对请求哈希,之前见过就返回缓存 | 精确重复时 100% 省 | 上下文敏感性 (用户 A 看到给用户 B 的回应) |
| 语义响应缓存 | 语义相近的查询返回同一个响应 | 在 FAQ 上节省可观 | 漏掉细微的语义差异 |
| KV 缓存 (自托管) | 单次请求内部复用注意力计算 | 看工作流 | 只在自托管时能动,厂商抽象掉了 |
| 检索缓存 | 缓存常见查询的检索结果 | 中等节省、检索延迟降低 | 检索源更新后会过期 |
| Embedding 缓存 | 同样文本不重算 embedding | 中等节省 (embedding 本来就便宜) | 换 embedding 模型时会过期 |

Prompt 前缀缓存是最容易拿到的胜利。Anthropic、OpenAI 和大部分主流厂商现在都提供它。开启它就是一个 API 标志。在 Anthropic 上,缓存命中只花原始处理成本的 10%。Qantas 一个 2000 token 稳定 + 500 token 动态的客服 prompt,开了 prompt 缓存,稳定那部分跨调用基本就是免费的。

**PM 决策点**

- 我们有没有充分用上 prompt 前缀缓存? (这件事通常默认是没开的,要主动问。)
- 完整响应缓存对这个工作流安全吗? (如果工作流带用户特定上下文,大概率不行。)
- 底层数据变化的时候,缓存怎么失效?

**注意事项**

- 完整响应缓存如果不小心 (没把用户 ID 放进缓存 key),会跨用户泄漏数据。
- 语义缓存用 embedding 相似度,但语义相近的问题可能有不同的答案 (比如"我的航班怎么样?"在不同时间点问的意思就不一样)。
- 厂商缓存有 TTL,超过 TTL 内容就用不上了 (Anthropic 默认 5 分钟,可以延长)。

**要点总结: 缓存能大幅砍成本和延迟,但需要谨慎设计。Prompt 前缀缓存是稳赢,响应缓存有时候是危险的。**

**Qantas 案例**

Qantas 客服 AI 的缓存策略大概会是这样。

Prompt 前缀缓存是不带犹豫的胜利。每次客服调用的 system prompt 是 2200 tokens (角色、工具描述、品牌指导、规则、示例),跨所有调用都是稳定的。开了 prompt 缓存之后,这 2200 tokens 在每次调用上花 $0.0003 而不是 $0.003。每天 5 万次调用,就是每天省 $135,每年 $49,275——光是打开一个 API 开关。

工具描述也享受缓存待遇。工具列表稳定的时候,工具 schema 也是 prompt 缓存的一部分。检索回来的文档不享受 prompt 缓存,因为它们随查询变化,但 system prompt + 工具描述享受。

完整响应缓存对客服 AI 来说很危险。响应取决于客户特定的上下文 (他们的订单、他们的等级、他们的历史)。两个客户问同样的问题,正确答案可能不同。完整响应缓存会制造数据泄漏: 客户 A 看到给客户 B 计算的响应。在这个上下文里它行不通。

但完整响应缓存在其他用例里很好用。比如 Qantas 政策的"常见问题"内容,"行李额度多少?"、"Frequent Flyer status match 规则是什么?" 答案不是用户特定的,是政策事实,在政策变更前一直有效。响应可以积极缓存。这能从那种"每周被问几千次同样问题"的查询里砍下大量成本,而不影响质量。

语义响应缓存是中等风险。"我能改我的航班吗?"和"我能修改我的订单吗?" 语义相近,但具体答案可能因订单属性而不同。语义响应缓存在通用信息查询上有效,在订单特定查询上失效。生产 pattern 经常是: 对前 100 个常见问题用语义缓存,对订单或客户特定查询不用。

检索缓存是中等收益。常见检索查询 ("行李政策") 命中的是同一组检索文档 chunk。缓存这些可以避免每次都重新查 vector DB。节省幅度适中 (检索本身就快),但延迟下降是真切的。

有意思的失败 pattern 是缓存失效太慢。如果 Qantas 行李政策在 9 月 15 日变更,缓存的响应需要立即失效。如果它们继续返回旧答案好几天,客户就拿到了错误信息,Qantas 还得发更正。失效是缓存设计里关键的一部分,经常被低估。

往大了说,这件事给 AI 交付的启示是: 缓存是真实的杠杆,但它需要架构上的思考。Prompt 前缀缓存是没理由不打开的胜利。响应缓存是用例特定的,需要合适的隔离 (按用户做缓存 key)。语义缓存对常见查询很强,对上下文特定查询很危险。设计缓存周到的团队,永远不会为他们不需要付的 token 费用买单。不投入的团队会。
