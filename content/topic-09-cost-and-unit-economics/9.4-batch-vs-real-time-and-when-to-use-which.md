**Definition**

Real time inference processes requests as they arrive, returning responses synchronously, typically within seconds. Batch inference accumulates many requests and processes them together asynchronously, returning results minutes to hours later. Most providers offer batch APIs at 30 to 50 percent of real time pricing.

**Why it matters in delivery**

Many enterprise AI workloads do not need real time. Classifying support tickets overnight, summarising yesterday's call recordings, enriching customer records weekly, none of these need a sub second response. Defaulting everything to real time leaves real money on the table. PMs who recognise batchable workloads cut costs meaningfully without touching prompts, models, or architecture.

**How it works**

| Workload | Latency requirement | Batch suitable? | Typical savings |
|---|---|---|---|
| User facing chatbot | Seconds | No | N/A |
| Real time search | Sub second | No | N/A |
| Ticket classification overnight | Hours | Yes | 30 to 50 percent |
| Document enrichment | Hours to days | Yes | 30 to 50 percent |
| Periodic summarisation | Hours | Yes | 30 to 50 percent |
| Training data generation | Days | Yes | 30 to 50 percent |
| Mass content generation | Hours | Yes | 30 to 50 percent |
| Bulk data extraction | Hours | Yes | 30 to 50 percent |

Beyond direct cost savings, batch APIs typically have higher rate limits and let you process large volumes that would hit real time throttling.

**PM decision points**

- For each AI workload, what is the actual latency requirement, hours, minutes, seconds?
- Are workloads that should be batch running on real time APIs out of habit?
- Does the chosen provider offer batch APIs for the model the team needs?

**Watch outs**

- Batch APIs have variable turnaround times, plan for the long tail
- Not all providers offer batch for all models, check before scoping
- Batch jobs need error handling for partial failures, not all of a batch may succeed

**Takeaway: batch is a 30 to 50 percent discount for the workloads that can tolerate latency. Audit workloads and move what you can.**

**Qantas story**

Qantas has many AI workloads that do not need real time response and are paying real time prices unnecessarily. Recognising which workloads can run as batch is a quick win that often saves 30 to 50 percent of cost on the affected pipelines.

Consider a hypothetical Qantas customer feedback analysis pipeline. The pipeline takes inbound customer comments from multiple channels (post flight surveys, social media, contact centre transcripts) and uses AI to classify sentiment, identify themes, extract specific service mentions, and flag urgent issues. Volume might run to 50,000 to 100,000 items per day.

The naive architecture treats each item as a real time inference call, with the AI processing items as they arrive. Total monthly cost at scale is meaningful. The realisation is that this workload does not need real time at all. Customer feedback analysis is a daily or weekly process. Nothing happens at midnight that needs to wait for sentiment analysis on a survey submitted at noon. The pipeline can run as a daily batch job that processes the day's accumulated feedback overnight.

Moving to a provider's batch API (Anthropic and others offer batch processing at roughly half the real time price, with turnaround times of several hours) cuts the cost of the workload by close to 50 percent for the same volume and same model. The engineering work to convert is small (collect items into batches, submit batch jobs, process results when ready). The savings are immediate.

Other Qantas workloads with similar characteristics include marketing copy generation (the team produces campaign assets in batches, not in real time), engineering manual analysis (a batch process to extract structured data from technical documents, run quarterly), and document enrichment workflows (adding AI generated tags to large document collections, run as needed).

The pattern is to ask, for each AI workload, what the actual latency requirement is. If the answer is "by tomorrow morning" or "by end of week," the workload is a batch candidate. If the answer is "within seconds," it needs real time. Many workloads default to real time out of habit, not requirement.

The interesting failure modes are around batch error handling. Real time inference has clean retry semantics: a failed call gets retried immediately. Batch inference can have partial failures within a batch, which need to be handled. The orchestration code needs to track which items in a batch succeeded and which failed, retry the failures, and produce a complete result set even when individual items had issues. This is not hard but it is different from real time error handling.

For AI delivery, the lesson is that the batch versus real time question is one of the easiest cost optimisations to identify and one of the most commonly overlooked. The default is real time because that is how AI demos are built. The reality is that many enterprise workloads have latency tolerances of hours or days, and moving them to batch is a meaningful saving with minimal engineering work. Clients are typically unaware of this lever, and a quick audit of "which workloads can run as batch" during a cost review often surfaces immediate savings.

**定义**

实时 AI 调用响应当用户等待时 (聊天,搜索,即时响应)。批处理 AI 调用在后台运行,可能在分钟、小时或天的工作流中 (报告生成,数据丰富,夜间处理)。它们具有非常不同的成本、设计、和运营画像。

**为何在交付中重要**

许多被定为"AI 应用"的项目实际上是批处理工作流,被设计为它们是实时聊天机器人。这增加成本,放慢交付,并增加复杂性而无价值。能够将真正的批处理工作流与真正的实时工作流分开的 PM 节省时间并发布更快的项目。

**运作原理**

| 模式 | 它如何工作 | 优势 | 劣势 |
|---|---|---|---|
| 实时同步 | 用户等待响应,通常 1 到 10 秒 | 高用户体验,直接价值 | 高每调用成本,严格延迟约束 |
| 实时异步 | 用户提交,响应到达 (推送,电子邮件,通知) 在分钟内 | 比同步更宽松的延迟,更便宜的模型 | UX 复杂,需要异步设计 |
| 批处理实时间隔 | 调用在每隔 N 秒/分钟运行,处理累积的请求 | 比同步便宜,合理实时 | 仍然在每个间隔启动开销 |
| 批处理 | 在累积的数据上运行 (隔夜,每周),作为一个大型作业 | 最便宜每项,使用批处理 API 价格 (50% 折扣) | 不实时,小时或天延迟 |
| 流式 | 在数据可用时立即处理,无明确批处理边界 | 实时与异步处理 | 复杂基础设施 |

主要提供商现在为批处理工作负载提供 50% 折扣 (Anthropic 批处理 API,OpenAI 批处理 API,Google Vertex AI 批处理预测)。如果延迟可以容忍小时,这是显著的节省。

**PM 决策点**

- 这个工作流真的需要实时,还是异步就足够?
- 我们是否在仅时间敏感时支付实时溢价?
- 我们是否可以批处理像生产规模分类这样的工作负载?

**注意事项**

- "实时"经常意味着"在合理的时间内",而不是"亚秒"。澄清要求。
- 异步模式给比同步好得多的 UX (通知到达,用户不会盯着旋转器)
- 批处理 API 通常具有 24 小时 SLAs,不适合每小时工作流

**要点总结: 当真正实时时使用实时。当延迟可以放宽时使用异步或批处理。让定价反映用例。**

**Qantas 案例**

考虑跨 Qantas AI 用例的批处理与实时分发。

客户服务聊天助手是真正的实时。客户等待响应。模式必须是同步的,延迟必须在秒,不是分钟。无法批处理这些。

但客户服务工单分类 (对入站电子邮件分类,然后路由到适当的团队) 是一个不同的故事。电子邮件不需要在亚秒内分类。当客户发送电子邮件时,他们期望响应时间在小时,不是秒。分类可以以 10 分钟的间隔运行,作为一个批处理作业,处理过去 10 分钟内到达的所有电子邮件。在批处理 API 价格,这削减成本 50%。

机组运营分析 (在每个航班后分析机组报告以识别趋势) 是显然批处理工作流。每次航班结束时它生成报告。这些报告不需要立即分析。每晚批处理在过去 24 小时内的所有报告上运行的分析作业是高效的。在批处理 API,成本是实时的一半,工程更简单,数据团队对此熟悉。

营销内容生成 (起草路线特定促销活动) 是异步实时的良好候选者。营销人员请求活动,在几分钟内通过电子邮件返回草稿。这给好的 UX 而无需严格延迟约束。它可以使用更便宜的模型,因为没有用户等待。

频繁飞行客户细分 (聚类客户为旅行模式) 是显然批处理。每周一次或每月一次的作业,聚类整个数据库。这甚至不需要实时 API; 它可以使用批处理 embedding API 和批处理 LLM API。

错误是当所有这些都被实施为实时聊天机器人。运营报告分析作为聊天机器人?客户搜索每月一次,价值不证明实时基础设施。营销活动起草作为聊天机器人?营销人员发起请求,然后离开等待响应; 他们不与机器人交谈。常见的反模式是 "我们将构建一个 AI 助手来做 X",当 X 实际上是一个具有适当 UX 的批处理工作流。

对 AI 交付来说,启示是范围确定应该明确区分真正实时,异步实时和批处理工作流。每个有不同的架构,成本画像,工程努力。错误地将批处理工作流定为实时是常见且昂贵的错误。能够说"这个用例不需要聊天机器人,它需要每天运行的批处理作业,这里是为什么"的交付从业者发布更简单更便宜的解决方案,提供相同的真实价值。
