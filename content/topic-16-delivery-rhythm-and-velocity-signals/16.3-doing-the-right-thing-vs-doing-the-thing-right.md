**Definition**

Two failure modes are common in AI delivery, and they require different responses. The first is "doing the wrong thing well", where the team executes flawlessly on a project that should not have been done, or on a use case that does not serve the actual user need. The second is "doing the right thing poorly", where the team is on the correct project but is executing badly. The two failures look similar in status reports (the project is in trouble) but require completely different interventions. This item is about telling them apart and knowing which is more dangerous.

**Why it matters in delivery**

In conventional consulting wisdom, doing the wrong thing well is the more dangerous failure: it produces a polished solution to an irrelevant problem, which is expensive and hard to recover from. In AI delivery this remains true, but the diagnostic is harder because the symptoms of both failures overlap. A project that is failing on execution looks similar to a project that is succeeding on execution but solving the wrong problem.

The deeper reason this distinction matters: the response to each failure is opposite. If the team is doing the wrong thing well, the response is to pause, re-examine the use case, and potentially re-direct. If the team is doing the right thing poorly, the response is to keep going, improve execution, and not change the project. Doing the wrong response to either failure makes it worse. Pausing a project that just needs execution improvement creates churn. Pushing harder on a project that is on the wrong thing produces a polished mistake.

**How it works**

The diagnostic distinguishes between the two failures through five questions.

| Question | Doing the wrong thing well | Doing the right thing poorly |
|---|---|---|
| Are users excited when they see early outputs? | No, even though outputs are polished | Yes, but outputs need refinement |
| Is the eval set itself reasonable? | No, the eval set tests for wrong things | Yes, the eval set is right but pass rate is low |
| Does the operating team find the system useful in practice? | No, even when it works as specified | Yes when it works, frustrated when it does not |
| Would killing the project produce relief or panic? | Relief, possibly hidden | Panic, the work matters |
| Is the team's energy about "let us improve" or "let us do something different"? | Different | Improve |

If two or more answers point to "doing the wrong thing well", the project needs a re-examination. If two or more point to "doing the right thing poorly", the project needs execution improvement, not re-direction.

**Symptoms that look like one but are the other**

The diagnostic is hard because both failures can present similarly. A few patterns where the surface symptom misleads.

*Eval scores are low.* Could be either. If the eval set is testing the right things and pass rate is low, the project is executing poorly on the right thing. If the eval set is testing things the operating team does not care about, the project is doing the wrong thing well (the team is improving its score on irrelevant tests).

*Users are unenthusiastic.* Could be either. If users like the idea but the early outputs are rough, the project is on the right thing but executing poorly. If users have stopped engaging, are not coming to working sessions, or describe the project flatly when asked, the project may be on the wrong thing.

*Project feels slow.* Could be either. If the team feels slow but engaged, focused on real problems, this is the eval valley of a right-thing project. If the team feels slow and increasingly disengaged, doing work that does not feel meaningful, this may be a wrong-thing project.

The PM's job is to look past the surface symptom and ask the diagnostic questions deliberately.

**Which is more dangerous**

The standard answer is "doing the wrong thing well", and that remains true in AI delivery. The reasons:

A wrong-thing project that is well executed will ship. It will then be used briefly, found unhelpful, and abandoned. The team is left with a polished artifact that does not produce business value. The cost is the entire project budget. The cost of recognising the wrong-thing in week six and pivoting is much smaller than completing it.

A right-thing project that is poorly executed will produce visible struggles. The team and client will see them. The interventions to improve execution are well understood: more engineering effort, better evals, more workshops with users, more time. The cost of poor execution is recoverable if recognised. The cost of the wrong thing is harder to recover.

The second reason: a wrong-thing project damages relationships. The operating team that participated in a wrong-thing project, and saw it launched, often becomes skeptical of future AI projects. The opportunity cost of the wrong thing is not just this project's budget, but the harder time the next project will have getting cooperation.

**Communicating the diagnosis**

When the diagnosis is "doing the right thing poorly", the conversation with the client is easier. The team owns the execution gap, names specific improvements, and asks for time or resources. Clients accept this when it is presented honestly.

When the diagnosis is "doing the wrong thing well", the conversation is harder. The team is essentially saying "we have built this well, and we do not think it solves the right problem". The framing matters. It is not "we wasted your money", it is "what we have learned by building has shown us the use case needs to be reshaped". The reshaping can often save most of the work that has been done.

The conversation is best had in private with the operating sponsor first, before any wider stakeholder. The sponsor needs to be part of the diagnosis, not surprised by it. From there, the conversation broadens to the steering committee with a recommendation, not a problem.

**PM decision points**

- For each project I am running, can I name with confidence whether the team is doing the right thing or the wrong thing?
- Am I asking the diagnostic questions deliberately, or only when something seems wrong?
- When I diagnose wrong-thing, am I willing to surface it to the operating sponsor honestly?

**Watch outs**

- The team will resist a wrong-thing diagnosis, because it implies the work so far has limited value. The PM has to be willing to make the diagnosis even when the team disagrees.
- The operating sponsor sometimes wants to keep going on a wrong-thing project to avoid the political cost of changing direction. The PM's job is to make the costs of continuing visible.
- Sometimes the diagnosis is partial: a project is doing the right thing on some dimensions and the wrong thing on others. In that case, the response is to keep the right parts and re-direct the wrong parts.

**Takeaway: doing the wrong thing well and doing the right thing poorly look similar in symptoms but require opposite responses. Five diagnostic questions distinguish them. Wrong-thing failures are more dangerous because they produce polished mistakes and damage future AI projects. The harder conversation is the more valuable one to have.**

**Qantas story**

Imagine running a Qantas AI project to build a customer service chat tool for the airport ground operations team. The tool is designed to help duty managers respond to customer enquiries during operational disruptions. By week eight, the project is in trouble. The eval scores are at 78 percent and not climbing. The team is working hard. The operating sponsor is concerned. The instinct in week eight is to push for better execution: more eval cycles, more prompt iteration, more model experimentation.

The PM, instead, runs the diagnostic.

Are users excited when they see early outputs? Mixed. The duty managers who have seen demos appreciate the technical capability but have not asked to use it themselves. They have not pulled the team into their workflows. When asked directly, several say "this is impressive but I do not think it fits how I actually work during a disruption".

Is the eval set itself reasonable? The eval set was constructed by the team with the operating sponsor's input. The duty managers were not closely involved. When the team reviews the eval set with three actual duty managers, the duty managers describe many of the eval inputs as "unrealistic" or "not the kind of question I would type into a tool during a disruption".

Does the operating team find the system useful in practice? When the team places the early version in front of duty managers during a simulated disruption exercise, the duty managers use it once, find it slower than their existing process, and stop using it for the rest of the exercise.

Would killing the project produce relief or panic? In a private conversation with the operating sponsor, the PM asks the question directly. The sponsor pauses, then admits that killing the project would produce relief, mixed with concern about how to explain it.

Is the team's energy about "let us improve" or "let us do something different"? The team is increasingly raising the question of whether the use case is right. One team member, in a recent retrospective, said directly that "we are building something well but I do not think they will use it".

Four out of five answers point to "doing the wrong thing well". The project is executing competently but on a use case that does not match how duty managers actually work during disruptions. Pushing harder on execution would produce a polished tool that would not be used.

The PM raises this with the operating sponsor in a private one-on-one. The framing is not "we have wasted your money", it is "what we have learned by building has shown us the use case needs to be reshaped". The sponsor, given the diagnostic, agrees.

The team and sponsor go back to the duty managers with a different question: "during a disruption, what is the hardest 30 seconds of your work, where AI could genuinely help?" The conversations reveal a different use case: the duty managers do not want a chat tool, they want a system that automatically generates the first draft of the customer notification template based on the disruption parameters, which they can then edit. This is faster than typing and faster than searching for the template they used last time.

The project is re-scoped in week nine. Three weeks of work are repurposed: the prompt engineering, the eval infrastructure, and the duty manager relationships all transfer. The new use case is built in seven weeks instead of the eight weeks remaining, because the team is now solving a problem the duty managers actually have. The launched tool is enthusiastically adopted.

The interesting counterfactual is what would have happened if the diagnostic had not been run. The team would have spent the remaining six weeks improving the chat tool, the launch would have been on schedule, the duty managers would have used it briefly and abandoned it, and the project would have been classified as a failure six months later. The work would have been good, but on the wrong thing.

The lesson for AI delivery is that "doing the right thing" is not a given. It needs to be tested explicitly, especially when other signals suggest something is off. The diagnostic is uncomfortable because it sometimes recommends pivoting. The cost of pivoting in week eight is much less than the cost of completing the wrong thing in week 14. The PM who is willing to ask the harder question saves more value than the PM who optimises execution on a project that should not have been continued.

**定义**

AI 交付里两种失败模式常见, 需要不同回应。第一是 "做错的事但做得好", 团队在一个不该做的项目上、或在一个不服务实际用户需求的 use case 上, 执行得完美。第二是 "做对的事但做得差", 团队在对的项目上, 但执行得差。两种失败在 status 报告里看起来相似 (项目在麻烦中), 但需要完全不同的干预。这一节是关于区分它们, 以及知道哪个更危险。

**为何在交付中重要**

传统咨询智慧里, 做错的事但做得好是更危险的失败: 它产出对无关问题的精致解决方案, 贵且难恢复。AI 交付里这仍然真, 但诊断更难, 因为**两种失败的症状重叠**。一个在执行上失败的项目, 看起来跟一个在执行上成功但解决错问题的项目相似。

这种区分重要的更深原因: 对每种失败的回应是相反的。如果团队在做错的事但做得好, 回应是暂停、重审 use case、可能重新定向。如果团队在做对的事但做得差, 回应是继续、改善执行、不改项目。对任一失败做错的回应让它更糟。暂停一个只需要改善执行的项目制造搅动。对一个做错事情的项目更加用力, 产出精致的错误。

**运作原理**

诊断通过五个问题区分两种失败。

| 问题 | 做错的事但做得好 | 做对的事但做得差 |
|---|---|---|
| 用户看到早期输出时兴奋吗? | 不, 即使输出精致 | 是, 但输出需要精炼 |
| eval set 本身合理吗? | 不, eval set 测错的东西 | 是, eval set 对但通过率低 |
| 运营团队在实际中觉得系统有用吗? | 不, 即使它按规格工作 | 工作时是, 不工作时挫败 |
| 杀掉项目会产出宽慰还是恐慌? | 宽慰, 可能隐藏 | 恐慌, 工作有意义 |
| 团队的能量是关于 "我们改善" 还是 "我们换" 的? | 换 | 改善 |

如果两个或更多答案指向 "做错的事但做得好", 项目需要重审。如果两个或更多指向 "做对的事但做得差", 项目需要改善执行, 不是重新定向。

**看起来像一种但实际是另一种的症状**

诊断难, 因为两种失败能呈现得相似。几个表面症状误导的 pattern。

*Eval 分数低*。**可能是任一种**。**如果 eval set 测对的东西、通过率低, 项目在对的事上执行得差**。**如果 eval set 测运营团队不在意的东西, 项目在做错的事但做得好 (团队在改善无关测试上的分数)**。

*用户不热情*。**可能是任一种**。**如果用户喜欢主意但早期输出粗糙, 项目在对的事上但执行得差**。**如果用户停止 engage、不来工作会议、被问时平淡描述项目, 项目可能在错的事上**。

*项目感觉慢*。**可能是任一种**。**如果团队感觉慢但 engaged, 聚焦在真问题上, 这是对的事项目的 eval 低谷**。**如果团队感觉慢且越来越 disengaged, 做的工作感觉没意义, 这可能是错的事项目**。

PM 的工作是看穿表面症状, 刻意问诊断问题。

**哪个更危险**

标准答案是 "做错的事但做得好", 这在 AI 交付里仍然真。**原因**:

一个做错的事但执行得好的项目会上线。然后被短暂使用、发现没用、被抛弃。团队留下一个不产出业务价值的精致产物。成本是整个项目预算。第 6 周识别错的事并 pivot 的成本, 比完成它小得多。

一个做对的事但执行得差的项目会产出可见的挣扎。团队和客户会看到。改善执行的干预良好理解: 更多工程精力、更好的 evals、跟用户更多 workshop、更多时间。执行差的成本如果被识别可恢复。做错事的成本更难恢复。

**第二个原因**: 做错的事项目损害关系。参与了做错事项目的运营团队, 看到它上线, 经常对未来 AI 项目变得怀疑。做错的事的机会成本不只是这个项目的预算, 是下个项目获得合作时会遇到的更难时光。

**沟通诊断**

当诊断是 "做对的事但做得差", 跟客户的对话更容易。团队拥有执行缺口, 命名具体改善, 请求时间或资源。客户在它被诚实呈现时接受。

当诊断是 "做错的事但做得好", 对话更难。团队本质上在说 "我们建得好, 但我们不认为它解决对的问题"。**措辞重要**。不是 "我们浪费了你的钱", 是 "我们通过建造学到的东西显示 use case 需要重塑"。重塑经常能保留大部分已做的工作。

对话最好先私下跟运营 sponsor 进行, 在任何更广 stakeholder 之前。Sponsor 需要是诊断的一部分, 不是被它惊吓。从那, 对话扩大到 steering committee, 带建议, 不是问题。

**PM 决策点**

- 对我正在跑的每个项目, 我**能不能有信心地命名团队在做对的事还是错的事**?
- 我**有没有刻意问诊断问题**, 还是**只在事情看起来不对时**?
- 当我诊断 "错的事", 我**愿意诚实地把它浮给运营 sponsor 吗**?

**注意事项**

- **团队会抵抗错的事诊断**, 因为**它暗示到目前为止的工作价值有限**。**PM 必须愿意做诊断, 即使团队不同意**。
- **运营 sponsor 有时想继续做错的事项目, 以避免改变方向的政治成本**。**PM 的工作是让继续的成本可见**。
- **有时诊断是局部的**: **一个项目在某些维度上做对的事、在另一些维度上做错的事**。**那种情况, 回应是保留对的部分、重新定向错的部分**。

**要点总结: 做错的事但做得好, 和做对的事但做得差, 症状看起来相似, 但需要相反回应。五个诊断问题区分它们。错的事失败更危险, 因为它们产出精致错误、损害未来 AI 项目。更难的对话是更值得有的。**

**Qantas 案例**

设想你跑一个 Qantas AI 项目, 给机场地面运营团队建一个客服聊天工具。工具被设计来帮值班经理在运营中断期间回应客户咨询。到第 8 周, 项目在麻烦中。Eval 分数在 78%, 不在爬。团队在努力工作。运营 sponsor 担心。第 8 周的本能是推动更好的执行: 更多 eval 循环、更多 prompt 迭代、更多模型实验。

PM 反而跑诊断。

用户看到早期输出时兴奋吗? **混合**。看过 demo 的值班经理欣赏技术能力, 但没要求自己用。他们没把团队拉进他们的工作流。被直接问时, 几位说 "这印象深刻, 但我不觉得它适合我在中断期间实际怎么工作"。

eval set 本身合理吗? eval set 由团队带着运营 sponsor 输入构建。值班经理没紧密参与。当团队跟三位实际值班经理 review eval set, 值班经理描述很多 eval 输入为 "不现实" 或 "不是我在中断期间会输入工具的那种问题"。

运营团队在实际中觉得系统有用吗? 当团队在模拟中断演习中把早期版本放在值班经理面前, 值班经理用了一次, 发现比他们现有流程慢, 演习剩下时间停止用。

杀掉项目会产出宽慰还是恐慌? 跟运营 sponsor 的私下对话里, PM 直接问问题。Sponsor 停顿, 然后承认杀掉项目会产出宽慰, 混合着关于怎么解释的关切。

团队的能量是关于 "我们改善" 还是 "我们换" 的? 团队越来越提出 use case 是否对的问题。一位团队成员在最近的回顾里直接说 "我们在建一个好东西, 但我不觉得他们会用"。

五个答案里四个指向 "做错的事但做得好"。项目在执行得能干, 但在不匹配值班经理在中断期间实际怎么工作的 use case 上。在执行上更用力会产出一个精致但不会被用的工具。

PM 在私下一对一里跟运营 sponsor 提出这个。措辞不是 "我们浪费了你的钱", 是 "我们通过建造学到的东西显示 use case 需要重塑"。Sponsor, 给定诊断, 同意。

团队和 sponsor 带不同问题回到值班经理面前: "中断期间, 你工作中最难的 30 秒是什么, AI 能真正帮上忙的?" 对话揭示一个不同的 use case: 值班经理不想要聊天工具, 他们想要一个根据中断参数自动生成客户通知模板的第一稿的系统, 然后他们能编辑。这比打字快, 也比搜索上次用的模板快。

项目第 9 周被重新 scope。三周工作被重新利用: prompt 工程、eval 基础设施、值班经理关系都转移。新 use case 在七周内建成, 而不是剩下的八周, 因为**团队现在在解决值班经理实际有的问题**。上线的工具被热情采纳。

有意思的反事实是没跑诊断会发生什么。团队会花剩下的六周改善聊天工具, 上线按时, 值班经理短暂使用并抛弃, 项目六个月后被分类为失败。工作会是好的, 但在错的事上。

AI 交付的启示: "做对的事" 不是给定的。它需要被明确测试, 尤其当其他信号暗示什么不对时。诊断不舒服, 因为它有时建议 pivot。第 8 周 pivot 的成本比第 14 周完成错的事的成本小得多。愿意问更难问题的 PM, 比在不该继续的项目上优化执行的 PM, 节省更多价值。
