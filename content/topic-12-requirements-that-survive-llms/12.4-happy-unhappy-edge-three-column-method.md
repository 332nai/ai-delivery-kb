**Definition**

The three column method is a workshop technique for collecting AI requirements from operating teams. It forces every requirement to be specified in three modes: the happy path (what the system does when everything is normal), the unhappy path (what the system does when the input is problematic but the system is still expected to handle it), and the edge cases (rare or unusual inputs that should be handled specially, deferred, or refused). The method produces requirements that are far harder to misinterpret than prose, and that map cleanly into the eval set described in 12.2.

**Why it matters in delivery**

Most requirements documents describe only the happy path. The unhappy path is left to the engineering team to guess, and the edge cases are discovered in production when they break the system. In AI delivery this gap is especially expensive, because LLM systems behave unpredictably on inputs they were not specified for. The three column method closes the gap by making the operating team think about all three modes at workshop time, while the cost of disagreement is low and the right people are in the room.

The other benefit: this is a method that operating teams find natural. They live in the unhappy path. The customer service supervisor knows exactly what kinds of customer messages are weird, what the agents struggle with, and what the genuinely impossible cases look like. The three column structure invites that knowledge into the requirements work, where it has historically been excluded.

**How it works**

For each use case the team is scoping, run a workshop with three to five operating team members. Draw a three column table on the whiteboard, headed "Happy", "Unhappy", "Edge case". For each capability the system should have, fill in all three columns.

| Capability | Happy path | Unhappy path | Edge case |
|---|---|---|---|
| Summarise customer feedback | Clear, well written feedback in English, single topic | Long, rambling, multi-topic, with emotional language and typos | Feedback that is actually a legal threat, contains confidential information, or is in a language not supported |
| Answer policy question | Single, clear question with a documented answer | Multi-part question, some parts not in policy docs | Question is asking for advice rather than policy lookup, or is testing the system |
| Draft response email | Standard request, clear precedent in past responses | Sensitive topic, ambiguous request, unclear customer intent | VIP customer, regulatory complaint, or possible litigation matter |

The rule is that every cell must be filled before the workshop ends. The team is not allowed to skip the unhappy path or the edge case columns because they are hard to think about. Those are exactly the columns that pay off in production.

**What to do with the filled in table**

Each cell becomes one or more rows in the eval set. Happy path cells produce the bulk of the eval rows. Unhappy path cells produce the rows that test robustness. Edge case cells produce the rows that test refusal, deferral, or special handling.

The table also becomes the source for the system prompt. The happy path cells inform what the system should do by default. The unhappy path cells inform the system's robustness instructions ("if the input is multi-topic, summarise each topic separately"). The edge case cells inform the refusal and routing instructions ("if the input contains a legal threat, do not respond, route to legal queue with the original message preserved").

A useful follow up after the workshop is to annotate each cell with how the team currently handles that case without AI. This gives the eventual AI system a baseline to beat, and reveals workflows that may need to change.

**Why three columns and not more**

Some teams want to add columns for "very rare", "catastrophic failure", "regulatory edge", and so on. Resist. The three column structure is deliberately coarse. The goal is to elicit thinking, not to produce a perfect taxonomy. Once you go to five or six columns, the operating team stops engaging and starts trying to figure out where each example belongs. Three columns are enough to surface most of the requirement work without becoming a meta-discussion about classification.

If a particular case is hard to categorise (is this unhappy path, or is it edge case?), the right move is usually to write it down twice and decide later. The categorisation does not matter as much as the existence of the row.

**PM decision points**

- For each AI capability in scope, has a three column table been produced with operating team members in the room?
- Are the unhappy path and edge case columns filled to the same depth as the happy path column, or is the team only specifying the easy mode?
- Has each cell been converted into one or more eval rows, so the workshop output flows into the specification?

**Watch outs**

- The operating team may resist the unhappy and edge columns because they feel like exception handling, not requirements. The framing that helps is "if we do not specify these, the AI will guess, and the guess will be wrong in a way that hurts you".
- Avoid running this workshop with only the executive sponsor in the room. The sponsor lives in the happy path. The operating team lives in the other two. Without them, the table is incomplete.
- Three columns is a starting structure, not a final artifact. As the project progresses, some cells will spawn sub-cases that need their own rows. That is fine. The structure adapts.

**Takeaway: every AI capability should be specified in three modes, not one. The happy path tells you what the system does. The unhappy path tells you how it copes. The edge case tells you when it should not act. Without all three, the requirement is half written.**

**Qantas story**

Imagine being asked to specify an AI tool for Qantas customer service that handles seat selection change requests: a customer messages in asking to change their seat, the system understands the request, checks availability, makes the change if possible, and confirms it. The PRD describes this in two paragraphs. The team and the customer service operating team agree to run a three column workshop instead.

The workshop assembles a customer service supervisor, two senior agents, a frequent flyer specialist, and the delivery team's PM. The first capability tackled is "understand the customer's seat change request".

The happy path column fills quickly. "I want to change seat 14C to a window seat" is happy path. "Can I switch to 22A please" is happy path. The team writes five or six examples.

The unhappy path column takes longer and is more interesting. "I want to move because the person next to me smells" is unhappy path: the request is legitimate but emotionally loaded. "Can I get an exit row, I am tall" is unhappy path: the request might involve an upgrade or fee. "I want my whole family of 4 sat together but we are spread across the cabin" is unhappy path: the request is multi-part and depends on availability the system needs to check. The team writes ten examples that probe different unhappy modes.

The edge case column is the most generative. "Can you upgrade me to business class" (this is not a seat change). "My booking is for tomorrow and I want to change my seat from last week's flight" (the booking does not exist). "Can you change my seat and also rebook my connection" (out of scope, compound request). "I think the agent who served me earlier was racist" (this is not a seat change request at all). "I am writing on behalf of my elderly mother who has dementia" (consent and identity questions). The team writes 12 edge cases.

The total table for this one capability has 28 rows. Each row will become an eval. The system prompt will be informed by all three columns. The handover logic to a human agent will be informed mostly by the edge case column.

The most useful moment in the workshop comes from one of the senior agents, who says: "the racist complaint one is the kind of thing we get once a week, and the AI must not try to handle it, it must hand off cleanly with the original message preserved and the customer's emotional state acknowledged." That single sentence becomes one of the most important rows in the eval set, because it specifies a behaviour the system absolutely must do correctly. Without the workshop, this row would never have existed, and the production system would eventually have produced an inappropriate response to a legitimate complaint, with significant brand consequences.

The lesson for AI delivery is that the unhappy path and the edge cases are not exception handling. They are the requirement. Operating teams know them implicitly. The three column workshop is a low cost technique for extracting that knowledge before the engineering work begins, and converting it into eval rows and system prompt instructions that produce robust systems. The 90 minutes spent here saves multiple weeks of post-launch firefighting.

**定义**

三栏法是一个**收集 AI 需求的 workshop 技术**, 跟运营团队一起用。它**强制每一条需求都按三种模式被规定**: happy path (一切正常时系统做什么)、unhappy path (输入有问题但系统仍然被期待处理时做什么)、edge case (稀有或异常输入, 应该被特殊处理、推迟、或拒绝)。这个方法产出的需求**比 prose 难得多被误解**, 而且**干净地映射到 12.2 描述的 eval set**。

**为何在交付中重要**

大多数需求文档只描述 happy path。unhappy path 被留给工程团队猜, edge case 在生产里被发现, 因为它们把系统弄崩了。AI 交付里这个缺口**尤其昂贵**, 因为 LLM 系统在没被规定的输入上行为不可预测。三栏法**通过让运营团队在 workshop 时就想清楚三种模式**来填补这个缺口, 趁着分歧成本还低、合适的人还在房间里。

**另一个好处**: 这个方法**运营团队觉得自然**。他们活在 unhappy path 里。客服主管**精确知道**哪些客户消息怪、坐席卡在哪里、什么样的案子是真的不可能。三栏结构**邀请这种知识进入需求工作**, 而这种知识**历史上是被排除在外的**。

**运作原理**

对于团队正在 scope 的每一个 use case, 跟 3 到 5 个运营团队成员开 workshop。在白板上画一张三栏表, 表头 "Happy"、"Unhappy"、"Edge case"。对系统应该具备的每一个能力, 三栏都填。

| 能力 | Happy path | Unhappy path | Edge case |
|---|---|---|---|
| 总结客户反馈 | 清晰、写得好的英文反馈, 单一话题 | 长、絮叨、多话题, 带情绪化语言和错别字 | 反馈实际上是**法律威胁**, 含**机密信息**, 或**不支持的语言** |
| 回答政策问题 | 单一、清晰的问题, 有文档化的答案 | 多部分问题, 有些部分不在政策文档里 | 问题在**寻求建议而非政策查询**, 或在**测试系统** |
| 起草回复邮件 | 标准请求, 过往回复有明确先例 | 敏感话题, 含糊请求, 客户意图不清 | VIP 客户、监管投诉、**可能涉诉**的事项 |

规则是 workshop 结束前每一格都必须填。团队不被允许跳过 unhappy path 或 edge case 那两栏, 仅仅因为它们难想。那恰好是在生产里回报最高的两栏。

**填完表怎么用**

每一格变成 eval set 的一行或多行。Happy path 格产出 eval 的主体行。Unhappy path 格产出测试鲁棒性的行。Edge case 格产出测试拒绝、推迟、或特殊处理的行。

这张表**也变成 system prompt 的来源**。Happy path 格**告诉系统默认做什么**。Unhappy path 格**告诉系统鲁棒性指令** ("如果输入是多话题, 每个话题分别总结")。Edge case 格告诉系统拒绝和路由指令 ("如果输入含法律威胁, 不要回应, 路由到 legal queue, 原始消息保留")。

Workshop 之后一个有用的延伸: 给每一格标注 "团队今天没有 AI 时怎么处理这种情况"。这给最终的 AI 系统**一个要打败的基线**, 也**揭示可能需要变的工作流**。

**为什么是三栏而不是更多**

有些团队**想加列**, 加 "非常稀有"、"灾难性失败"、"监管边缘" 等等。**抵抗**。三栏结构**故意是粗的**。目标是引出思考, 不是产出一个完美的分类法。一旦你做到五六栏, 运营团队就停止 engage、开始尝试搞清楚每个例子归哪一栏。三栏足以浮出大部分需求工作, 同时不会变成关于分类的 meta 讨论。

如果某个案子难分类 (这是 unhappy path 还是 edge case?), 对的动作通常是写两次, 以后再决定归类。分类没那么重要, 重要的是这一行存在。

**PM 决策点**

- 对每一个在范围内的 AI 能力, 我有没有**带着运营团队成员**产出过三栏表?
- Unhappy path 和 edge case 那两栏**填到了跟 happy path 一样的深度**, 还是团队**只规定了简单模式**?
- 每一格**有没有被转成一行或多行 eval**, 这样 workshop 产出**流进了规格**?

**注意事项**

- 运营团队**可能抗拒 unhappy 和 edge 那两栏**, 因为它们**感觉像异常处理, 不像需求**。**有用的措辞**是: **"我们不规定这些, AI 就会自己猜, 而猜的方向会以伤害你们的方式出错"**。
- 避免**只跟 executive sponsor 一起开这个 workshop**。**Sponsor 活在 happy path**。**运营团队活在另外两栏**。**没有他们, 这张表是不完整的**。
- 三栏是**起手结构, 不是最终产物**。项目推进时, **有些格会派生出需要自己的行的子情况**。**那很正常**。**结构会适应**。

**要点总结: 每一个 AI 能力都该用三种模式规定, 不是一种。Happy path 告诉你系统做什么。Unhappy path 告诉你它怎么应对。Edge case 告诉你它何时不该行动。没有这三栏, 需求只写了一半。**

**Qantas 案例**

设想你被要求规定一个 Qantas 客服的 AI 工具, 处理座位变更请求: 客户发消息要求换座位, 系统理解请求、查可用性、可能的话改座位、并确认。PRD 用两段话描述这件事。团队和客服运营团队同意改成跑一个三栏 workshop。

Workshop 凑齐**一位客服主管、两位资深坐席、一位 frequent flyer 专员、交付团队的 PM**。第一个攻击的能力是 "理解客户的座位变更请求"。

Happy path 那一栏很快填满。"我想把 14C 换成靠窗座位" 是 happy path。"我能换到 22A 吗" 是 happy path。团队写了五六个例子。

Unhappy path 那一栏花时间更久, 也更有意思。"我想换座位, 因为旁边的人有味" 是 unhappy path: 请求合法但情绪化。"我能要紧急出口排吗, 我个子高" 是 unhappy path: 请求可能涉及升级或费用。"我想要我们一家 4 口坐一起, 但我们散在客舱各处" 是 unhappy path: 请求是多部分的, 取决于系统需要查的可用性。团队写了 10 个例子, 探测不同的 unhappy 模式。

Edge case 那一栏产出最多。"你能把我升级到商务舱吗" (这不是座位变更)。"我的订位是明天的, 我想改我上周航班的座位" (那个订位不存在)。"你能改我的座位, 顺便改我的接驳" (超出范围, 复合请求)。"我觉得刚才服务我的坐席有种族主义倾向" (这根本不是座位变更请求)。"我代我有痴呆的高龄母亲写的" (同意和身份的问题)。团队写了 12 个 edge case。

这一个能力的总表是 28 行。每一行都会变成一条 eval。System prompt 会被三栏共同告知。移交给人工坐席的逻辑, 主要被 edge case 那一栏告知。

**Workshop 里最有用的瞬间**来自一位资深坐席, 他说: "那个种族歧视投诉的例子, 我们每周都会遇到一次。AI 必须不要试图处理它, 它必须干净地把案子交出去, 原始消息保留, 客户的情绪状态被承认"。**那一句话**变成 eval set 里最重要的几行之一, 因为**它规定了一个系统绝对必须做对的行为**。没有这场 workshop, 这一行永远不会存在, 生产系统最终会对一个合法投诉产出不合适的回应, 带来重大的品牌后果。

AI 交付的启示: unhappy path 和 edge case 不是异常处理。**它们就是需求**。运营团队隐性地知道它们。三栏 workshop 是一个低成本技术, 在工程工作开始之前把那种知识提取出来, 转换成产出鲁棒系统的 eval 行和 system prompt 指令。在这里花的 90 分钟, 省下上线后多周的救火。
