**Definition**

A client requirement for AI almost always arrives in the form "the AI should do X", where X is a verb phrase: "summarise feedback", "answer policy questions", "extract invoice data", "generate marketing copy". The job of the delivery team in the first two weeks is to translate that verb phrase into a concrete table of inputs and expected outputs. Until that translation is done, the requirement cannot be built, tested, or argued about.

**Why it matters in delivery**

Traditional requirements engineering assumes deterministic systems. "When the user clicks submit, the form is saved" is unambiguous: it either happens or it does not. LLM systems are probabilistic. "The AI should summarise feedback" has thousands of valid interpretations. Without a concrete input-output table, the team and the client will spend the project arguing about whether the system meets the requirement, because the requirement was never specific enough to either pass or fail.

The deeper point: in AI delivery, the input-output table *is* the requirement. The PRD paragraph is a marketing document. The evals (covered in 12.2) are the contract. This item is about producing the raw material that becomes evals.

**How it works**

A working translation has three layers:

*Layer 1: The verb.* What is the AI actually doing? Pick one of a small number of verbs: summarise, classify, extract, generate, answer, route, draft, translate, rank. Compound verbs ("summarise and recommend") usually hide two separate requirements that should be modelled separately.

*Layer 2: The input shape.* What goes in? Be specific about format, length, language, source, and quality. "Customer feedback" is not an input shape. "Free text customer feedback, 50 to 800 words, English or Mandarin, from the post-flight survey" is an input shape.

*Layer 3: The output shape.* What comes out? Be specific about format, length, structure, and constraints. "A summary" is not an output shape. "A 3 sentence summary in plain text, no markdown, neutral tone, no quotes from the input, in the same language as the input" is an output shape.

Once these three layers exist, the next step is to produce a table of 20 to 40 worked examples. Each row is one input plus the expected output for that input. Some rows are typical, some are edge cases, some are intentional failure modes (input that the AI should refuse to process, or handle specially).

| Input example | Expected output | Notes |
|---|---|---|
| Typical positive feedback | Concise neutral summary | Baseline case |
| Typical negative feedback | Concise neutral summary, no emotional language | Most common edge |
| Mixed language input | Summary in the dominant language | Language detection ambiguity |
| Single sentence input | Repeat the sentence verbatim, do not synthesise | Degenerate case |
| Input containing PII | Refuse, return a defined error message | Compliance case |
| Empty or whitespace | Return defined empty response | Robustness case |

The table is not exhaustive. It does not need to be. It needs to cover the typical case plus the cases the team and the client have agreed are important.

**How to produce the table in practice**

Three sources work well together:

1. *Historical data, if the client has it.* Real examples of the inputs the system will see. Sample 50 to 100, sort by representativeness, pick the 20 to 40 that span the distribution.
2. *Workshop with the operating team.* The people who will use the output are the best source of "what does a good output look like for this input". Run a 90 minute workshop where they react to candidate inputs and write the expected outputs themselves.
3. *Synthetic generation, sparingly.* For inputs that are hard to collect (e.g. specific failure modes), synthesise them. Mark synthetic rows clearly so the team does not over-index on them.

The output of this work is not a PRD section. It is a spreadsheet or a JSON file. It will become the seed for the eval set (covered in 12.2). Storing it in a way that engineers can use is part of the deliverable.

**PM decision points**

- Have I converted every verb phrase in the requirements into a concrete input-output table, or do some requirements still live as prose?
- Are the rows in each table reviewed and signed off by an operating team member, not just the executive sponsor?
- Are edge case and failure mode rows explicitly included, or is the table only happy path?

**Watch outs**

- Compound verbs ("summarise and rank by priority and suggest next action") usually hide three requirements with three different difficulties. Decompose them.
- "Expected output" is harder to write than people expect. The first round is usually 70 percent of the way there. Plan to iterate the table at least twice.
- The table will surface disagreement between stakeholders ("I would not summarise it that way"). This is good. The disagreement is the requirement work. Resolve it now, not in week eight.

**Takeaway: an AI requirement is not a sentence, it is a table. Each row is a concrete input paired with a concrete expected output. Until the table exists, the requirement cannot be built or tested. Produce it in the first two weeks.**

**Qantas story**

Imagine being asked to build an AI tool for Qantas customer service that "summarises complex customer complaints for agent handover". The requirement arrives as a single sentence in the SOW. It looks self explanatory. It is not.

Layer 1 forces a question: is this one verb or two? "Summarise complex customer complaints" is one. But the unstated implication of "for agent handover" is that the output also recommends the next action. That is a second verb. The team and the client agree to split it: a summarisation tool and a recommendation tool, built and evaluated separately.

Layer 2 forces the input shape. Customer complaints arrive through five channels (email, web form, X mentions, app messages, voice transcripts). The text length ranges from 20 words to 4000 words. Some are in English, some in Mandarin, some in mixed languages. The team and the client agree the v1 scope is email and web form complaints in English, 50 to 2000 words. Mandarin and other channels are deferred to v2.

Layer 3 forces the output shape. After discussion with the customer service operating team, the agreed output is: a 4 to 6 sentence neutral summary in plain text, identifying the customer issue, the date of the underlying event, the resolution sought by the customer, and any explicit deadline the customer has stated. No markdown, no quotes, no emotional adjectives.

The team then produces a 30 row table. Eight rows are typical complaints sampled from last month's actual cases. Five rows are unusual but real cases (e.g. a complaint that is actually a compliment in disguise). Four rows are edge cases (very short complaints, complaints that are mostly an attached PDF, complaints in legal language). Three rows are failure modes (complaints containing threats, complaints containing PII that should be redacted, empty submissions).

The table is reviewed by two operating managers from the customer service team. They disagree with the team on five rows. The disagreements are useful: in three of the five, the operating managers are right and the team adjusts the expected output. In two, the team explains why the proposed output is technically better, and the operating managers update their mental model.

The artifact produced from this exercise is not the PRD that everyone forgets in week three. It is the seed of the eval set. When an engineer runs the first model against this table and 24 out of 30 rows match the expected output, both the team and the client know exactly where the gap is. That conversation is concrete, not philosophical.

The lesson for AI delivery is that the most important translation work in the first two weeks is converting the verb phrases in the SOW into input-output tables. The verb phrases sound like requirements. They are not. The tables are the requirements. Everything downstream, from the prompt design to the eval set to the success criteria, depends on this translation being done well and done early.

**定义**

客户对 AI 的需求几乎总是以 "AI 应该做 X" 的形式到达, 其中 X 是一个动词短语: "总结反馈"、"回答政策问题"、"提取发票数据"、"生成营销文案"。交付团队在头两周的工作就是把那个动词短语翻译成**一张具体的输入-期待输出表**。在这张表存在之前, 这个需求**不能被构建、不能被测试、也不能被有意义地争论**。

**为何在交付中重要**

传统需求工程假设的是**确定性系统**。"用户点提交, 表单被保存" 是无歧义的: 要么发生了, 要么没发生。LLM 系统是**概率性的**。"AI 应该总结反馈" 有几千种有效解读。没有这张具体的输入-输出表, 团队和客户会在整个项目里争论系统到底有没有满足需求, 因为这个需求从来没具体到能通过或失败。

更深一层: 在 AI 交付里, 输入-输出表本身就是需求。PRD 那段文字是营销文档。evals (在 12.2 讲) 才是合同。这一节讲的是产出**会变成 evals 的原材料**。

**运作原理**

一个能工作的翻译有三层:

*第一层: 动词。* AI 实际在做什么? 从一小组动词里挑一个: 总结、分类、提取、生成、回答、路由、起草、翻译、排序。**复合动词** ("总结**并**推荐") 通常藏着两个独立需求, 应该分开建模。

*第二层: 输入形态。* 输入是什么? 在格式、长度、语言、来源、质量上要具体。"客户反馈" 不是输入形态。"航后调查里的自由文本客户反馈, 50 到 800 字, 中文或英文" 才是输入形态。

*第三层: 输出形态。* 输出是什么? 在格式、长度、结构、约束上要具体。"一份总结" 不是输出形态。"3 句话的总结, 纯文本, 没有 markdown, 中性语气, 不引用输入里的原话, 跟输入同种语言" 才是输出形态。

三层都明确之后, 下一步是**产出一张 20 到 40 行的有具体示例的表**。每一行是**一个输入加上对应的期待输出**。一部分是典型的, 一部分是边缘情况, 一部分是**有意的失败模式** (AI 应该拒绝处理或特殊处理的输入)。

| 输入示例 | 期待输出 | 备注 |
|---|---|---|
| 典型正面反馈 | 简洁中性总结 | 基线 |
| 典型负面反馈 | 简洁中性总结, 不用情绪化语言 | 最常见的边缘 |
| 混合语言输入 | 用主导语言写总结 | 语言检测有歧义 |
| 只有一句话的输入 | 原样重复那一句, 不要硬合成 | 退化情况 |
| 含 PII 的输入 | 拒绝, 返回定义好的错误信息 | 合规情况 |
| 空或只有空白 | 返回定义好的空响应 | 鲁棒性情况 |

这张表**不需要穷尽**。它只需要覆盖典型情况, 加上团队和客户共同认定为重要的情况。

**实际怎么产出这张表**

三个来源配合得很好:

1. *历史数据 (如果客户有的话)*。系统将来要见到的输入的**真实样本**。抽 50 到 100 条, 按代表性排序, 挑 20 到 40 条覆盖分布。
2. *跟运营团队做 workshop*。**会用这个输出的人是 "好输出对这个输入长什么样" 的最佳来源**。开一个 90 分钟的 workshop, 让他们对着候选输入, 自己写期待输出。
3. *合成生成, 谨慎使用*。对于难收集的输入 (比如特定的失败模式), 合成它们。**清楚标记合成行**, 这样团队不会在它们身上过度优化。

这次工作的产物**不是 PRD 的一节**。是一份电子表格或 JSON 文件。它会成为 eval set 的种子 (在 12.2 讲)。把它存成工程师能用的形态, 是交付物的一部分。

**PM 决策点**

- 我有没有把需求里的每一个动词短语都转成了**具体的输入-输出表**, 还是有些需求还活在 prose 里?
- 每张表的行**有没有被运营团队的人审阅签字**, 还是只有高管 sponsor 签了?
- 边缘情况和失败模式行**明确包含**了吗, 还是这张表只有 happy path?

**注意事项**

- 复合动词 ("总结**并**按优先级排序**并**建议下一步") 通常藏着三个难度不同的需求。**拆开**。
- "期待输出" 比人想象的难写。第一轮通常只到 70%。**预计这张表至少要迭代两轮**。
- 这张表**会暴露 stakeholder 之间的分歧** ("我不会这样总结")。**这是好事**。分歧本身就是需求工作。**现在解决, 不要拖到第八周**。

**要点总结: AI 需求不是一句话, 是一张表。每一行是一个具体输入配一个具体期待输出。表不存在, 需求就不能建也不能测。在前两周把它产出来。**

**Qantas 案例**

设想你被要求给 Qantas 客服建一个 AI 工具, "为坐席交接总结复杂的客户投诉"。这个需求在 SOW 里只是一句话。它**看起来不言自明**。**它不是**。

第一层逼出一个问题: 这是一个动词还是两个? "总结复杂客户投诉" 是一个。但 "为坐席交接" 这个没说出口的暗示是**输出还要推荐下一步行动**。那是第二个动词。团队和客户同意拆开: 一个总结工具、一个推荐工具, 分别构建、分别评估。

第二层逼出输入形态。客户投诉从五个渠道来 (邮件、网页表单、X 上的提及、app 内消息、语音转写)。文本长度从 20 字到 4000 字不等。有些英文、有些中文、有些混合语言。团队和客户同意 v1 范围是英文的邮件和网页表单投诉, 50 到 2000 字。中文和其他渠道**推到 v2**。

第三层逼出输出形态。跟客服运营团队讨论之后, 商定的输出是: 4 到 6 句话的中性总结, 纯文本, 指出客户问题、问题发生的日期、客户寻求的解决方案、客户明确说出的任何 deadline。没有 markdown、没有引用、没有情绪化形容词。

团队接着产出一张 30 行的表。8 行是上个月真实案例里抽出的典型投诉。5 行是不常见但真实的案例 (例如, 一条其实是变相表扬的 "投诉")。4 行是边缘情况 (极短的投诉、主要是附件 PDF 的投诉、用法律语言写的投诉)。3 行是失败模式 (含威胁的投诉、含需要遮蔽的 PII 的投诉、空提交)。

表被客服运营团队的两位经理审阅。他们在 5 行上**跟团队意见不一致**。这些分歧很有用: 5 行里有 3 行运营经理是对的, 团队调整期待输出。剩下 2 行, 团队解释为什么提议的输出**技术上更好**, 运营经理更新了他们的心智模型。

这次练习产出的产物**不是会在第三周被所有人遗忘的 PRD**。它是 eval set 的种子。当工程师把第一版模型跑到这张表上, 30 行里有 24 行匹配期待输出, 团队和客户都**精确知道差距在哪**。那场对话是具体的, 不是哲学的。

AI 交付的启示: 前两周最重要的翻译工作, 是**把 SOW 里的动词短语转成输入-输出表**。动词短语听起来像需求。**它们不是**。**表才是需求**。从 prompt 设计到 eval set 到成功标准, 下游所有东西**都依赖这次翻译做得好且做得早**。
