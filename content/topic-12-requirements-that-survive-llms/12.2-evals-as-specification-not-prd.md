**Definition**

In a traditional software project, the PRD (Product Requirements Document) is the contract between product and engineering. It describes what should be built in prose, supplemented by mocks and acceptance criteria. In an AI project, the PRD is still useful as a narrative document, but it is not the specification. The specification is the eval set: a structured collection of test inputs paired with expected outputs, scoring rules, and pass thresholds. This is what engineering builds against, and what the client signs off on.

**Why it matters in delivery**

The most common requirements failure pattern in AI delivery is: PRD signed off in week two, model built in weeks three through six, demo in week seven, client says "this is not what we asked for". The PRD did not pin down what "what we asked for" actually meant in machine-checkable form. The eval set does.

Treating evals as the specification has three concrete consequences:

1. The team and the client argue about evals in week two, not about demos in week eight. The conversation moves from subjective to objective.
2. The engineering work has a target it can iterate against. "Pass 85% of the evals" is buildable. "Be useful" is not.
3. When the model is updated (different version, different provider, new prompt), regression is detectable. Without evals, every prompt change is a leap of faith.

**How it works**

A specification eval set has the following structure. It is the same artifact described in Topic 7, but here the framing is "this is your requirements document", not "this is your testing infrastructure".

| Component | What it contains | Who owns it |
|---|---|---|
| Inputs | 50 to 200 real or realistic input cases, sampled to represent the production distribution | Operating team (sourced from real use) |
| Expected outputs | The right answer, or a description of what makes an answer right | Operating team (with delivery team scribing) |
| Scoring rule | How to judge each input/output pair: exact match, semantic match, rubric, LLM judge, human judge | Delivery team (with client review) |
| Pass threshold | The percentage of evals that must pass for the system to be acceptable | Joint decision, documented |
| Tier labels | Tagging each eval as critical, important, or nice to have | Joint decision |

Each row is a specification statement. Together, the rows are the requirements document. A new joiner to the project should be able to read the eval set and understand what the system is supposed to do, without reading the PRD.

**Why this works better than a PRD for AI**

Three reasons:

*Prose hides ambiguity, examples expose it.* "The AI should provide helpful product information" sounds clear in a PRD. When the team and the client try to write 30 specific examples of (customer question, helpful response) pairs, they find they disagree about 8 of them. Those 8 disagreements are the real requirement work.

*Evals are machine-checkable.* The PRD has to be checked by a human reading prose against a demo. The eval set is checked by a script in 30 seconds. Iteration speeds up by an order of magnitude.

*Evals survive model and prompt changes.* When the model gets upgraded next quarter, you can re-run the eval set and immediately see whether the system still meets requirements. With a PRD only, you have to manually re-test.

**How to introduce this to the client**

Clients who have done traditional software projects expect a PRD. Going to them and saying "we are not writing one" creates anxiety. The better framing is: "we are going to write a short PRD for the narrative and the business context, and a structured eval set for the actual specification. The eval set is what we will both sign off on, and what we will both check progress against."

A useful artifact for the conversation is a one page document with two columns: "what goes in the PRD" (vision, users, business outcomes, non-functional requirements like latency or cost) and "what goes in the eval set" (the actual behaviour the system needs to exhibit). Both are produced. The eval set is the one that has teeth.

**PM decision points**

- Have I produced an eval set, or have I only produced a PRD?
- For each requirement in the PRD, can I point to the eval rows that test it? If not, the requirement is not yet a specification.
- Has the client signed off on the eval set, or only on the PRD prose?

**Watch outs**

- Some requirements genuinely cannot be expressed as evals (e.g. latency, cost, security posture). These belong in the PRD or in a separate non-functional spec, not forced into the eval set.
- An eval set without a pass threshold is a checklist, not a specification. Always pair the eval set with a target percentage and a definition of which evals are critical.
- Evals that the client cannot understand are not evals the client can sign off on. Write the inputs and expected outputs in plain language even if scoring is technical.

**Takeaway: in AI delivery, the eval set is the specification. The PRD is the narrative. The eval set is what engineering builds against, what the client signs off on, and what survives model updates.**

**Qantas story**

Imagine running an AI project at Qantas to build an internal policy assistant for the customer service team: a tool that lets agents ask "what is our policy on X" and get a correct answer drawn from internal documentation. The traditional approach would be to write a PRD describing the tool, its users, its expected behaviour, and acceptance criteria in prose, then build to that PRD.

The eval-as-spec approach starts differently. In week two, the team and the customer service operating team sit down and produce an eval set of 120 questions. The questions are real: they are pulled from a sample of last quarter's "agent-to-supervisor" escalations, where an agent asked a supervisor for policy clarification. Each question is paired with the correct answer, sourced from the policy documents and confirmed by the operating team.

The 120 questions are tiered. Forty are tagged "critical": these are questions about safety, refunds, and disruption compensation, where a wrong answer would cause direct customer harm or financial loss. Sixty are tagged "important": common questions where a wrong answer would cause customer frustration. Twenty are tagged "nice to have": edge cases where the system is allowed to defer to a human.

The pass thresholds are negotiated explicitly. The team and the client agree: 95% pass rate on critical, 85% on important, 70% on nice-to-have. Anything below this is not production ready, regardless of how good the demo looks.

The signed off artifact is the eval set. The PRD is a 4 page document that gives business context and lists the non-functional requirements. The eval set is the spec.

This has three consequences that play out over the project. First, in week four, when the first model is tested, it scores 91% on critical, 82% on important, 65% on nice-to-have. The conversation with the client is concrete: not "is the model good enough" but "we are 4 points short on critical, here is where it is failing, here is what we are doing about it". Second, in week seven, the team upgrades to a newer model. The eval set is re-run automatically. The new model scores 96% on critical and 88% on important. The decision to switch is data driven, not vibes driven. Third, in production six months later, the eval set is the regression test. When a vendor updates the underlying model, the operating team can verify within an hour whether anything broke.

The interesting comparison is with the parallel project at the same time, which was specified by a traditional PRD. That project had a similar build quality, but the steering committee meetings in weeks six through ten were dominated by "is this what we asked for" debates, because the PRD prose could be interpreted in multiple ways. The eval-specified project did not have those debates. The arguments were resolved in week two by writing down 120 specific question-answer pairs, and after that the discussion was always about hitting a number.

The lesson for AI delivery is that evals are not just for testing. They are the most useful form of requirements documentation that the field has produced. Investing in a good eval set in week two saves an enormous amount of weeks-eight-through-twelve confusion. The PRD does not go away, but it loses its status as the contract. The contract is the eval set.

**定义**

在传统软件项目里, PRD (产品需求文档) 是产品和工程之间的合同。它**用 prose 描述**要建什么, 配上 mock 和验收标准。AI 项目里, PRD 作为叙事文档仍然有用, 但它不是规格。规格是 eval set: 一份结构化的、把测试输入和期待输出配对、附带打分规则和通过阈值的集合。工程对着这个建, 客户签字接受这个。

**为何在交付中重要**

AI 交付里最常见的需求失败 pattern 是: 第二周 PRD 签字、第三到六周建模型、第七周 demo、客户说 "这不是我们要的"。PRD 没有把 "我们要的" 钉死成**机器可验证的形态**。eval set 钉死了。

把 evals 当作规格, 有三个具体后果:

1. **团队和客户在第二周吵 eval, 不在第八周吵 demo**。对话从主观变客观。
2. **工程工作有了可迭代的目标**。"通过 85% 的 evals" 是可建造的。"有用" 不是。
3. **当模型被升级时 (换版本、换厂商、改 prompt), 回归是可检测的**。没有 evals, **每一次 prompt 改动都是信仰之跃**。

**运作原理**

作为规格的 eval set 有以下结构。它是 Topic 7 描述的同一个产物, 但这里的定位是 "这是你的需求文档", 不是 "这是你的测试基础设施"。

| 组件 | 包含什么 | 谁拥有 |
|---|---|---|
| 输入 | 50 到 200 条真实或拟真的输入, 抽样覆盖生产分布 | 运营团队 (来自真实使用) |
| 期待输出 | 正确答案, 或描述什么样的答案算正确 | 运营团队 (交付团队记录) |
| 打分规则 | 怎么判每一对输入/输出: 精确匹配、语义匹配、rubric、LLM judge、人工 judge | 交付团队 (客户审阅) |
| 通过阈值 | 系统要被接受, 通过率多少 | 双方共同决定, 写下来 |
| 分层标签 | 把每一条 eval 标为 critical、important、nice to have | 双方共同决定 |

每一行都是一句规格说明。所有行加起来, 就是需求文档。项目新加入的人, 应该能通过读 eval set 理解系统该做什么, 不用读 PRD。

**为什么这对 AI 比 PRD 好用**

三个原因:

*Prose 藏歧义, 例子暴露它。* "AI 应该提供有帮助的产品信息" 在 PRD 里**看起来很清楚**。当团队和客户尝试写 30 个具体的 (客户问题, 有帮助的回应) 对子时, 他们**发现自己在其中 8 条上意见不一**。**那 8 条分歧, 就是真正的需求工作**。

*Evals 是机器可验证的。* PRD 要靠人**对着 demo 读 prose** 来检查。eval set 用脚本 30 秒检查完。**迭代速度提高一个数量级**。

*Evals 能挺过模型和 prompt 的变更。* 下一季度模型升级时, **重跑 eval set, 立刻看到系统是否还满足需求**。只有 PRD 的话, 得手动重测。

**怎么向客户介绍这件事**

做过传统软件项目的客户**期待一份 PRD**。直接告诉他 "我们不写 PRD" 会引起焦虑。更好的措辞是: "我们会写一份简短的 PRD 来讲叙事和业务背景, 然后写一份结构化的 eval set 作为真正的规格。eval set 是我们双方都会签字、双方都会用来核进度的东西。"

对话里有一个有用的产物: 一张一页的对照表, 两栏。"PRD 里写什么" (愿景、用户、业务结果、非功能需求如 latency 或成本) 和 "eval set 里写什么" (系统需要展现的实际行为)。**两个都产出**。有牙齿的是 eval set。

**PM 决策点**

- 我产出了 eval set, 还是只产出了 PRD?
- PRD 里的每一条需求, 我能指出**对应它的那几条 eval** 吗? 如果不能, **那条需求还没变成规格**。
- 客户签字的是 **eval set**, 还是只签了 PRD 的 prose?

**注意事项**

- 有些需求**确实不能表达成 evals** (例如 latency、成本、安全姿态)。**它们归 PRD 或单独的非功能规格管, 不要硬塞进 eval set**。
- **没有通过阈值的 eval set 是 checklist, 不是规格**。永远把 eval set 跟目标百分比和 "哪些 eval 是 critical 的定义" 配对。
- **客户看不懂的 evals, 客户没法签字**。**输入和期待输出用大白话写**, 哪怕打分本身是技术性的。

**要点总结: AI 交付里, eval set 是规格。PRD 是叙事。工程对着 eval set 建, 客户签字接受 eval set, eval set 能挺过模型更新。**

**Qantas 案例**

设想你在 Qantas 跑一个 AI 项目, 给客服团队建一个内部政策助手: 坐席能问 "我们关于 X 的政策是什么", 拿到从内部文档抽取的正确答案。**传统做法**是写一份 PRD 描述工具、用户、期待行为、验收标准, 用 prose 写, 然后照着 PRD 建。

eval-作为-规格的做法**起手就不一样**。第二周, 团队和客服运营团队坐下来, 产出一份 120 个问题的 eval set。问题是**真实的**: 它们来自上季度 "坐席-向-主管-升级" 的样本, 那些坐席问主管做政策澄清的情况。每个问题都配一个正确答案, 来源是政策文档, 由运营团队确认。

120 个问题**分层**。40 个标 "critical": 关于安全、退款、中断补偿, 答错会直接导致客户伤害或财务损失。60 个标 "important": 常见问题, 答错会引起客户挫败感。20 个标 "nice to have": 边缘情况, 系统**被允许把这些转给人工**。

通过阈值**明确协商**。团队和客户同意: critical 95% 通过率、important 85%、nice-to-have 70%。低于这个就不是生产就绪, 不管 demo 多好看。

签字的产物**是 eval set**。PRD 是一份 4 页的文档, 给业务背景, 列非功能需求。eval set 才是规格。

这件事在项目过程中**带来三个后果**。第一, 第四周第一版模型测试时, critical 91%、important 82%、nice-to-have 65%。跟客户的对话**是具体的**: 不是 "模型够不够好", 而是 "critical 上我们差 4 个点, 这是它失败的地方, 这是我们正在做的"。第二, 第七周团队升级到一个新模型。eval set **自动重跑**。新模型 critical 96%、important 88%。换模型的决定是数据驱动的, 不是 vibe 驱动的。第三, 六个月后在生产里, eval set 是回归测试。供应商更新底层模型时, 运营团队**一小时内**能验证有没有什么坏了。

**有意思的对比**是同期一个**用传统 PRD 规定**的并行项目。那个项目构建质量类似, 但**第 6 到 10 周的 steering committee 都被 "这是我们要的吗" 的辩论占据**, 因为 PRD prose 可以被多种方式解读。eval-规格的项目没有那些辩论。争论在第二周通过写下 120 对具体的问答就解决了, 之后所有讨论都是关于**击中一个数**。

AI 交付的启示: evals 不只是用来测试。它们是这个领域产出过的最有用的需求文档形态。在第二周投资一份好的 eval set, 能省下大量第 8 到 12 周的混乱。PRD 不会消失, 但它失去了作为合同的地位。合同是 eval set。
