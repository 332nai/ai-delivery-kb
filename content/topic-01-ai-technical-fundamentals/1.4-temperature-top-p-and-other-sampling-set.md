::: en

**Definition**

Sampling settings control how the model picks its next token from the list of possibilities. Temperature scales how adventurous the choice is (0 means always the most likely token, 1+ means more random). Top p (nucleus sampling) restricts the choice to the smallest set of tokens whose combined probability adds up to p (e.g. 0.9 means the top 90 percent of probability mass).

**Why it matters in delivery**

These are the only knobs you can turn at inference time without changing the prompt or the model. Wrong settings make a perfectly good prompt look broken. Clients see inconsistent output and assume the model is unreliable, when really someone left temperature at 1.0 on a classification task that should be deterministic.

**How it works**

At every step, the model has a probability distribution over tens of thousands of possible next tokens. Sampling settings shape which one gets picked.

| Setting | Range | Effect | Use when |
|---|---|---|---|
| Temperature 0 to 0.3 | Low | Deterministic, repeatable, picks safest token | Classification, extraction, structured output, evals |
| Temperature 0.7 to 1.0 | Mid to high | Varied, more creative phrasing | Drafting, brainstorming, marketing copy |
| Temperature 1.0+ | High | Often incoherent, prone to errors | Rarely useful in production |
| Top p 0.9 to 1.0 | Standard | Allows natural variation while cutting off long tail | Default for most chat use cases |
| Top p 0.1 to 0.3 | Tight | Forces very conservative output | Highly constrained generation |

In practice, most teams adjust temperature and leave top p at default. Adjusting both at once is rarely needed and makes debugging harder.

**PM decision points**

- Is this task deterministic (extraction, classification) or generative (writing, ideation)?
- Will the same input ever need to produce the same output for audit or compliance?
- Are eval results noisy because the task is hard, or because temperature is too high?

**Watch outs**

- Temperature 0 is not fully deterministic across providers, there is still some variance
- High temperature increases hallucination rates, not just creativity
- Some APIs expose only one of temperature or top p, check before scoping

**Takeaway: temperature is the difference between a reliable system and a coin flip. Default to 0 for anything you need to evaluate or audit.**

**Qantas story**

Within Qantas, AI use cases span an enormous range from highly deterministic to highly creative. The same airline has teams that want zero variability (extracting specific fields from supplier invoices, classifying customer complaints by category, generating standardised flight delay notifications) and teams that want lots of variability (drafting marketing copy for new Hawaii routes, generating variations of cabin crew briefing language, brainstorming campaign concepts for the Frequent Flyer program).

A finance team automating accounts payable wants temperature near zero. The same invoice should produce the same extracted fields every time. Audit trails depend on reproducibility. A 0.7 temperature setting that worked beautifully for a marketing copy generator would create chaos in finance, where the same vendor invoice might be classified differently on Monday and Friday, breaking reconciliation.

Meanwhile, a marketing team using temperature 0 on caption generation would get the same captions for every flight sale. The product would feel mechanical and stale. The same low temperature that brings finance teams confidence destroys marketing's creative output.

The lesson for delivery teams supporting an enterprise like Qantas is that there is no single "correct" temperature setting for the company. Each use case has its own profile. A central AI platform team needs to expose temperature as a deliberate configuration choice, not a hidden default, and educate downstream teams on which end of the spectrum suits their work. The most common failure pattern is a platform team that picks one setting (often 0.7, the prototype default) and ships it everywhere, then spends months debugging why downstream teams complain about either inconsistency or blandness.

For AI delivery specifically, this is a useful framing in client conversations. When a stakeholder says "the AI is unreliable," the diagnostic question is often not about the model or the prompt, but about whether the sampling settings match the task type. The first 30 seconds of a debugging conversation should be "what is your temperature set to and is the task deterministic or generative." That single question resolves more problems than people expect.

::: zh

**定义**

采样设置控制模型如何从可能性列表中选择下一个 token。Temperature 调节选择的冒险程度 (0 意味着总是选最可能的 token,1+ 意味着更随机)。Top p (nucleus sampling) 限制选择在累积概率达到 p 的最小 token 集合中 (例如,0.9 意味着前 90% 的概率质量)。

**为何在交付中重要**

这些是你在不改变 prompt 或模型的情况下,在推理时唯一能转动的旋钮。错误的设置让一个完美的 prompt 看起来出问题了。客户看到不一致的输出,以为模型不可靠,而实际上是有人在应该确定的分类任务上把 temperature 留在 1.0。

**运作原理**

每一步,模型都有一个分布在数万个可能的下一个 token 上的概率。采样设置塑造哪一个被选中。

| 设置 | 范围 | 效果 | 使用场景 |
|---|---|---|---|
| Temperature 0 到 0.3 | 低 | 确定性、可重复、选择最安全的 token | 分类、提取、结构化输出、evals |
| Temperature 0.7 到 1.0 | 中到高 | 多样、更有创意的措辞 | 起草、头脑风暴、营销文案 |
| Temperature 1.0+ | 高 | 通常不连贯、容易出错 | 在生产中很少有用 |
| Top p 0.9 到 1.0 | 标准 | 允许自然变化,同时切断长尾 | 大多数聊天用例的默认 |
| Top p 0.1 到 0.3 | 紧 | 强制非常保守的输出 | 高度约束的生成 |

实践中,大多数团队调整 temperature,把 top p 留在默认值。同时调整两者很少必要,而且让调试更难。

**PM 决策点**

- 这个任务是确定性的 (提取、分类) 还是生成性的 (写作、想法)?
- 同样的输入是否需要为审计或合规产生相同的输出?
- Eval 结果嘈杂是因为任务难,还是因为 temperature 太高?

**注意事项**

- Temperature 0 在不同提供商之间不是完全确定的,仍有一些方差
- 高 temperature 增加幻觉率,不仅是创造力
- 一些 API 只暴露 temperature 或 top p 之一,需求确定前检查

**要点总结: Temperature 是可靠系统和抛硬币之间的区别。对任何需要评估或审计的内容,默认设为 0。**

**Qantas 案例**

在 Qantas 内部,AI 用例跨越从高度确定性到高度创造性的巨大范围。同一家航空公司的不同团队既要零变异性 (从供应商发票中提取特定字段、按类别分类客户投诉、生成标准化航班延误通知),也要大量变异性 (为新的夏威夷航线起草营销文案、生成机组人员简报语言的变体、为 Frequent Flyer 项目头脑风暴活动概念)。

自动化应付账款的财务团队希望 temperature 接近零。同一张发票每次都应产生相同的提取字段。审计追踪依赖于可重复性。对营销文案生成器效果绝佳的 0.7 temperature 设置,会在财务部门制造混乱,同一张供应商发票可能在周一和周五被不同地分类,破坏对账。

与此同时,在文案生成上使用 temperature 0 的营销团队会为每个机票促销得到相同的文案。产品会感觉机械和陈旧。给财务团队带来信心的同一个低 temperature 摧毁了营销的创意输出。

对支持像 Qantas 这样的企业的交付团队来说,启示是公司没有单一"正确"的 temperature 设置。每个用例都有自己的画像。中央 AI 平台团队需要将 temperature 暴露为一个有意识的配置选择,而不是隐藏的默认值,并教育下游团队哪一端的范围适合他们的工作。最常见的失败模式是平台团队选择一个设置 (通常是 0.7,原型默认值) 并把它发布到所有地方,然后花数月调试为什么下游团队抱怨不一致或乏味。

对 AI 交付来说具体而言,这是客户对话中有用的框架。当利益相关者说"AI 不可靠"时,诊断问题往往不是关于模型或 prompt,而是关于采样设置是否匹配任务类型。调试对话的前 30 秒应该是"你的 temperature 设置是什么,任务是确定性的还是生成性的"。这一个问题解决的问题比人们预期的要多。
