**Definition**

Closed weight models are accessed only through the provider's API (e.g. Claude, GPT, Gemini). You send tokens, you receive tokens, you never see or download the model itself. Open weight models have their weights published for anyone to download and run (e.g. Llama, Qwen, DeepSeek, Mistral). "Open weight" is not the same as "open source," since training data and code are usually not released.

**Why it matters in delivery**

This is one of the first architectural decisions in any enterprise AI project and it has huge commercial, legal, and operational consequences. Clients in regulated industries or with sovereignty requirements often cannot send data to a third party API. Clients with high volume use cases may find closed API costs untenable at scale. Knowing the trade off lets you scope the right solution instead of defaulting to whatever the team used last time.

**How it works**

| Dimension | Closed weight (API) | Open weight (self hosted) |
|---|---|---|
| Quality at frontier | Highest, defines the state of the art | 6 to 12 months behind, closing fast |
| Setup time | Minutes, just an API key | Weeks, needs GPU infra and ops |
| Cost model | Pay per token, scales linearly | Fixed GPU cost, cheaper at high volume |
| Data control | Data leaves your environment, governed by provider terms | Data never leaves your environment |
| Customisation | Limited to prompting, fine tuning via API | Full control, can fine tune, distill, modify |
| Maintenance burden | Provider handles updates, deprecations | Your team owns inference, scaling, monitoring |
| Best for | Most enterprise use cases, especially early stage | Regulated industries, sovereign data, high volume, edge deployment |

The break even point on cost is usually around tens of millions of tokens per day. Below that, closed APIs almost always win on total cost of ownership once you factor in engineering time.

**PM decision points**

- Does the client have hard requirements on data residency, sovereignty, or no third party processors?
- What is the expected token volume in year one and year two?
- Does the team have GPU operations skills, or is that a new hire and a new risk?
- Is the use case quality sensitive enough that frontier model performance matters?

**Watch outs**

- "Open weight" does not mean licence free, check Llama, Qwen, DeepSeek terms for commercial restrictions
- Self hosting on cloud GPUs is not the same as on premise, clarify which the client means
- Quality gaps narrow fast, a six month old "we tested open models, they were bad" assessment is already out of date

**Takeaway: closed API is the right default for almost every project, until data residency, volume economics, or customisation needs force you to self host.**

**Qantas story**

Qantas, like most large Australian enterprises, has a strong default toward closed API consumption of AI for almost every use case. The reasons are not primarily technical, they are commercial and operational. Qantas already has enterprise agreements with AWS and Microsoft. Adding Claude via Bedrock or Azure OpenAI is a procurement amendment, not a new vendor relationship. The data residency questions are answered by region selection. The compliance posture inherits from existing cloud agreements.

The case for open weight models at Qantas is narrower than people assume. Even high volume use cases like customer service intent classification, where unit economics matter, do not always justify self hosting once you factor in the operational cost of running inference infrastructure, the talent required to maintain it, and the GPU procurement complexity. The closed API margin is real, but so is the engineering overhead of running open weights at airline scale and reliability.

Where open weight does earn its place is in narrowly constrained use cases. Edge deployment on aircraft cabin systems would be one (latency requirements, no reliable internet). Highly sensitive internal data that cannot leave the corporate boundary at all would be another. Specific high volume embedded use cases (text classification on millions of customer interactions per month) might pencil out. But each of these is a deliberate engineering choice, not a default architecture.

The broader insight for AI delivery is that the open vs closed conversation is usually a leadership conversation, not an engineering one. Executives ask "should we be self hosting" because they have heard about cost, sovereignty, or strategic independence at conferences. The right response is not to debate the technology, but to walk through the client's specific constraints, volumes, and team capabilities. For most large Australian enterprises in 2026, the answer is closed API for 95 percent of use cases and selective open weight for the 5 percent where it materially matters. Framing it that way moves the conversation from religious debate to portfolio decision making.

**定义**

Closed weight 模型只能通过提供商的 API 访问 (例如 Claude、GPT、Gemini)。你发送 tokens,你接收 tokens,你永远看不到或下载模型本身。Open weight 模型的权重发布给任何人下载和运行 (例如 Llama、Qwen、DeepSeek、Mistral)。"Open weight"与"open source"不同,因为训练数据和代码通常不发布。

**为何在交付中重要**

这是任何企业 AI 项目的最早架构决策之一,并且有巨大的商业、法律和运营后果。在监管行业或有主权要求的客户通常无法将数据发送给第三方 API。具有高量使用场景的客户可能发现闭源 API 成本在规模下难以承受。了解权衡能让你确定正确的解决方案范围,而不是默认使用团队上次用的东西。

**运作原理**

| 维度 | Closed weight (API) | Open weight (自托管) |
|---|---|---|
| 前沿质量 | 最高,定义最先进水平 | 落后 6 到 12 个月,快速缩小 |
| 设置时间 | 几分钟,只需要 API key | 数周,需要 GPU 基础设施和运维 |
| 成本模型 | 按 token 付费,线性扩展 | 固定 GPU 成本,在高量下更便宜 |
| 数据控制 | 数据离开你的环境,受提供商条款约束 | 数据从不离开你的环境 |
| 定制 | 仅限于 prompting,通过 API 进行 fine tuning | 完全控制,可以 fine tune、蒸馏、修改 |
| 维护负担 | 提供商处理更新、弃用 | 你的团队拥有推理、扩展、监控 |
| 最适合 | 大多数企业用例,尤其是早期阶段 | 监管行业、主权数据、高量、边缘部署 |

成本上的盈亏平衡点通常在每天数千万 tokens 左右。在此之下,一旦你考虑工程时间,closed API 几乎总是在总拥有成本上获胜。

**PM 决策点**

- 客户在数据驻留、主权或无第三方处理器上是否有硬性要求?
- 第一年和第二年的预期 token 量是多少?
- 团队是否有 GPU 运维技能,还是这是一次新招聘和新风险?
- 这个用例是否对质量敏感到前沿模型性能很重要?

**注意事项**

- "Open weight"不意味着免许可证,检查 Llama、Qwen、DeepSeek 的条款看商业限制
- 在云 GPU 上自托管与本地部署不同,澄清客户指哪个
- 质量差距快速缩小,六个月前的"我们测试过开源模型,它们很差"评估已经过时

**要点总结: Closed API 是几乎每个项目的正确默认,直到数据驻留、量经济学或定制需求迫使你自托管。**

**Qantas 案例**

Qantas,像大多数大型澳大利亚企业一样,对几乎每个用例都有强烈的偏好,即默认使用 closed API 消费 AI。原因主要不是技术性的,而是商业和运营性的。Qantas 已经与 AWS 和 Microsoft 有企业协议。通过 Bedrock 或 Azure OpenAI 添加 Claude 是采购修订,不是新的供应商关系。数据驻留问题通过区域选择回答。合规姿态从现有云协议继承。

在 Qantas,open weight 模型的理由比人们想象的要窄。即使是高量用例如客户服务意图分类,单位经济学很重要,一旦你考虑运行推理基础设施的运营成本、维护它所需的人才,以及 GPU 采购的复杂性,自托管也并不总是合理。closed API 的差额是真实的,但在航空规模和可靠性下运行 open weights 的工程开销也是。

open weight 真正赢得位置的地方是在狭窄约束的用例上。在机舱系统上的边缘部署可能是一个 (延迟要求,无可靠的互联网)。完全无法离开企业边界的高度敏感的内部数据可能是另一个。特定的高量嵌入式用例 (每月对数百万客户互动进行文本分类) 可能算得过来。但这些每一个都是有意的工程选择,而不是默认架构。

对 AI 交付来说,更广泛的洞察是,open 与 closed 的对话通常是领导对话,而不是工程对话。高管问"我们是否应该自托管",因为他们在会议上听说过成本、主权或战略独立性。正确的回应不是辩论技术,而是逐一讨论客户的特定约束、量和团队能力。对大多数大型澳大利亚企业来说,在 2026 年,95% 的用例答案是 closed API,5% 实质性重要的地方选择性地使用 open weight。这样框定将对话从宗教辩论转移到组合决策制定。
