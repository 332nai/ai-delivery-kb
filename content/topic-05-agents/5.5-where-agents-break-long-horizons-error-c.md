**Definition**

Agents fail in characteristic ways that are different from single LLM call failures. The three most common are: long horizon failures (agent loses the thread on tasks with many steps), error compounding (small errors snowball across steps), and cost blowouts (agents run for far more steps than expected). Understanding these failure modes is what separates teams that ship reliable agents from teams that abandon agent projects.

**Why it matters in delivery**

Almost every agent project hits these failure modes in production. PMs who recognise the pattern can scope around them and set guardrails early. PMs who do not get blindsided in week three when costs are 5x forecast and tasks are completing 60 percent of the time.

**How it works**

| Failure mode | What happens | Why | Mitigation |
|---|---|---|---|
| Long horizon failure | Agent forgets the original goal after many steps | Context fills with intermediate results, original task drifts | Re inject goal each iteration, summarise old steps, hard step limit |
| Error compounding | Small mistakes accumulate, final output is badly wrong | Each step's small error feeds the next step | Verification at each step, narrower tool surface, eval per step |
| Cost blowout | Agent runs 50 steps for a task that should take 5 | Inefficient loops, agent over thinks, retries pile up | Step limit, cost cap per task, route easy tasks away from agent |
| Tool misuse | Agent calls wrong tool or wrong arguments | Too many tools, vague descriptions | Fewer tools, clearer descriptions, validation |
| Infinite loops | Agent gets stuck retrying the same thing | No stop condition, model confidence stays high | Detect repeated states, force escalation |
| Silent failure | Agent reports success but did not complete | No verification step, hallucinated success | Tool result validation, completion checks |

**Worked example, error compounding**

Step 1: Agent retrieves customer record. Correct, but uses outdated cached data.

Step 2: Agent looks up account based on step 1 data. Finds the wrong account.

Step 3: Agent summarises account activity. Activity is real but for the wrong account.

Step 4: Agent emails the customer. Email is fluent, polite, and entirely wrong.

No single step looked broken. The error compounded silently.

**PM decision points**

- What is the maximum acceptable cost and time per task, and is the agent enforcing it?
- How does the system handle tasks that hit limits, escalate, fail gracefully, retry?
- Where are we verifying intermediate results vs trusting them blindly?

**Watch outs**

- Demos always hit best case, production hits worst case, plan for both
- Cost monitoring needs to be at task level, not just monthly aggregate
- Long horizon tasks (over 20 steps) are at the edge of what current models do reliably, scope accordingly

**Takeaway: agents fail in compounding ways. Cap steps, cap cost, verify results, and have a human escalation path from day one.**

**Qantas story**

Agent failure modes show up in interesting ways at Qantas scale. Consider the disruption recovery agent again, in production. The expected behaviour is that each recovery task completes in five to ten agent steps, costs about AUD 0.50 in model calls, and produces a coherent recovery plan within ninety seconds.

The actual production behaviour, in the first weeks of any such system, would likely include the following failure modes. A small percentage of tasks involve unusually complex disruptions and the agent loops well beyond the expected step count, running fifty or more steps and costing AUD 15 per task. Some tasks get stuck retrying the same retrieval call because the underlying data is incomplete and the agent does not recognise it. Some tasks produce confidently wrong outputs because an earlier step retrieved stale data and every subsequent step compounded the error. Some tasks silently fail by reporting success while having skipped a critical constraint check.

Each of these is a known agent failure pattern, and each has a known mitigation. Hard step limits cap runaway loops. Cost limits per task prevent budget surprises. Detection of repeated tool calls with same parameters catches stuck loops. Verification steps after each major decision catch error compounding. Schema validation on agent outputs catches silent failures.

The interesting organisational point is who notices these failures. Cost monitoring at the team level catches the first failure mode within hours. Customer service tickets about wrong recovery decisions catch the second mode within days. Audit reviews catch the third and fourth modes within weeks. Each mode has a different surface area, and the observability strategy needs to cover all of them.

The other lesson is that agent failure rates depend heavily on the difficulty distribution of the workload. A pilot with curated test cases looks great. Production with the full long tail of real disruptions looks much worse. The gap between pilot success and production reality is often 20 to 30 percentage points on task completion rate. Teams that plan for this gap, with conservative rollout, graceful escalation to human handlers, and aggressive monitoring, survive the first month. Teams that do not, often pause the rollout and lose months rebuilding confidence.

For AI delivery, the takeaway is that agents fail in compounding, expensive, sometimes silent ways. The mitigations are well known and not optional. Hard limits on steps and cost. Verification at every meaningful decision point. Observability that surfaces both successful tasks and the cost distribution. A clear escalation path to humans when limits are hit. Teams that build these in from the first version ship agents that survive contact with production. Teams that bolt them on after the first incident lose trust quickly and rarely recover it.

**定义**

Agent 的失败方式跟单次 LLM 调用不一样。最常见的三种是: 长视野失败 (agent 在多步任务里跟丢了主线)、错误复合 (小错误在步骤之间滚雪球)、成本爆炸 (agent 跑的步数远远超过预期)。理解这几种失败方式,是"能发出可靠 agent 的团队"和"放弃 agent 项目的团队"之间的区别。

**为何在交付中重要**

几乎每个 agent 项目在生产里都会碰到这些失败 pattern。能识别这些 pattern 的 PM,能在项目早期围着它们做范围设计、提前设好护栏。识别不了的 PM,会在第三周被打个措手不及——那时候成本是预测的 5 倍,任务完成率只有 60%。

**运作原理**

| 失败 pattern | 发生了什么 | 为什么 | 缓解 |
|---|---|---|---|
| 长视野失败 | Agent 在很多步之后忘了原始目标 | 上下文被中间结果填满,原始任务被挤走 | 每次迭代重新注入目标、把旧步骤做摘要、设硬步数上限 |
| 错误复合 | 小错误累积起来,最终输出严重错 | 每一步的小错都被传到下一步 | 每步做校验、收窄工具面、按步骤 eval |
| 成本爆炸 | 一个本该 5 步完成的任务,agent 跑了 50 步 | 低效循环、agent 想太多、重试堆积 | 步数上限、每任务成本上限、把简单任务从 agent 路径里拿走 |
| 工具误用 | Agent 调错了工具或者参数填错 | 工具太多、描述太模糊 | 减少工具、改清晰描述、加校验 |
| 死循环 | Agent 卡在重试同一件事 | 没有停止条件、模型置信度一直很高 | 检测重复状态、强制升级 |
| 静默失败 | Agent 报告成功,但根本没完成 | 没有校验步骤、把不存在的成功幻觉了出来 | 工具结果校验、完成情况检查 |

**举例,错误复合**

第 1 步: Agent 检索客户记录。检索本身没错,但用的是过期的缓存数据。

第 2 步: Agent 基于第 1 步的数据查账户。找到了一个错的账户。

第 3 步: Agent 总结账户活动。活动数据是真的,但属于错的那个账户。

第 4 步: Agent 给客户发邮件。邮件流畅、礼貌,完全错了。

每一步单看都不像坏掉。错误是悄无声息地复合起来的。

**PM 决策点**

- 每个任务可接受的最大成本和最大时间是多少?Agent 有没有强制执行这两个上限?
- 系统怎么处理达到上限的任务?升级、优雅失败、还是重试?这三种都要明确路径。
- 我们在哪里校验中间结果,而不是盲目相信它们?

**注意事项**

- Demo 总是命中最好情况,生产命中最坏情况。两边都要做规划。
- 成本监控要做到任务级别,不能只看每月聚合。这两件事是绑在一起的。
- 长视野任务 (超过 20 步) 已经在当前模型可靠完成的边缘了,定范围的时候要算上这一点。

**要点总结: Agent 以复合的方式失败。限步数、限成本、校验结果、从第一天起就准备好一条人工升级路径。**

**Qantas 案例**

Agent 的失败 pattern,在 Qantas 这种规模上会以有意思的方式表现出来。再回到那个中断恢复 agent,假设它在生产里跑。预期的行为是: 每个恢复任务 5 到 10 个 agent 步骤完成,模型调用花费大约 0.50 澳元,90 秒内产出一份连贯的恢复方案。

任何这种系统在头几周的真实生产行为,大概率会出现以下几种失败 pattern。一小部分任务涉及异常复杂的中断,agent 远远超出预期步数,跑了 50 步以上,每个任务花掉 15 澳元。有些任务卡在反复重试同一个检索调用,因为底层数据本来就不完整,而 agent 不识别这一点。有些任务给出了自信但错误的输出,因为某个早期步骤检索到了过期数据,后面每一步都把这个错误放大了。还有些任务干脆静默失败: 报告成功,但其实跳过了一个关键的约束检查。

这每一种都是已知的 agent 失败 pattern,每一种都有已知的缓解。硬步数上限抑制失控循环。每任务成本上限防止预算意外。检测"带相同参数的重复工具调用"能抓出卡住的循环。每个主要决策之后加一道校验步骤,能抓住错误复合。在 agent 输出上做 schema 校验,能抓住静默失败。

有意思的组织视角是: 谁会注意到这些失败。团队级别的成本监控,在几小时内就能抓到第一种失败。客户对错误恢复决策的投诉工单,几天内能反映出第二种。审计 review 在几周内能抓到第三和第四种。每一种失败的"暴露面"不一样,可观测性策略要把全部覆盖到。

另一个教训是: agent 失败率严重依赖工作负载的难度分布。一个带精选测试用例的试点看起来很漂亮。生产环境里的真实中断长尾跑起来,表现差得多。试点成功率和生产现实之间的差距,在任务完成率上经常是 20 到 30 个百分点。为这道差距做规划的团队 (保守地分批推、对人工处理者有优雅升级、监控密集),第一个月活下来了。没做规划的团队经常被迫暂停推广,然后花几个月重建信任。

往大了说,这件事给 AI 交付的启示是: Agent 以"复合的、昂贵的、有时静默的"方式失败。缓解措施都是已知的,不是可选项。步数和成本的硬上限。每一个有意义的决策点都做校验。可观测性既要看成功的任务,也要看成本分布。一条达到上限时通向人工的清晰升级路径。从第一版就把这些都建进去的团队,做出来的 agent 才能在跟生产环境接触之后活下来。第一次事故之后才把这些拼上去的团队,信任掉得很快,而且很少能再补回来。
