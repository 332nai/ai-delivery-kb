**Definition**

Tool use (also called function calling) is the mechanism by which an LLM can request that an external function be executed, receive the result, and incorporate it into its response. The model does not run the tool itself, it generates a structured request that your code executes and returns. Tools can be anything: a search API, a calculator, a database query, a third party service.

**Why it matters in delivery**

Tool use is the bridge between language models and real systems. Without it, an LLM is a closed box that can only generate text. With it, the LLM can read your CRM, query your database, send emails, call third party APIs, and act in the world. Every agentic system, every modern chatbot that does anything useful, runs on tool use.

**How it works**

The four step pattern:

1. You describe tools to the model in its system prompt or via the API's tool parameter (name, what it does, what inputs it takes)
2. The model decides whether to call a tool, and which one, based on the user's message
3. Your code receives the tool call, executes it, returns the result
4. The model reads the result and either calls another tool or generates a final answer

A typical tool definition:

```
{
  "name": "search_customer",
  "description": "Look up a customer by email or phone number",
  "parameters": {
    "type": "object",
    "properties": {
      "email": {"type": "string"},
      "phone": {"type": "string"}
    }
  }
}
```

| Tool type | Example | Risk profile |
|---|---|---|
| Read only data lookup | Search products, get weather, query stock | Low, hard to do damage |
| Write operations | Update CRM, send email, create ticket | Medium, can affect real systems |
| Code execution | Run Python, run SQL | High, sandbox required |
| External API calls | Stripe, Slack, third party services | Variable, depends on auth and scope |
| Long running operations | File processing, batch jobs | Needs async handling |

**PM decision points**

- Which tools does the agent actually need on day one, fewer is almost always better
- Are write operations gated by human approval, or fully autonomous?
- What happens when a tool fails or returns an error, how does the model recover?

**Watch outs**

- Too many tools confuse the model, it picks the wrong one or hallucinates parameters
- Tool descriptions are part of the prompt, vague descriptions lead to misuse
- Tool authentication and authorisation is a real security surface, treat it like API security

**Takeaway: tool use turns LLMs from talkers into doers. Scope tools tightly, gate write operations, monitor everything.**

**Qantas story**

Tool use is where AI moves from interesting to genuinely useful at Qantas. Consider a hypothetical AI assistant for the Frequent Flyer team handling member inquiries. The assistant on its own can talk about points programs in general, but it cannot answer the questions that matter (what is my balance, can I upgrade this booking, am I eligible for status match). Those questions require reading from Qantas systems.

The tool set might include lookup member by email or membership number, get current points balance and status tier, check upgrade availability for a specific booking, calculate points required for a specific reward redemption, retrieve recent activity, and check eligibility for specific promotions. Each tool is a thin wrapper around an existing system or API, exposed to the model with a clear description and parameter schema.

The interesting design question is how to handle write operations. Should the AI be able to actually redeem points, change a booking, or apply a status match? The conservative answer at most large enterprises is no, every write operation goes through a human approval step. The AI prepares the action, presents it for review, and the human commits it. This trades automation for safety, and at Qantas brand standards, that trade is usually worth it.

The other interesting question is how many tools to expose. The temptation is to give the agent every tool that might be useful. The reality is that more tools confuse the model. With ten tools, the agent picks the right one most of the time. With fifty tools, the failure rate on tool selection grows noticeably. The discipline is to expose the minimum tool set for the use case and add tools deliberately as evals demonstrate value.

Tool design is also under appreciated. A poorly designed tool with vague parameter descriptions and inconsistent error responses confuses the model. A well designed tool with clear descriptions, strict parameter validation, and informative error messages helps the agent recover from mistakes. The tool layer is product design as much as engineering.

For AI delivery, the broader lesson is that tool use is where AI delivery work intersects with the rest of the enterprise tech stack. The model is just the brain. The tools are how it reaches into existing systems. Designing those tools well, with proper scoping, validation, observability, and human approval gates, is what turns a chatbot demo into a real production system. Teams that treat tool design as an afterthought ship demos. Teams that treat it as core engineering ship products.

**定义**

工具调用 (也叫 function calling) 是一种机制: LLM 可以请求执行一个外部函数,接收结果,然后把结果纳入回应。模型本身不跑工具,它生成一个结构化的请求,你的代码执行它,然后把结果返回给模型。工具可以是任何东西: 搜索 API、计算器、数据库查询、第三方服务。

**为何在交付中重要**

工具调用是语言模型跟真实系统之间的桥梁。没有它,LLM 是一个封闭盒子,只能生成文本。有了它,LLM 可以读你的 CRM、查你的数据库、发邮件、调第三方 API、在真实世界里产生动作。每一个 agentic 系统,每一个能做有用事情的现代聊天机器人,运行的基础都是工具调用。

**运作原理**

四步模式:

1. 你在 system prompt 里、或者通过 API 的 tool 参数,向模型描述工具 (名字、做什么、接受什么输入)
2. 模型根据用户消息决定要不要调工具、调哪一个
3. 你的代码接收到工具调用请求,执行它,把结果返回
4. 模型读结果,要么再调另一个工具,要么生成最终答案

一个典型的工具定义:

```
{
  "name": "search_customer",
  "description": "按 email 或电话号码查找客户",
  "parameters": {
    "type": "object",
    "properties": {
      "email": {"type": "string"},
      "phone": {"type": "string"}
    }
  }
}
```

| 工具类型 | 例子 | 风险画像 |
|---|---|---|
| 只读数据查询 | 搜索产品、查天气、查股价 | 低,很难造成损害 |
| 写操作 | 更新 CRM、发邮件、创建工单 | 中,可能影响真实系统 |
| 代码执行 | 跑 Python、跑 SQL | 高,需要沙箱 |
| 调外部 API | Stripe、Slack、各种第三方服务 | 不定,看认证和权限范围 |
| 长时间操作 | 文件处理、批处理任务 | 需要异步处理 |

**PM 决策点**

- Agent 第一天真正需要哪些工具?少几乎总是更好。
- 写操作要不要过人工审批,还是完全自主?这件事不在第一周定下来,后面会出大问题。
- 工具失败或返回错误的时候会发生什么?模型怎么恢复?这套机制要早设计。

**注意事项**

- 工具太多会让模型懵: 它会挑错工具,或者把参数编出来。
- 工具描述本身就是 prompt 的一部分,描述模糊就会被误用。
- 工具的认证和授权是真实的安全表面,要按 API 安全的标准来对待。

**要点总结: 工具调用把 LLM 从"说话的"变成"干活的"。工具范围要收紧,写操作要把关,所有动作都要可观测。**

**Qantas 案例**

工具调用是 AI 在 Qantas 从"有趣"变成"真有用"的分水岭。设想一个 AI 助手给 Frequent Flyer 团队用,处理会员咨询。光靠它自己,助手可以泛泛地聊积分计划,但回答不了那些真正重要的问题 (我现在积分多少、能不能升舱、能不能做 status match)。这些问题都需要从 Qantas 系统里读数据。

工具集可能包括: 按 email 或会员号查会员、获取当前积分余额和等级、检查某个具体订单的升舱可用性、计算某个具体兑换需要多少积分、查最近的活动记录、查某个促销的资格。每一个工具都是对现有系统或 API 的薄包装,配清晰的描述和参数 schema 暴露给模型。

有意思的设计问题是写操作怎么处理。AI 能不能实际执行兑换积分、变更订单、或者应用 status match?对大部分大型企业来说,保守的答案是不能,每一个写操作都要过人工审批这一关。AI 准备好动作,提交去 review,人工最终提交。这是用自动化换安全,在 Qantas 的品牌标准下,这种交换通常是值得的。

另一个有意思的问题是暴露多少工具。诱惑是把所有"可能有用"的工具都给 agent。现实是工具越多模型越懵。10 个工具,agent 大部分时候能选对。50 个工具,工具选择的失败率明显上升。纪律是: 为这个用例暴露最小工具集,等 evals 证明价值之后再有意识地加。

工具本身的设计也经常被低估。一个参数描述含糊、错误响应不一致的工具,会让模型懵。一个描述清晰、参数校验严格、错误信息有用的工具,能帮 agent 从错误里恢复。工具这一层既是工程,也是产品设计。

往大了说,这件事给 AI 交付的启示是: 工具调用是 AI 交付工作跟整个企业技术栈接口的地方。模型只是大脑,工具才是它伸进现有系统的手。把工具设计好——合适的范围、校验、可观测性、人工审批关卡——才是把一个聊天机器人 demo 变成真正生产系统的关键。把工具设计当事后再想的团队,只能发出 demo。把它当核心工程的团队,发出来的才是产品。
