**Definition**

An agent is an LLM that runs in a loop, deciding what to do next based on the results of previous steps, with access to tools and some form of memory. The defining feature is the loop. A single LLM call is not an agent. An LLM that calls a tool once is not an agent. An LLM that keeps going until a task is done, choosing its own next step, is an agent.

**Why it matters in delivery**

"Agent" is the most overloaded word in AI right now. Clients use it to mean anything from a chatbot to a fully autonomous worker. PMs who can ground the conversation in a precise definition save scoping nightmares. Agents also have fundamentally different cost, latency, and reliability profiles than single shot LLM calls, and getting this wrong destroys project economics.

**How it works**

The core loop:

```
[Goal or task]
    -> [LLM decides: which tool, which action, or done?]
    -> [Execute the action (call tool, run code, search)]
    -> [Observe the result]
    -> [Add result to context, loop back to LLM]
    ... continues until done or stopped ...
    -> [Final answer or action]
```

{{chart: agent-loop}}

The components:

| Component | What it does | Example |
|---|---|---|
| LLM (the brain) | Decides next step at each loop iteration | Claude, GPT, Gemini |
| Tools | The actions the agent can take | Search, calculator, database query, send email |
| Memory | What the agent remembers across loop iterations | Conversation history, scratchpad, retrieved facts |
| Orchestration | The code that runs the loop and enforces limits | Custom code, LangGraph, OpenAI Agents SDK |
| Stop conditions | When the loop ends | Task done, max steps, error, timeout |

**PM decision points**

- Does the task actually require a loop, or would a single LLM call plus retrieval work?
- What is the max number of steps before the agent should stop and ask a human?
- How will we measure agent performance, completion rate is not enough, you also need quality and cost per task?

**Watch outs**

- Clients say "agent" when they mean "chatbot," always clarify what they really want
- Agents fail in compounding ways, each step has some error rate, multiply across steps
- The most reliable agentic systems are the ones with the fewest steps and the most constrained tools

**Takeaway: an agent is an LLM in a loop with tools. Use the word precisely or scope will spiral.**

**Qantas story**

Across Qantas, the word "agent" gets used to mean very different things in different conversations. A customer service chatbot is sometimes called an agent. A workflow that processes inbound emails through a fixed pipeline is sometimes called an agent. A genuine autonomous system that decides its own steps is also called an agent. Without a precise definition, scoping conversations go in circles.

Consider where a true agent earns its complexity at Qantas. Disruption recovery is a strong candidate. When a major operational event happens (a runway closure, a major aircraft technical issue, a crew shortage), the recovery decisions involve multiple data sources (flight schedules, crew rosters, aircraft positioning, customer manifests), multiple constraints (duty time, maintenance, slot rules), and multiple possible actions (cancel, delay, rebook, swap, divert). The order and combination of these decisions cannot be specified up front because each step depends on what the previous step revealed.

An agent designed for this would have access to a defined set of tools (read schedule, read crew roster, read aircraft availability, read customer manifest, simulate proposed changes, draft customer notifications). It would loop, deciding its next action based on what it has learned so far. It would stop when a recovery plan is fully defined and ready for human approval.

This is a genuinely agentic problem. The shape of the task cannot be pre specified. The agent does the thinking that a senior duty manager would otherwise do in their head. The cost per task is high (many model calls, large context, expensive flagship model) but the value per task is also high (a good recovery plan saves hundreds of thousands of dollars per major disruption).

Conversely, most Qantas use cases do not need agents. Customer service queries, content generation, knowledge search, structured data extraction, these are all single shot or short pipeline tasks that a basic LLM call with retrieval or tool use handles well. Wrapping them in an agent loop adds cost and unreliability for no benefit.

For AI delivery, the takeaway is that "let us build an agent" is rarely the right answer to an enterprise problem. The right question is whether the task genuinely requires a loop of decision making, or whether it is a single shot transformation that the team is fashionably overengineering. Agents earn their keep on tasks where the path cannot be pre specified. For everything else, simpler is better, and pretending a single shot pipeline is an agent does not make it one.

**定义**

Agent 是一个跑在循环里的 LLM,它根据前一步的结果决定下一步该做什么,能访问工具,也带某种形式的记忆。定义性的特征是"循环"。单次 LLM 调用不是 agent。调用一次工具的 LLM 也不是 agent。只有那种"一直跑到任务完成,自己选下一步"的 LLM,才是 agent。

**为何在交付中重要**

"Agent"是 AI 圈里被滥用得最厉害的词。客户嘴里的 agent 可以是聊天机器人、也可以是完全自主的数字员工,中间所有东西都被叫 agent。能把对话拉回精确定义的 PM,能为团队省下需求确定阶段的大量痛苦。Agent 在成本、延迟、可靠性上的画像,跟单次 LLM 调用是根本不同的——这件事搞错了,项目的经济学就崩了。

**运作原理**

核心循环:

```
[目标或任务]
    -> [LLM 决定: 用哪个工具,做什么动作,还是结束?]
    -> [执行动作 (调用工具、跑代码、做检索)]
    -> [观察结果]
    -> [把结果加进上下文,回到 LLM]
    ... 一直循环直到完成或停下 ...
    -> [最终答案或动作]
```

{{chart: agent-loop}}

组件:

| 组件 | 它干什么 | 例子 |
|---|---|---|
| LLM (大脑) | 每次循环迭代时决定下一步 | Claude、GPT、Gemini |
| 工具 | Agent 能执行的动作 | 搜索、计算器、数据库查询、发邮件 |
| 记忆 | Agent 在循环之间记住的东西 | 对话历史、便签本、检索回来的事实 |
| 编排 | 跑循环并执行限制的代码 | 自定义代码、LangGraph、OpenAI Agents SDK |
| 停止条件 | 循环什么时候结束 | 任务完成、达到最大步数、出错、超时 |

**PM 决策点**

- 这个任务真的需要循环,还是一次 LLM 调用加检索就够?这个判断错了,后面所有决策都偏。
- Agent 在停下来问人之前,最多能跑多少步?这个上限要早定。
- 你打算怎么度量 agent 的表现?完成率不够,还要看每次任务的质量和成本。

**注意事项**

- 客户嘴里说"agent",意思经常是"聊天机器人"。每次都要先把这件事澄清清楚。
- Agent 是复合性失败的: 每一步都有一点错误率,跨步骤相乘,整体可靠性掉得很快。
- 最可靠的 agentic 系统,是步骤最少、工具最受约束的那种。

**要点总结: Agent 是一个带工具的、跑在循环里的 LLM。这个词要用得精确,不然范围一定失控。**

**Qantas 案例**

在 Qantas 内部,"agent"这个词在不同对话里指代差别很大的东西。客服聊天机器人有时被叫 agent。处理入站邮件的固定 pipeline 也被叫 agent。真正自己决定步骤的自主系统也叫 agent。没有精确定义,需求确定的对话就在原地打转。

想想真正的 agent 在 Qantas 哪里能撑起它自身的复杂度。中断恢复是一个强候选场景。重大运营事件 (跑道关闭、重大飞机技术问题、机组短缺) 发生的时候,恢复决策涉及多个数据源 (航班时刻、机组排班、飞机定位、客户名单)、多个约束 (值勤时长、维修、时刻规则)、多个可能的动作 (取消、延误、重新预订、调换、改道)。这些决策的顺序和组合没法预先指定,因为每一步都取决于上一步揭示了什么。

为这种场景设计的 agent,会有一组定义好的工具 (读时刻表、读机组排班、读飞机可用性、读客户名单、模拟拟议变更、起草客户通知)。它会循环,基于"目前为止知道了什么"决定下一个动作。当恢复方案完全成型、等待人工批准的时候,它停下来。

这是一个真正的 agentic 问题。任务的形状没法预先定下来。Agent 做的,本来是一位资深值班经理在脑子里完成的思考。每次任务的成本很高 (多次模型调用、大上下文、贵的旗舰模型),但每次任务的价值也很高 (一份好的恢复方案,在一次重大中断里能省下几十万澳元)。

反过来,Qantas 绝大多数用例不需要 agent。客服查询、内容生成、知识搜索、结构化数据提取,这些都是单次调用或者短 pipeline 的任务,一次基础 LLM 调用加上检索或工具调用就处理得很好。把它们硬塞进 agent 循环里,只会增加成本和不可靠性,没好处。

往大了说,这件事给 AI 交付的启示是: "我们来做个 agent 吧",很少是企业问题的正确答案。正确的问题是: 这个任务是不是真的需要一个决策循环,还是它本来就是一次单次转换,只是团队在赶时髦做过度工程?Agent 只在"路径无法预先指定"的任务上,才赚回它的成本。除此之外,简单的方案更好。把一条单次 pipeline 包装成 agent,并不能让它真的变成 agent。
