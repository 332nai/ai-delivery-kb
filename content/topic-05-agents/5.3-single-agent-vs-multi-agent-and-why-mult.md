**Definition**

A single agent is one LLM running in a loop with a set of tools. A multi agent system has multiple LLM instances, often with different roles (planner, researcher, writer, critic), coordinating to complete a task. Multi agent architectures sound elegant and are widely written about. They are rarely the right choice in production.

**Why it matters in delivery**

Multi agent is the architectural pattern most prone to scope creep, cost blowout, and reliability problems. Clients hear about "agent swarms" or "AutoGPT style systems" and ask for them. PMs who can push back with a clear argument for the simpler architecture save weeks of complexity that delivers nothing the client actually needed.

**How it works**

| Architecture | Description | Strength | Weakness |
|---|---|---|---|
| Single agent | One LLM, one prompt, many tools, one loop | Simple, debuggable, cheaper | Can struggle with very complex multi role tasks |
| Sequential pipeline | One LLM call after another, each with a different prompt | Predictable, easy to evaluate per step | Not really "agentic," just a workflow |
| Multi agent with handoffs | Specialised agents pass control to each other (researcher -> writer -> editor) | Modular, clear roles | Higher cost, complex coordination, hard to debug |
| Hierarchical multi agent | A manager agent delegates to worker agents | Handles complex tasks | Compounding error rates, expensive, slow |

The case for single agent: easier to prompt, easier to eval, lower latency, lower cost, fewer failure modes. The case for multi agent: rare, but real, when sub tasks need very different skills (e.g. code execution vs creative writing) or different model tiers (use cheap model for simple steps, expensive model for hard steps).

**PM decision points**

- Can this be done with one well prompted agent and a clear set of tools?
- If multi agent, is each agent doing genuinely different work, or is the split arbitrary?
- How will we debug when something goes wrong across agent handoffs?

**Watch outs**

- Multi agent papers and demos are not production, most do not survive real workloads
- Coordination overhead grows quickly, three agents is much harder than two
- Cost multiplies, multi agent systems often spend 5 to 10x more tokens than necessary

**Takeaway: default to single agent. Only go multi agent when sub tasks need genuinely different capabilities or models.**

**Qantas story**

In a notional Qantas AI architecture, the temptation toward multi agent systems shows up early. A typical pitch goes: build a researcher agent that gathers data, a planner agent that proposes options, a verifier agent that checks constraints, and an executor agent that drafts the output. It sounds modular and elegant. It is almost always the wrong choice.

Consider the disruption recovery use case from earlier. The naive multi agent design has four specialised agents handing off to each other. In practice, this creates several problems. Coordination overhead grows quickly, with each handoff introducing failure points and context loss. Cost multiplies because each agent has its own LLM calls. Debugging is harder because errors can compound across handoffs and the root cause is not always clear. Latency adds up.

The single agent equivalent does all four roles in one loop, with a structured prompt that walks through research, planning, verification, and execution as phases of the same agent's work. The same model, in the same conversation context, performs all four functions. The result is cheaper, faster, easier to debug, and often higher quality because nothing is lost in handoffs.

The case where multi agent earns its complexity at Qantas would be narrow. One example might be an agent that writes code (using a coding optimised model) handing off to an agent that runs tests (using a faster cheaper model with sandboxed execution). The two agents do genuinely different work with different model requirements, and the split is justified. Even there, the modern approach is often a single agent with role specific tools rather than separate agent instances.

The other case is when the sub problems are genuinely parallel. If an agent needs to research multiple options simultaneously (say, four candidate recovery plans), spawning parallel agent instances each working on one option can be faster than serial processing. The pattern is parallelism, not specialisation.

For AI delivery, the practical lesson is that multi agent architectures are popular in conference talks and rare in successful production systems. The default is single agent with good prompting and a clear tool set. Multi agent gets considered only when there is a specific, measurable reason a single agent cannot do the job, and the team can articulate the trade off (cost, complexity) clearly. Most clients who ask for "an agent swarm" because they read about it somewhere accept a single agent solution once the trade offs are explained.

**定义**

单 agent 是一个 LLM 跑在循环里,带一组工具。多 agent 系统是多个 LLM 实例,通常带不同角色 (规划者、研究员、写手、批评者),协调起来完成一个任务。多 agent 架构听起来优雅,在会议演讲里讨论得也很多。它们在生产环境里很少是正确的选择。

**为何在交付中重要**

多 agent 是最容易导致范围蔓延、成本超支、可靠性问题的架构 pattern。客户听说了"agent 群"或者"AutoGPT 风格系统",就来要求做一个。能用简单架构的清晰论据顶回去的 PM,能为客户省下交付一个他们根本不需要的复杂方案的好几周时间。

**运作原理**

| 架构 | 描述 | 优势 | 劣势 |
|---|---|---|---|
| 单 agent | 一个 LLM、一个 prompt、多个工具、一个循环 | 简单、可调试、更便宜 | 在非常复杂的多角色任务上可能吃力 |
| 顺序 pipeline | 一个 LLM 调用接一个,每个带不同 prompt | 可预测、容易按步骤评估 | 不是真正的"agentic",只是一个工作流 |
| 带切换的多 agent | 专家 agent 互相传递控制权 (研究员 → 写手 → 编辑) | 模块化、角色清晰 | 成本更高、协调复杂、难 debug |
| 分层多 agent | 经理 agent 派活给工人 agent | 能处理复杂任务 | 错误率复合、贵、慢 |

单 agent 的优势是: 更容易写 prompt、更容易做 eval、延迟更低、成本更低、失败模式更少。多 agent 的优势很罕见但真实: 当子任务需要非常不同的能力 (比如代码执行 vs 创意写作),或者不同的模型层级 (简单步骤用便宜模型,困难步骤用贵模型)。

**PM 决策点**

- 这个事情能不能用一个 prompt 写得好的 agent 配一组清晰工具搞定?在动多 agent 之前先回答这个问题。
- 如果决定上多 agent,每个 agent 是不是真的在做不同的工作,还是这个拆分本身就是任意的?
- 出问题的时候,跨 agent 切换的 debug 路径是什么?这件事要在开工前想清楚。

**注意事项**

- 多 agent 的论文和 demo 不是生产。大部分在真实工作负载下活不下来。
- 协调开销增长得很快。三个 agent 比两个 agent 难处理得多,不是线性增长。
- 成本是乘法关系。多 agent 系统经常烧掉的 token 是真实需要的 5 到 10 倍。

**要点总结: 默认走单 agent。只有当子任务需要真正不同的能力或模型时,才考虑多 agent。**

**Qantas 案例**

在假设中的 Qantas AI 架构里,多 agent 的诱惑很早就会冒出来。典型的方案是这样推销的: 建一个收集数据的研究员 agent、一个提出选项的规划者 agent、一个检查约束的验证者 agent、再来一个起草输出的执行者 agent。听起来又模块化又优雅。但这几乎总是错的选择。

回到之前那个中断恢复用例。天真的多 agent 设计是四个专家 agent 互相切换。实际跑起来会带出几个问题。协调开销快速增长,每次切换都引入失败点和上下文损耗。成本变成乘法,因为每个 agent 都有自己的 LLM 调用。Debug 也变难,因为错误能跨切换复合,根因并不总能立刻看清。延迟也是层层叠加。

等价的单 agent 方案是: 在一个循环里完成全部四个角色,用一个结构化的 prompt 把研究、规划、验证、执行作为同一 agent 工作的不同阶段串起来。同一个模型、同一个对话上下文,执行全部四个功能。结果更便宜、更快、更容易 debug,而且经常质量还更高——因为切换中间什么都没丢。

多 agent 在 Qantas 真正能撑起自身复杂度的场景是很窄的。一个例子可能是: 一个写代码的 agent (用编码优化的模型) 切换给一个跑测试的 agent (用更快更便宜的模型,带沙箱执行)。这两个 agent 用不同的模型做真正不同的工作,拆开是说得通的。但即便在这个场景下,现代做法通常也是"单 agent 配上角色特定的工具",而不是真的去开多个 agent 实例。

另一个真正的场景是子问题天然并行。如果一个 agent 需要同时研究多个选项 (比如四个候选恢复方案),并行开多个 agent 实例、每个负责一个选项,确实比串行处理更快。但这里的 pattern 是"并行",不是"专业化"。

往大了说,这件事给 AI 交付的启示是: 多 agent 架构在会议演讲里很受欢迎,在成功的生产系统里很罕见。默认走"prompt 写得好的单 agent + 清晰的工具集"。只有当存在一个具体的、可度量的理由,证明单 agent 做不了这件事,而且团队能把取舍 (成本、复杂度) 说清楚的时候,才考虑多 agent。大多数因为"在哪儿读到了"就来要求做"agent 群"的客户,在你把取舍解释清楚之后,都会接受单 agent 方案。
