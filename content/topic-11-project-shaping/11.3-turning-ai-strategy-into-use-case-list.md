**Definition**

Clients often buy "AI strategy" as the first phase of an engagement, but neither the SOW nor the client usually defines what the artifact looks like. The job in the first two to three weeks is to convert the abstract noun "strategy" into a concrete, prioritised list of use cases, each with enough specificity that a delivery team could start work on Monday.

**Why it matters in delivery**

A strategy phase that ends without a concrete use case list is a strategy phase that does not justify its fee. The client cannot act on it, the delivery team cannot estimate against it, and the next phase will start with the same ambiguity it should have removed. In AI specifically, vagueness is expensive: every "we should use AI for customer service" can mean six different products with six different cost profiles and six different risk levels. Forcing the conversation down to use case level is what makes the next phase fundable.

**How it works**

A working use case is a row in a table with the following columns. If any column is empty, the use case is not ready.

| Column | What goes in it | Why it matters |
|---|---|---|
| Use case name | One line, plain English | Forces clarity, kills jargon |
| User and trigger | Who is using it, what makes them open it | Reveals if there is a real user |
| Today's path | How is this done today, without AI | Defines the baseline to beat |
| AI pattern | RAG, agent, summarisation, classification, generation | Tells you cost and complexity |
| Value hypothesis | Hours saved, revenue lifted, errors reduced, in a number | Tells you if it is worth doing |
| Hardest input | The thing that, if missing, kills the use case | Surfaces the real risk |
| Owner | One name on the client side who would champion this | Tests whether anyone actually wants it |

The discipline is filling in every cell. The hardest cells are usually "value hypothesis" (clients resist quantifying) and "owner" (use cases that nobody owns are usually use cases nobody really wants).

**How to generate the candidate list**

The team typically starts with a long list of 30 to 50 candidate use cases, sourced from a mix of:

- Workshops with the operating teams, structured around their daily pain
- Existing client documents (digital strategy decks, backlog items, customer complaint themes)
- A walk through the value chain, asking at each step "where does information move slowly or imperfectly"
- An external scan of what similar companies are doing publicly
- The team's own pattern library (the use cases that have worked in adjacent industries)

Then the list is collapsed through filters:

1. *Is the user real and identified?* Drop the ones that exist only in a strategy deck.
2. *Is there data to support it, or can data be obtained within the engagement?* Drop the ones that need data the client cannot get.
3. *Does AI actually help, or is this better solved by RPA, a SQL view, or a phone call?* Drop the ones where AI is the wrong tool.
4. *Is the value hypothesis defensible to a CFO?* Drop the ones that survive only on vibes.

A list of 30 candidates typically reduces to 8 to 12 viable use cases.

**Prioritisation**

A 2x2 still works, despite its consulting cliche status: value on one axis, feasibility on the other. The interesting move is putting *time to first user value* as the feasibility axis, not *technical complexity*. Some technically complex use cases reach users faster than technically simple ones because of data availability, change management, or political alignment.

The output of prioritisation is a tiered list:

- **Tier 1 (build in next phase):** 2 to 4 use cases, high value, near term feasibility
- **Tier 2 (build in subsequent phase):** 3 to 5 use cases, conditional on tier 1 learnings
- **Tier 3 (parked):** the rest, with a documented reason for each

**PM decision points**

- Have I forced every use case to a single sentence, or am I allowing paragraphs?
- For tier 1, can I name the human user, and can they name me back?
- Is the value hypothesis specific enough that the CFO would read it without rolling their eyes?

**Watch outs**

- Use cases that are exciting in workshop and boring in production are common. Filter for "do users actually open this on a Tuesday morning".
- Watch for use cases that are really features of an existing product, not standalone use cases. Sometimes the right answer is "this is a feature request for SAP, not an AI project".
- A use case that the executive sponsor loves but no operating manager will champion is a use case that fails on day 30 of building.

**Takeaway: AI strategy is a deliverable only when it ends in a prioritised use case list, where each row has a real user, a real data source, and a real owner. Anything less is decoration.**

**Qantas story**

Imagine being asked to lead a six week AI strategy phase for Qantas Group, brief framed as "identify where generative AI can create most value across our customer and operational journeys". The fee is good. The expectation is a thoughtful deck. The temptation is to produce a beautiful narrative arc with five themes and twenty principles.

The discipline is to do the narrative arc *and* the use case list. The deck without the list is a thought piece. The list without the deck does not get funded. Both are needed.

The team runs eight workshops across customer service, frequent flyer, operations, revenue management, ground operations, freight, and corporate functions. The raw output is 47 candidate use cases. Some are obviously real: assisting customer service agents with policy lookups, automating disruption communications, summarising long passenger feedback. Some are obviously not: "AI to predict pilot fatigue from social media" survives the workshop because someone is enthusiastic, but does not survive the filter for "do we have the data and would we ever deploy this".

The filter passes reduce the 47 to about 12. The 12 fit into a tiered list. Tier 1 contains three: an agent assist tool for customer service, a disruption communication drafter for the operations control centre, and a corporate FAQ assistant for internal employees. Each of the three has a named operating sponsor, a defined data source, a value hypothesis in dollars or hours, and a hardest input that has been surfaced and discussed.

The interesting moment is in the readout to the executive committee. The CFO does not engage with the thematic narrative slides. The CFO engages, hard, with the value hypothesis column of the tier 1 table. Two of the three numbers get challenged. One gets revised down. One gets defended successfully. The third, the FAQ assistant, gets challenged on whether the value justifies the effort, and the team agrees to descope it into a smaller pilot rather than a full build.

That conversation, between the CFO and the team's numbers, is what justifies the next phase fee. Without the use case table, the conversation would have been about whether the deck was "interesting", which is a much weaker basis for funding.

The lesson for AI delivery is that strategy work in AI is only useful insofar as it produces something buildable. The role of the strategy phase is to do the hard work of converting executive ambition into a list a delivery team can act on. If that list does not exist at the end, the strategy did not happen.

**定义**

客户经常会把 "AI 战略" 作为合作的第一阶段买下来, 但 SOW 和客户自己通常都没定义这个交付物长什么样。前两到三周的工作就是把抽象名词 "战略" 转化成一份**具体的、排过优先级的 use case 清单**, 每一条都具体到让一个交付团队周一就能开工。

**为何在交付中重要**

一个**没以具体 use case 清单结尾**的战略阶段, 是一个对不起自己费率的战略阶段。客户不能据此行动, 交付团队不能据此估算, 下一阶段会从这一阶段本应消除的模糊里重新开始。AI 领域这一点尤其严重: 每一个 "我们应该用 AI 做客服" 都可以指代六种不同的产品, 六种不同的成本结构, 六种不同的风险等级。**把对话压到 use case 这一层**, 是让下一阶段拿到预算的前提。

**运作原理**

一条可用的 use case 是表格里的一行, 包含下面这些列。**任何一列空着, 这条 use case 就还没准备好**。

| 列 | 该填什么 | 为什么重要 |
|---|---|---|
| Use case 名称 | 一行, 大白话 | 强制清晰, 杀死 jargon |
| 用户和触发 | 谁在用、什么时候打开它 | 揭示是否真的有用户 |
| 今天怎么做 | 没有 AI 的情况下今天怎么做这件事 | 定义要打败的 baseline |
| AI pattern | RAG、agent、摘要、分类、生成 | 告诉你成本和复杂度 |
| 价值假设 | 节省多少小时、提升多少收入、减少多少错误, 用数字 | 告诉你值不值得做 |
| 最难的输入 | 缺了它这个 use case 就死的那个东西 | 暴露真实风险 |
| Owner | 客户侧愿意推动这件事的一个具体人名 | 测试有没有人**真的想要** |

纪律是**每一格都要填**。最难填的两格通常是**价值假设** (客户抗拒量化) 和 **owner** (没有 owner 的 use case 通常是**没有人真的想要**的 use case)。

**怎么生成候选清单**

团队通常会从一份 30 到 50 条候选 use case 的长清单开始, 来源混合:

- 跟一线运营团队的 workshop, 围绕他们日常的痛点
- 客户已有的文档 (数字化战略 deck、积压的 backlog、客户投诉主题)
- 沿着价值链走一遍, 在每一步问 "信息在哪里**流动得慢或不准确**"
- 看外部相似公司公开在做什么
- 团队自己的 pattern 库 (在邻近行业跑通过的那些 use case)

然后用过滤器把清单收缩:

1. *用户是真实的、有名字的吗?* 砍掉只活在战略 deck 里的那些。
2. *支持它的数据存在吗, 或能在本次合作期内拿到吗?* 砍掉数据拿不到的那些。
3. *AI 真的能帮上忙吗, 还是 RPA、一个 SQL view、或者打个电话就能解决?* 砍掉**用错工具**的那些。
4. *价值假设能在 CFO 面前站住吗?* 砍掉**只靠氛围撑着**的那些。

30 条候选通常会收缩到 8 到 12 条可用 use case。

**优先级排序**

2x2 矩阵虽然是咨询陈词滥调, 但仍然管用: 一个轴是价值, 另一个轴是可行性。**有意思的一招是**: 把 "到达第一个用户价值的时间" 作为可行性轴, 而不是技术复杂度。有些技术上复杂的 use case 反而比技术上简单的更快到达用户, 原因是数据可用、变更管理顺利、或者政治上对齐。

排序的输出是一份分层清单:

- **第一档 (下一阶段建):** 2 到 4 条, 高价值、近期可行
- **第二档 (再下一阶段建):** 3 到 5 条, 取决于第一档的学习
- **第三档 (搁置):** 剩下的, 每条都写明搁置的具体原因

**PM 决策点**

- 我有没有强制每条 use case 压到一句话, 还是允许它们写成段落?
- 第一档里, 我能不能说出**真实用户**的名字, 他们也能不能说出**我的**名字?
- 价值假设具体到 CFO 读了不会翻白眼的程度了吗?

**注意事项**

- "Workshop 上很激动, 生产上很无聊" 的 use case 很常见。**用 "用户在周二早上真的会打开它吗" 来过滤**。
- 警惕那些其实是**已有产品的一个 feature** 而不是独立 use case 的东西。有时候正确答案是 "这是给 SAP 的一个 feature request, 不是 AI 项目"。
- **高管 sponsor 喜欢但没有运营经理愿意推动**的 use case, 是建到第 30 天就会死掉的 use case。

**要点总结: AI 战略只有在结尾产出一份排过优先级的 use case 清单时, 才算交付物。每一行要有真实用户、真实数据源、真实 owner。少于这个, 都是装饰。**

**Qantas 案例**

设想你被要求带一个 Qantas Group 的六周 AI 战略阶段, 命题是 "在我们的客户和运营旅程中, 识别生成式 AI 能产生最大价值的地方"。费率不错。期待是一份**深思熟虑的 deck**。诱惑是产出一份漂亮的叙事弧线, 五个主题、二十条原则。

纪律是**叙事弧线和 use case 清单都要做**。**没有清单的 deck 是思想品**, 拿不到下一阶段预算。**没有 deck 的清单**又不容易被高管理解。两个都需要。

团队跑了八场 workshop, 覆盖客服、frequent flyer、运营、收益管理、地面运营、货运、企业职能。原始产出是 47 条候选 use case。有些显然是真实的: 帮客服 agent 查政策、自动化中断通讯、把长篇乘客反馈做摘要。有些显然不是: "用 AI 从社交媒体预测飞行员疲劳" 在 workshop 上活下来, 是因为有人很热情, 但在 "我们有数据吗, 我们真的会部署这个吗" 的过滤器面前活不过去。

过滤几遍, 47 收缩到大约 12 条。12 条分成分层清单。**第一档三条**: 给客服的 agent assist 工具、给运营控制中心的中断通讯起草器、给内部员工的企业 FAQ 助手。这三条每一条都有一个**具名的运营 sponsor**、**定义清楚的数据源**、**用美元或小时表达的价值假设**, 以及一个**已经被识别和讨论过的最难输入**。

有意思的瞬间出现在向 executive committee 汇报时。CFO 不接茬主题叙事的 slide。CFO 在第一档表格的**价值假设那一列**上较真。三个数字里有两个被挑战。一个被往下调了。一个被成功辩护。第三个 (FAQ 助手) 被挑战 "这个价值值不值得这么大投入", 团队当场同意把它降级成一个更小的 pilot, 而不是完整 build。

**那场对话, 也就是 CFO 跟团队的数字之间的那场对话, 才是支撑下一阶段费率的东西**。没有这张 use case 表, 对话只会变成 "这份 deck 有没有意思", 那是一个弱得多的拿预算依据。

AI 交付的启示: AI 领域的战略工作, **只有当它产出可以建的东西时才有用**。战略阶段的角色是把高管的雄心翻译成一份**交付团队可以照着做的清单**。如果结尾这份清单不存在, 那这个战略阶段没真的发生过。
