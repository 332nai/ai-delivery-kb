**Definition**

Every interaction with an LLM has three message roles. The system prompt sets the model's persona, rules, and constraints, and is usually invisible to the end user. The user prompt is what the end user types. The assistant prompt is what the model produces, which becomes part of the conversation history on the next turn.

**Why it matters in delivery**

Most production AI products live or die by the quality of the system prompt. It is the part the PM and the team have the most control over, and it is where consistency, brand voice, safety rules, and task structure are enforced. Teams that treat the system prompt as an afterthought ship products that behave differently across users and break under edge cases.

**How it works**

| Role | Set by | Purpose | Typical length |
|---|---|---|---|
| System | Product team | Persona, rules, format, tools, refusal policy | 200 to 2,000+ tokens |
| User | End user | The actual question or instruction | Variable, often short |
| Assistant | Model | The response, plus tool calls if any | Variable |

The model treats the system prompt as the highest priority instruction set, but not as absolute. A well crafted user message can still override weak system prompts, which is the basis of most prompt injection attacks.

A typical structure for a strong system prompt:

1. Role and identity ("You are a customer support agent for an Australian bank")
2. Capabilities and tools ("You have access to account lookup and transaction search")
3. Behaviour rules ("Always verify identity before sharing account details")
4. Output format ("Respond in plain text, no markdown")
5. Refusal policy ("If asked about products outside banking, redirect politely")
6. Examples (1 to 3 representative interactions)

**PM decision points**

- Who owns the system prompt, and where is the canonical version stored?
- How are changes tested and versioned, and who can deploy a change?
- Is the system prompt long enough to cover edge cases, or so long it crowds the context window?

**Watch outs**

- A system prompt is not a security boundary, users can sometimes extract it or override it
- Long system prompts eat context budget, every word competes with user input and retrieved docs
- "Just tell it to be helpful" produces unpredictable behaviour, always be specific

**Takeaway: the system prompt is the product. Treat it as code, version it, test it, review changes.**

**Qantas story**

Consider what a high quality system prompt for a Qantas customer service AI assistant might look like. The naive version, of the sort that often ships in first prototypes, says something like "You are a helpful customer service assistant for Qantas Airways. Answer customer questions politely and accurately." Forty words, almost no useful constraint.

A production grade system prompt for the same use case runs 1,500 to 2,500 words and covers a long list of specific behaviours. Identity and brand voice (warm but efficient, never overly familiar, never apologising excessively in line with the Qantas service philosophy). Boundaries (you can answer questions about Qantas flights, frequent flyer, baggage, and check in; you cannot discuss codeshare partner internal policies, cannot quote fares not in the current system, cannot make commitments about goodwill compensation). Tools available (booking lookup, frequent flyer balance, schedule check, disruption status). Verification requirements (always confirm passenger identity before sharing booking details, never volunteer information about other passengers on the same booking). Refusal patterns (when asked about competitor airlines, redirect; when asked about industrial action or operational incidents, defer to media statements; when asked anything outside scope, hand off to a human gracefully). Output format (plain text for chat, structured fields for tool inputs, no markdown in customer facing responses).

The reason this length is necessary is that each rule typically comes from a specific incident or a policy team requirement. The brand team wants the voice constraint. Legal wants the refusal patterns around industrial action. Privacy wants the verification requirements. Frequent Flyer wants the boundary around codeshare partner policies. Each constituency adds a rule, and over time the prompt grows.

The interesting management challenge is that this system prompt becomes a living document with multiple stakeholders. Changes need review. Versions need testing. Regressions need rollback. The prompt becomes a piece of production code with the operational discipline that implies.

For AI delivery, the lesson is that "the AI is the model" is wrong. The AI is the system prompt plus the model plus the retrieval plus the tools. The system prompt is where most of the product specification actually lives. Treating it casually is the single most common cause of inconsistent AI product behaviour. Treating it like code, with version control, review, and testing, is how mature teams operate.

**定义**

每次与 LLM 的互动都有三种消息角色。System prompt 设置模型的角色、规则和约束,通常对最终用户不可见。User prompt 是最终用户输入的内容。Assistant prompt 是模型产生的内容,在下一轮变成对话历史的一部分。

**为何在交付中重要**

大多数生产 AI 产品的成败取决于 system prompt 的质量。它是 PM 和团队控制最多的部分,也是一致性、品牌声音、安全规则和任务结构得到执行的地方。把 system prompt 当作事后想法的团队发布的产品在不同用户之间行为不同,并在边缘情况下崩溃。

**运作原理**

| 角色 | 由谁设置 | 目的 | 典型长度 |
|---|---|---|---|
| System | 产品团队 | 角色、规则、格式、工具、拒绝政策 | 200 到 2,000+ tokens |
| User | 最终用户 | 实际的问题或指令 | 可变,通常短 |
| Assistant | 模型 | 回应,如果有工具调用也包括 | 可变 |

模型将 system prompt 视为最高优先级的指令集,但不是绝对的。精心制作的用户消息仍然可以覆盖弱 system prompt,这是大多数 prompt 注入攻击的基础。

一个强 system prompt 的典型结构:

1. 角色和身份 ("你是一家澳大利亚银行的客户支持代理")
2. 能力和工具 ("你有权访问账户查询和交易搜索")
3. 行为规则 ("在分享账户详情之前总是验证身份")
4. 输出格式 ("用纯文本回应,无 markdown")
5. 拒绝政策 ("如果被问到银行业以外的产品,礼貌地重新引导")
6. 示例 (1 到 3 个有代表性的互动)

**PM 决策点**

- 谁拥有 system prompt,规范版本存储在哪里?
- 变更如何测试和版本化,谁可以部署变更?
- system prompt 是否足够长以覆盖边缘情况,或者长到挤占上下文窗口?

**注意事项**

- system prompt 不是安全边界,用户有时可以提取或覆盖它
- 长 system prompts 消耗上下文预算,每个词都与用户输入和检索的文档竞争
- "就告诉它要有帮助"产生不可预测的行为,总是要具体

**要点总结: system prompt 就是产品。把它当作代码,版本化它,测试它,审查变更。**

**Qantas 案例**

考虑 Qantas 客户服务 AI 助手的高质量 system prompt 会是什么样子。在第一个原型中通常发布的天真版本说类似这样的话: "你是 Qantas Airways 的有帮助的客户服务助手。礼貌、准确地回答客户问题。"四十个字,几乎没有有用的约束。

同一用例的生产级 system prompt 长 1,500 到 2,500 字,涵盖一长串具体行为。身份和品牌声音 (温暖但高效,从不过度亲密,从不按照 Qantas 服务哲学过度道歉)。边界 (你可以回答关于 Qantas 航班、frequent flyer、行李和值机的问题; 你不能讨论代码共享伙伴内部政策、不能引用当前系统中没有的票价、不能就善意补偿做出承诺)。可用工具 (预订查询、frequent flyer 余额、时刻表检查、中断状态)。验证要求 (在分享预订详情之前总是确认乘客身份,从不主动透露同一预订上其他乘客的信息)。拒绝模式 (当被问到竞争对手航空公司时,重新引导; 当被问到工业行动或运营事件时,推迟到媒体声明; 当被问到任何范围之外的内容时,优雅地转交人工)。输出格式 (聊天用纯文本,工具输入用结构化字段,面向客户的响应中无 markdown)。

这种长度必要的原因是每条规则通常来自特定事件或政策团队要求。品牌团队想要声音约束。法务想要工业行动周围的拒绝模式。隐私想要验证要求。Frequent Flyer 想要代码共享伙伴政策周围的边界。每个选区添加一条规则,随着时间推移,prompt 增长。

有趣的管理挑战是这个 system prompt 变成一个有多个利益相关者的活文档。变更需要审查。版本需要测试。回归需要回滚。该 prompt 变成生产代码,带有这暗示的运营纪律。

对 AI 交付来说,启示是"AI 就是模型"是错误的。AI 是 system prompt 加模型加检索加工具。system prompt 是大部分产品规范实际存在的地方。随便对待它是 AI 产品行为不一致的最常见的单一原因。把它当作代码对待,带版本控制、审查和测试,是成熟团队的运作方式。
