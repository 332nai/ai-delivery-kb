**Definition**

Structured output is the practice of forcing the model to produce output in a predictable machine readable format, usually JSON, but also XML, YAML, or custom formats. Most providers now offer native modes (JSON mode, structured outputs, response format) that constrain generation to a defined schema.

**Why it matters in delivery**

Any AI system that feeds another system needs structured output. A chatbot that talks to humans can ramble. A pipeline that extracts data from invoices and writes to a database cannot. The single biggest cause of "the AI works but the integration is flaky" is unstructured or inconsistently structured output, and the fix is almost always at the prompting and schema layer.

**How it works**

| Method | Reliability | Effort | Use when |
|---|---|---|---|
| "Respond in JSON" in prompt | Low, frequent format errors | Trivial | Prototypes only |
| JSON mode (provider flag) | Medium, valid JSON but flexible structure | Low | Loose structure is fine |
| Structured output with schema | High, guaranteed to match schema | Medium | Production pipelines |
| Function calling / tool use | High, schema enforced | Medium | Output goes to a tool or API |
| Pydantic or Zod validators | High, runtime validation | Medium | Adds a safety net |

Native structured output works by constraining the model's token sampling at generation time, so invalid tokens (e.g. a letter where a number is required) are mathematically blocked. This is far more reliable than asking nicely in the prompt.

**Worked example**

Without schema: "Extract the customer name and order total from this email as JSON."

Result: sometimes `{"name": "...", "total": "$45.00"}`, sometimes `{"customer_name": "...", "order_total": 45}`, sometimes valid JSON wrapped in markdown code fences.

With schema enforced:

```
{
  "type": "object",
  "properties": {
    "customer_name": {"type": "string"},
    "order_total_aud": {"type": "number"}
  },
  "required": ["customer_name", "order_total_aud"]
}
```

Result: always matches exactly, every time.

**PM decision points**

- Is the output consumed by a human or a system? If a system, structured output is non negotiable
- Does the provider support native structured output, or does the team need to add a validation layer?
- How does the system handle schema violations, retry, fallback, or fail?

**Watch outs**

- Strict schemas can cause the model to lie to satisfy the schema, e.g. inventing a field value rather than returning null
- Very deep nested schemas degrade quality, keep schemas flat where possible
- Some providers charge for the schema as input tokens, factor into cost

**Takeaway: structured output is the bridge between AI and the rest of the stack. Use native schema modes, never rely on the prompt alone.**

**Qantas story**

Within Qantas's operational systems, structured output is everywhere. Booking systems, frequent flyer engines, customer service platforms, revenue management tools, and crew scheduling all run on rigidly structured data. Any AI integration into these systems must produce output that conforms to existing schemas, or the integration fails at the boundary.

Imagine an AI assistant that extracts structured fields from inbound customer service emails (passenger name, booking reference, travel dates, nature of request, urgency, suggested response category). The downstream system expects a strict JSON schema with specific field names, specific types, and specific enumerated values for the request category. There is no flexibility. A schema violation breaks the workflow.

The naive approach of "respond in JSON" in the prompt produces output that is JSON shaped maybe 95 percent of the time. The other 5 percent might have markdown code fences, extra commentary, slightly different field names, or values that look right but are not in the enumerated list. At Qantas inbound email volumes, that 5 percent failure rate represents thousands of broken records per day, each one requiring manual handling.

Switching to native structured output with a strict schema solves this. The model is mathematically constrained to produce output that matches the schema. Field names are exact. Types are correct. Enumerated values are from the allowed list. Parse failures drop to essentially zero.

The interesting design question is what happens when the email content does not cleanly map to the schema. A naive approach forces the model to fill in fields anyway, which leads to fabricated values. A better design has every field allow a null value plus a confidence indicator, and routes low confidence extractions to human review. The schema accommodates uncertainty instead of forcing the model to lie.

For AI delivery, the broader insight is that structured output is the bridge between AI and the enterprise systems that already exist. Most large Australian enterprises do not need AI that talks to humans, they need AI that talks to their existing platforms. The technical foundation for that is rigorous schema design, native structured output modes, and graceful handling of cases where the input does not cleanly fit the schema. Teams that treat this as an afterthought build integrations that look great in demos and fail in production. Teams that treat it as a first principle ship reliable systems.

**定义**

结构化输出是一种实践: 强制模型按照可预测的、机器可读的格式产出 (通常是 JSON,也有 XML、YAML 或自定义格式)。大部分厂商现在都提供原生模式 (JSON mode、structured output、response format),把生成约束在一个定义好的 schema 上。

**为何在交付中重要**

任何要把数据喂给下游系统的 AI 系统,都需要结构化输出。跟人对话的聊天机器人可以漫谈,但从发票里提取数据写进数据库的 pipeline 不行。"AI 本身没问题,集成层一直在抖"这件事的最大单一原因,就是输出没结构化或者结构不一致,修复几乎都在 prompting 和 schema 这两层。

**运作原理**

| 方法 | 可靠性 | 工作量 | 什么时候用 |
|---|---|---|---|
| Prompt 里写"用 JSON 回应" | 低,经常格式错 | 微乎其微 | 只在原型阶段 |
| JSON mode (厂商开关) | 中,JSON 有效但结构灵活 | 低 | 结构松散可以接受 |
| 带 schema 的结构化输出 | 高,保证匹配 schema | 中 | 生产 pipeline |
| Function calling / tool use | 高,schema 强制 | 中 | 输出要流到工具或 API |
| Pydantic 或 Zod 校验器 | 高,运行时校验 | 中 | 加一道安全网 |

原生结构化输出的工作方式,是在生成的时候直接约束模型的 token 采样过程: 无效的 token (比如本来该是数字的位置出现了字母) 在数学上直接就被挡掉了。这比在 prompt 里礼貌地请求模型"请输出 JSON"可靠得多。

**举例说明**

无 schema: "从这封邮件里提取客户名和订单金额,用 JSON 输出。"

结果: 有时候是 `{"name": "...", "total": "$45.00"}`,有时候是 `{"customer_name": "...", "order_total": 45}`,有时候是 JSON 但被包在 markdown 代码块里。

强制 schema:

```
{
  "type": "object",
  "properties": {
    "customer_name": {"type": "string"},
    "order_total_aud": {"type": "number"}
  },
  "required": ["customer_name", "order_total_aud"]
}
```

结果: 每次都精确匹配,每次都一样。

**PM 决策点**

- 输出是给人看的还是给系统消费的?如果是给系统,结构化输出是没得谈的硬要求。
- 厂商有没有原生结构化输出?如果没有,团队要加一层校验逻辑。
- Schema 违规时系统怎么处理?重试、回退、还是直接失败?这条路径要明确。

**注意事项**

- 严格的 schema 可能会让模型"为了满足 schema 而编造"——比如本来该是 null 的字段,模型硬填一个值。这两件事是绑在一起的。
- 嵌套太深的 schema 会降低质量。能扁平就尽量扁平。
- 有些厂商把 schema 本身按输入 token 计费,这部分成本要算进去。

**要点总结: 结构化输出是 AI 跟整个技术栈剩下部分之间的桥梁。用原生 schema 模式,永远不要只靠 prompt 撑着。**

**Qantas 案例**

在 Qantas 的运营系统内部,结构化输出无处不在。订单系统、Frequent Flyer 引擎、客服平台、收益管理工具、机组排班,全都跑在严格结构化的数据之上。任何 AI 跟这些系统的集成,产出的输出必须符合现有的 schema,否则集成在边界上就崩了。

设想一个 AI 助手,要从进来的客服邮件里提取结构化字段 (乘客姓名、订单参考号、行程日期、诉求性质、紧急程度、建议的回应类目)。下游系统期望的是一份严格的 JSON schema: 特定的字段名、特定的类型、诉求类目要在枚举值清单里。没有任何灵活性。一次 schema 违规,工作流就断了。

天真的做法是在 prompt 里写"请用 JSON 回应"。这种方式产出的东西,大概 95% 的时候长得像 JSON。剩下 5% 可能带着 markdown 代码块、加了一段评论、字段名稍微变了、或者值看起来对但不在枚举清单里。在 Qantas 的入站邮件量下,5% 的失败率意味着每天几千条破损记录,每一条都要人工处理。

切换到带严格 schema 的原生结构化输出之后,这个问题解决了。模型在数学层面被约束,产出的输出一定匹配 schema。字段名精确,类型正确,枚举值一定来自允许的清单。解析失败基本掉到零。

有意思的设计问题是: 如果邮件内容本来就没法干净地映射到 schema 怎么办? 天真的做法是强迫模型无论如何都填上,结果就是字段值被编造出来。更好的设计是: 让每个字段都允许 null,再加一个置信度指示器,把低置信度的提取送去人工审核。Schema 应该容纳不确定性,而不是逼模型撒谎。

往大了说,这件事给 AI 交付的启示是: 结构化输出是 AI 跟已有企业系统之间的桥梁。大部分澳洲大型企业,需要的不是跟人聊天的 AI,而是能跟现有平台对话的 AI。技术上的基础就是严谨的 schema 设计、原生的结构化输出模式、以及对"输入没法干净适配 schema"那种情况的优雅处理。把这件事当成事后再说的团队,做出来的集成在 demo 里看着很漂亮,在生产里崩。把它当成首要原则的团队,发出来的系统才可靠。
