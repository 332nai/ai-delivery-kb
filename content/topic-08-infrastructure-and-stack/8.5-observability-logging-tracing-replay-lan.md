**Definition**

Observability in AI systems is the ability to see what happened inside every interaction: the exact prompt sent, the retrieved chunks, the tool calls made, the model output, the cost, the latency, and the user feedback. Tools like Langfuse, Helicone, Arize, and LangSmith specialise in this for LLM workloads. Generic observability tools (Datadog, Honeycomb) can be configured to do it but require more setup.

**Why it matters in delivery**

Without observability, debugging an AI system is guesswork. When a user complains about a bad answer, you cannot reproduce it, cannot see what went wrong, and cannot prove it is fixed. With observability, debugging takes minutes instead of days, evals can be built from real traffic, and cost can be controlled. It is the single most under invested layer in most AI projects.

**How it works**

| What to capture | Why | Tool support |
|---|---|---|
| Full prompt and response | Reproduce and debug any interaction | All major tools |
| Tool calls and results | Understand agent decisions | Langfuse, LangSmith |
| Retrieval results | Debug RAG quality | Langfuse, Arize, custom |
| Latency per step | Find slow components | All major tools |
| Token counts and cost | Track unit economics | Langfuse, Helicone, Datadog |
| User feedback (thumbs, ratings) | Connect quality to specific interactions | Langfuse, LangSmith |
| Eval scores | Track quality over time | Langfuse, Arize |
| Replay capability | Run an exact past interaction with a new prompt or model | Langfuse, LangSmith |

A typical observability setup wraps every LLM call with a trace that captures all of the above, then exposes it in a dashboard for the team. Mature setups also export to analytics tools for cost forecasting and to eval pipelines for quality monitoring.

**PM decision points**

- Is observability instrumented from day one, not bolted on after launch?
- Can the team replay any production interaction with a different prompt or model?
- Are cost and quality dashboards reviewed weekly, or only when something breaks?

**Watch outs**

- Logging prompts and responses raises privacy and compliance issues, design for redaction
- Observability adds latency if synchronous, batch and stream where possible
- Self built observability is a tempting time sink, use existing tools unless you have a very specific need

**Takeaway: observability is not a nice to have. It is how you debug, how you build evals, and how you control cost. Build it from day one.**

**Qantas story**

Observability is the layer Qantas, or any enterprise, would discover the importance of the hard way the first time a production AI incident happens and the team cannot figure out what went wrong.

Consider a hypothetical Qantas frequent flyer assistant after a few months in production. A senior member complains that the AI told them they had 250,000 points when they actually had 25,000. The complaint reaches the team. The first question is what happened. Without observability, the team can guess: maybe a retrieval error, maybe a model hallucination, maybe a tool integration bug. With observability, the team pulls the exact trace of the interaction in two minutes.

The trace shows the system prompt that was active at the time, the user query, the tool call that was made (a member balance lookup), the response from the tool (which correctly returned 25,000 points), and the model output (which incorrectly said 250,000 points). The model had ignored the tool response and hallucinated a different number. Root cause identified in five minutes. Mitigation: add a deterministic check that the response's point figures match the tool response, and refuse to send if they do not. Deployed within a day.

Without that observability, the team would have spent days trying to reproduce, would have built false hypotheses, and would have left the member with a vague apology and no fix. With it, the team identified the issue, fixed it, and could explain to the member exactly what happened.

The other use of observability is cost analysis. A team running an internal agent for research support discovers their monthly bill is much higher than forecast. With observability, the team filters by task and finds that 70 percent of cost is from a small number of tasks that ran 30+ agent steps each. They identify the pattern, add stricter step limits, and cut cost by 60 percent. Without observability, the same investigation would have been guesswork against aggregate billing data.

The observability stack at Qantas scale needs to capture full prompts, full responses, all tool calls and their results, retrieval queries and returned chunks, token counts and cost per call, latency per step, and user feedback when available. Tools like Langfuse, Helicone, and LangSmith specialise in this. Generic observability tools like Datadog can be configured to do it with more setup. Either way, the investment needs to happen from day one.

The interesting privacy consideration is that observability captures prompts and responses, which often contain PII. The observability layer needs its own redaction discipline, its own access controls, and its own retention policies. This is not a security afterthought, it is part of the design.

For AI delivery, the lesson is that observability is the single most underinvested layer of most enterprise AI projects, and it is the layer that determines whether the team can debug, optimise, and improve over time. Building it in from day one is dramatically easier than adding it after launch. Clients who have shipped AI without observability previously understand this immediately. Clients who have not, sometimes need to see the consequence of running blind for a few weeks to internalise the value.

**定义**

可观察性是看到生产中实际发生什么的能力。对于 AI 系统,这意味着每个 LLM 调用的 prompts、completions、token 数、延迟、成本、错误、工具调用,以及多步工作流的完整执行痕迹。没有可观察性,生产 AI 是一个有时返回错误答案的黑盒子。

**为何在交付中重要**

可观察性是 AI 项目中差异化人员的最常见地方。每个团队都说"我们将监控它"。少数人实际上为它构建。当事件袭击 (它们会袭击) 时,具有真实可观察性的团队在分钟内找到原因。没有它的团队在天内找到原因,失去客户信任。可观察性不是奢侈品,它是 AI 在企业中的运营成熟度。

**运作原理**

| 信号 | 什么 | 为什么 |
|---|---|---|
| 完整 prompt 和 completion 日志 | 每个 LLM 调用,逐字 | 调试,审计,质量审查 |
| Token 计数 | 每个调用的输入和输出 tokens | 成本归因,容量规划 |
| 延迟分解 | 每步的时间 (检索,模型,工具) | 性能优化 |
| 错误和重试 | 失败,重试,最终结果 | 可靠性跟踪 |
| 工具调用痕迹 | 调用了什么工具,有什么输入,有什么输出 | Agent 调试 |
| 用户上下文 | 用户 ID (脱敏),会话,功能标志 | 范围调查 |
| 评估分数 | 在线评分 (用户反馈,自动检查) | 质量趋势 |
| 模型置信度 | 在可用时,token logprobs | 难度检测 |

工具选项: 开源 (Langfuse, OpenTelemetry, Phoenix) 和托管 SaaS (Datadog with LLM observability, Helicone, Braintrust)。许多团队从托管供应商开始,因为速度。

对 prompts 和 completions 的访问需要谨慎设计。它有时是 PII (用户在与 AI 共享个人数据)。它有时是商业敏感的 (Qantas 客户记录,内部文档)。日志保留,访问控制和 PII 编辑需要从一开始就设计。

**PM 决策点**

- 我们今天捕获哪些信号,什么是空白?
- 谁可以查看日志,以什么级别的细节,以多长时间?
- 我们设计了 PII 编辑吗,还是事件后才发现?

**注意事项**

- 仅在事件发生时打开调试日志记录意味着对那个事件没有可观察性
- LLM 调用日志是大的 (每个调用可能是 KB),提前预算存储
- 跨多个供应商 (云,LLM 提供商,工具) 的可观察性集成花费时间,从第一天起规划

**要点总结: 您不能调试您不能看到的东西。可观察性是不可协商的,从第一天起构建它。**

**Qantas 案例**

考虑 Qantas 客户服务 AI 中的可观察性。在最初阶段,团队压力大要快速交付,有时跳过可观察性投资,以更快交付一个"工作"的系统。第一个生产事件揭示了什么时候省略它的成本。

模式可预测地展开。客户报告 AI 助手在特定预订上向他们提供了错误信息。客户服务主管想要调查。"我们能看到 AI 与该客户的对话吗?"团队拼凑日志,但完整的 prompt 和 completion 记录不可用。他们能看到响应,但不能看到提供给模型的检索文档,或者它得到的 system prompt 版本,或者它做的工具调用,或者每步花费的时间。调查停滞。决议涉及向 AI 系统提出关于客户的有教育性问题,并希望可以重现行为。它经常不能。

带强可观察性的相同情况看起来完全不同。客户的会话 ID 被查找。完整的对话痕迹出现: 每个用户消息,每个 system prompt 版本 (它们演变),每个 LLM 调用与完整 prompt 和 completion,每个工具调用与输入和输出,每步的延迟,每个 LLM 调用的 token 计数,在调用时活跃的模型版本。调查在分钟内可能。根本原因被识别 (例如,在那个调用中检索从过时的政策版本拉取),修复部署到生产中。客户被以正确的信息跟进。

需要这种可观察性的纪律是真实的。每个 LLM 调用记录 prompt 加 completion,平均可能为 5KB。10,000 每日调用产生每天 50MB,每年 18GB 仅仅是 prompt 数据。保留政策必须考虑这一点。访问控制必须考虑数据敏感性 (一些对话包含 PII)。PII 编辑必须为可以共享的较低敏感日志而工作。

集成跨多个供应商。LLM 调用通过 Bedrock,所以 Bedrock 日志是一层。Embedding 模型可能是 OpenAI 直接,所以那是另一层。工具调用到 Qantas 内部 API,所以那是 Qantas 监控基础设施。Vector DB 查询到 OpenSearch,所以那是另一组日志。可观察性是关于跨多个供应商正常一致编织所有这些。

最成熟的 Qantas AI 项目从第一天起将完整可观察性视为不可协商。Langfuse 或 Datadog LLM 可观察性或类似工具部署在生产之前,而不是在事件之后。Prompt 和 completion 数据流入访问控制的日志存储。PII 编辑在管道中。所有信号的仪表板可供产品所有者和工程师每天查看。

对 AI 交付来说,启示是可观察性是分离的 AI 项目可以在生产中长期生存与的项目在事件中。它感觉像可以推迟的开销,直到第一次客户事件,然后突然团队 wishes 他们一直在投资。从范围确定时把可观察性作为基础要求的交付从业者构建了在生产现实接触中生存的项目。把它当作以后的附加组件的人构建那些没有的项目。
