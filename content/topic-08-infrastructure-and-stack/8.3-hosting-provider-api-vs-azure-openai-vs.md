**Definition**

There are four main ways to consume LLMs in production. Native provider APIs (Anthropic, OpenAI, Google direct). Cloud provider hosted versions of those models (Azure OpenAI, AWS Bedrock for Claude and others, Google Vertex). Self hosted open weight models (you run Llama, Qwen, DeepSeek on your own infrastructure). And specialised inference providers (Together, Fireworks, Groq) that host open weights for you on a per token API.

**Why it matters in delivery**

Hosting choice is driven by procurement, data residency, contracts, and unit economics, not by which is "best." Enterprise procurement often forces a specific path before engineering even gets a say. PMs who understand the trade offs can spot the right path early instead of scoping the wrong one and having it overturned in week six.

**How it works**

| Option | What you get | Trade off |
|---|---|---|
| Native provider API | Direct access, fastest features, simplest integration | Separate billing, separate contract, separate data terms |
| Azure OpenAI | OpenAI models on Azure, with Azure data terms and region control | Slight feature lag, Azure procurement, Microsoft contract |
| AWS Bedrock | Claude, Llama, others on AWS, with AWS data terms and IAM | Slight feature lag, AWS procurement, AWS region constraints |
| Google Vertex | Gemini and others on Google Cloud, with GCP terms | Slight feature lag, GCP procurement |
| Self hosted open weights | Llama, Qwen, DeepSeek, Mistral on your own GPUs or cloud GPUs | Full data control, you run inference, you own ops |
| Inference providers (Together, Fireworks, Groq, OpenRouter) | Open weight models as a managed API | Less mature, fewer enterprise certifications |

The pattern in regulated industries: data residency and existing cloud agreements decide it before AI considerations enter. If the client is an Azure shop, Azure OpenAI is the path of least resistance. If they are AWS, Bedrock. If they need everything to stay on prem, self hosted.

**PM decision points**

- What cloud and AI contracts does the client already have, and which models are accessible through them?
- Are there data residency, sovereignty, or zero retention requirements?
- Does the project need bleeding edge features (native API) or is stable enterprise good enough (cloud hosted)?

**Watch outs**

- New model versions hit native APIs first, cloud hosted versions often lag weeks or months
- Cloud hosted models have different rate limits, quotas, and request formats than native
- Self hosting "for cost reasons" rarely pencils out below 50M+ tokens per day

**Takeaway: hosting is a procurement decision wearing an engineering costume. Find the contractual path first, model the cost second, choose the architecture third.**

**Qantas story**

The hosting decision for any Qantas AI capability is driven by procurement, contracts, and data residency more than by engineering preference. The decision space is narrower than it looks from the outside.

Qantas has deep AWS and Microsoft relationships. Adding Claude via Bedrock or OpenAI via Azure is a procurement amendment, not a new vendor relationship. Direct Anthropic, OpenAI, or Google contracts would require new supplier onboarding, new privacy reviews, new payment processes, and new audit obligations. For a sophisticated procurement function, that is months of work for no technical benefit.

The Sydney region availability matters. Both Bedrock and Azure OpenAI have Sydney region options for the major model families, which satisfies the typical data residency requirements. Without Sydney availability, the conversation gets much harder because data leaving Australia raises additional review steps.

For most Qantas AI workloads, the hosting choice is therefore Claude on Bedrock or OpenAI on Azure, depending on which model family the team needs. Both have the regional presence, both inherit the cloud commercial agreements, and both satisfy the typical compliance posture without additional work.

Self hosting open weight models on Qantas owned infrastructure is technically possible but rarely justified. The use case would need to combine sensitive data (cannot leave the corporate boundary), high volume (needs the unit economics of self hosting), and acceptable quality at smaller model sizes (the workload does not need flagship reasoning). Most workloads fail one of these tests. The narrow exceptions exist (some operational safety data, some specific high volume embedded classification) but they are exceptions, not the default.

Inference providers like Together or Fireworks could host open weights as a managed API, but the procurement work is similar to a new direct provider contract, and the maturity is lower than Bedrock or Azure. For most Qantas use cases, this is not the right path.

The interesting strategic question is how to manage hosting in a multi cloud reality. Most large enterprises have both AWS and Azure for different reasons. A mature AI strategy uses both, with workloads placed based on the team owning them, the existing infrastructure they need to integrate with, and the specific models needed. Forcing all AI into one cloud creates friction and does not save much.

For AI delivery, the lesson is that hosting decisions are procurement decisions dressed in technical language. The right opening question in any scoping conversation is "what cloud and AI contracts does the client already have." The answer narrows the options dramatically, and the architecture conversation flows from there. Trying to push through a technically superior option that does not match the procurement reality wastes weeks for no benefit. The clients who appreciate this are the ones who have seen previous projects stall on procurement issues that were predictable from day one.

**定义**

模型 API 可以直接消费 (Anthropic API、OpenAI API、Google AI Studio),也可以通过云原生服务消费 (AWS Bedrock、Azure OpenAI、Google Cloud Vertex AI)。基础模型在两种情况下是同一个。差别在: 商业合同、数据处理、监控、可用 region、以及它怎么融入客户已有的架构。

**为何在交付中重要**

托管方式的选择对应用代码长什么样影响很小,但对项目什么时候能启动影响巨大。它决定采购时间线、数据驻留合规、合同语言、监控集成、部署在哪朵云。选错,启动延后几个月。选对,项目跑得顺。

**运作原理**

| 维度 | 直接 API | 云原生 |
|---|---|---|
| 商业关系 | 跟厂商签新合同 | 走现有云合同 |
| 第一次上线的时间 | 慢,除非新供应商已经批了 | 快,在现有合同下 |
| 数据驻留 | 看厂商的 region | 跟云 region 选择一致 |
| 合规继承 | 单独的合规审查 | 通常从云合同继承下来 |
| 监控集成 | 单独的工具或自定义 | 跟现有云监控自然集成 |
| 价格 | 通常稍微便宜一点 (比如 Anthropic 直接) | 稍微贵一点 (云加价),但走现有承诺额度 |
| 模型可得性 | 最早能用上新模型 | 慢一些,新模型上云需要时间 |
| 高级功能 | 完整 API 表面 | 子集,有些功能只在直接 API 上有 |

对大部分 ANZ 企业 (Qantas、银行、Telstra),云原生几乎都是默认。引入新供应商是几个月的工作,云原生消费是几天。

**PM 决策点**

- 客户现有的云合同覆盖了哪些?这是第一道筛选。
- 项目是不是需要某个只有直接 API 才有的高级功能?如果是,这是直接 API 的少数合理理由之一。
- 数据驻留要求能不能跟云的 region 可得性对上?

**注意事项**

- 云厂商相对直接 API 总是有滞后。有些功能晚到,有些可能永远不到。
- 价格差异不大。直接 API 那点成本节省,很少能撑得起合规复杂度。
- 有些客户对几朵云有不同偏好。如果走多模型架构,每个云要分开评估。

**要点总结: 对大部分企业,云原生托管是默认。直接 API 只在云路径真的走不通的时候才需要。**

**Qantas 案例**

托管选择在 Qantas 这边,几乎完全由现有云关系决定。航空公司在核心系统上用 AWS,在生产力和某些工作负载上用 Microsoft。任何新的 AI 工作负载,都会走这两条云合同里的一条来消费,除非有不可逾越的技术理由不能。

实际优势是直接而且重大的。引入新供应商是 6 个月的工作,要走多个内部团队 (法务、采购、安全、技术风险、隐私)。云原生消费是一次采购变更,通常几周搞定。AI 团队能在 6 个月里把东西做出来发出来,而不是花同样的时间在新供应商引入上。

数据驻留合规通过 region 选择就能干净地映射。AWS 悉尼 region (ap-southeast-2) 和 Azure Australia East 在用户和澳洲监管机构眼里,都有清晰的数据驻留含义。直接 API 通常走厂商的全球基础设施,可能跟也可能不跟澳洲驻留要求对得上。

监控集成更顺。Qantas 已经在用 AWS CloudWatch 和 Azure Monitor。云原生 AI 调用自然流进现有可观测性栈。直接 API 调用需要单独搭一套监控。

价格差异很少能撑起换方案的成本。Anthropic 直接的价格通常比 Bedrock 便宜 5 到 10%,但只有在云路径完全走不通的时候,这点折扣才值得引入一个新供应商的负担。绝大多数工作负载上,Qantas 接受云加价。

直接 API 能赢的场景很窄。有些功能在直接 API 上先推出 (比如 Anthropic 经常在直接 API 上先发新模型,Bedrock 跟进要几周到几个月)。如果团队真的"昨天"就需要新模型,直接 API 可能短期撑得住。但通常情况下,等云上线是更便宜的选项。

另一个潜在的直接 API 场景是量极大的工作负载,价格差异开始变得重要。在每月几百亿 token 的量级上,5% 折扣是真金白银。但 Qantas 很少有工作负载真正跑到这个量,所以这是理论而非实战。

往大了说,这件事给 AI 交付的启示是: 托管选择是一场采购对话,不是工程对话。从客户对话的早期就带着这个理解的交付者,能快速把架构对准。"我们要用 Anthropic 的 Claude" 只是开始。"在 ap-southeast-2 区域通过 Bedrock,走 Qantas 现有的 AWS 合同,启用 Anthropic 在 Bedrock 上提供的零数据留存选项" 才是真正的架构。后者让项目能真正启动起来。
