**Definition**

The reference stack is the standard architecture for production enterprise AI applications. It has five layers: the application (what users see), the orchestration layer (the AI logic), the model layer (LLM API or hosted model), the data layer (vector store, knowledge base, tools), and the observability layer (logging, tracing, monitoring). Almost every serious AI product follows some version of this.

**Why it matters in delivery**

Knowing the reference stack lets you scope projects accurately, ask the right architecture questions, and spot when something is missing. PMs without this mental model accept architecture diagrams they cannot evaluate, miss critical components like observability until production, and let teams over engineer layers that did not need to be custom.

**How it works**

```
[User]
   -> [Application layer]       <- Web app, mobile, Slack, Teams, embedded UI
   -> [Orchestration layer]     <- The "AI logic": prompts, agent loops, tool routing
   -> [Model layer]             <- LLM API call or self hosted model
   -> [Data + tools layer]      <- Vector store, databases, APIs, tools
   -> [Observability layer]     <- Logging, tracing, evals, cost monitoring (spans all layers)
```

| Layer | What it does | Common choices |
|---|---|---|
| Application | User interface, auth, session, business logic | Next.js, React, native mobile, Slack bot, Teams app |
| Orchestration | Prompt templates, agent loops, tool routing, state | Custom code, LangChain, LlamaIndex, LangGraph, n8n |
| Model | The actual LLM | Anthropic, OpenAI, Google, Bedrock, self hosted |
| Data and tools | Knowledge sources, function calling targets | Pinecone, pgvector, Postgres, internal APIs |
| Observability | Logs, traces, eval results, cost dashboards | Langfuse, Helicone, Arize, custom Datadog setup |

The biggest scoping mistake is treating this as a 6 week project to build "AI features." It is a full stack engineering project where the AI is one layer.

**PM decision points**

- Is every layer accounted for in the architecture diagram, especially observability?
- Which layers are custom vs framework vs SaaS, and is each choice justified?
- Who owns each layer, and where are the integration boundaries?

**Watch outs**

- Teams over invest in orchestration frameworks early and regret it, start with simple custom code
- Observability is almost always added too late, build it in from day one
- Cloud platforms (Azure, AWS, Google) increasingly bundle multiple layers, evaluate the trade off

**Takeaway: the AI is one layer of a five layer stack. Scope all five from the start.**

**Qantas story**

At Qantas, building any enterprise AI capability would mean working through all five layers of the reference stack, and the most common scoping mistake is treating the AI as if it is one layer instead of one component within all five.

Consider a hypothetical Qantas frequent flyer assistant. The naive scope says "build an AI chatbot for frequent flyer members." Six weeks, two engineers, one product manager. The realistic scope walks through each layer.

The application layer needs an interface for members, which probably means integration with the Qantas app and the website. That is front end engineering, identity integration with the Qantas member auth system, session management, and analytics instrumentation. Realistically three to four weeks of work.

The orchestration layer handles prompt management, conversation state, tool routing, error handling, and rate limiting. For a serious production system this is custom code with proper testing, not framework glue. Two to three weeks.

The model layer is the LLM API call, but it includes the provider relationship (Claude on Bedrock, given the AWS agreement), the region configuration (Sydney for data residency), the rate limit management, and the fallback logic when the primary model is unavailable. Less work in elapsed time, more work in coordination with cloud and procurement teams.

The data and tools layer is the biggest. RAG over the frequent flyer content (which lives across multiple internal systems), tools to read member account state (balance, status, recent activity), tools to check eligibility for specific offers and redemptions, tools to draft member communications. Each tool is an integration with an existing system, with its own access patterns, error semantics, and operational considerations. Realistically six to eight weeks across multiple integrations.

The observability layer captures every interaction with its full context, surfaces dashboards for quality and cost monitoring, feeds the eval pipeline, and supports incident debugging. If built from day one, two weeks. If bolted on after launch, weeks of pain and missed visibility.

The total is 15 to 20 weeks for a real production launch, not the six the naive scope assumed. The AI itself is maybe 20 percent of the work. The rest is integration, infrastructure, monitoring, and the discipline of treating it like a production system.

The mistake teams make is scoping around the visible AI work and discovering the rest later. The discipline is to map all five layers in the initial architecture, allocate time honestly across them, and treat each one as production engineering.

For AI delivery, the broader lesson is that AI delivery is a full stack engineering discipline. The model is exciting and visible, which is why it dominates conversations. The remaining 80 percent of the work is where projects succeed or fail. The mature delivery posture treats the stack as a whole and budgets for every layer. Clients who have shipped AI badly before recognise this immediately. Clients who have not, sometimes need to be walked through it carefully.

**定义**

参考栈是大多数生产 AI 系统中存在的标准层。模型 API (Anthropic、OpenAI 等) 提供智能。编排层 (LangChain、LangGraph、自定义代码) 跨步骤协调。向量数据库存储和检索 embedding。工具集成连接到企业系统。监控和可观察性跟踪事情。这五层一起组成几乎每个生产 AI 系统。

**为何在交付中重要**

理解参考栈是 PM 能够对话技术架构而不丢失的方式。它使您能够询问诊断问题 (我们使用什么编排层?我们有什么向量数据库?),做出有意识的供应商决策,并通过其层调试问题。没有它,所有 AI 系统看起来都像黑盒子。

**运作原理**

| 层 | 它做什么 | 流行选项 |
|---|---|---|
| 模型 API | 处理推理调用 | Anthropic、OpenAI、Bedrock、Azure OpenAI、Google AI、Together、Fireworks |
| 编排 | 协调多步流程,处理重试,管理状态 | LangChain、LangGraph、LlamaIndex、自定义代码 |
| 向量数据库 | 存储 embedding,支持语义搜索 | Pinecone、Weaviate、Qdrant、pgvector、Chroma、Bedrock Knowledge Bases |
| 检索增强 | Embedding 模型、reranker、混合搜索 | OpenAI、Cohere、Voyage、内置 |
| 工具集成 | 连接到企业系统 | 自定义 API 包装、MCP、function calling |
| 提示管理 | 版本和测试提示 | 自定义,以及 LangSmith、PromptHub 等 |
| 监控 | 跟踪请求、成本、错误、延迟 | Langfuse、Helicone、Datadog、Honeycomb、自定义 |
| 评估 | 衡量质量随时间 | 自定义,以及 Braintrust、Weights and Biases、Comet |

栈通常布局如下:

```
[用户] -> [应用层] -> [编排层] -> [模型 API]
                                -> [向量 DB] -> [embedding]
                                -> [工具] -> [企业系统]
   [监控/可观察性] 横向 (无处不在)
```

**PM 决策点**

- 我们的栈在每层使用什么,谁拥有每个的运营责任?
- 我们在哪里有供应商锁定,我们何时关心切换?
- 哪些层是托管 SaaS vs 自托管,以及客户的偏好是什么?

**注意事项**

- 框架快速变化,今天的标准明天可能弃用
- 一些客户对每层有现有偏好,提前询问限制
- 监控通常是最后建立的,首先成为大事件,提前预算

**要点总结: 大多数生产 AI 系统是相同的五层。学习栈,使您能够智能地诊断和决定。**

**Qantas 案例**

考虑 Qantas 内部生产 AI 系统的参考栈。从架构上,它将类似于您在其他大型企业中看到的内容,但有航空公司操作约束塑造选择的方式。

模型 API 通过现有云协议消费。Anthropic 的 Claude 通过 AWS Bedcrock。OpenAI 的 GPT 通过 Azure OpenAI。Google Gemini 在它确实赢得位置时通过 Google Cloud。每个模型选择决定是关于哪种现有云关系携带它,而不是直接关系。这避免了新的供应商引入开销。

编排是自定义代码或薄框架使用。Qantas 工程团队倾向于自己构建,而不是采用如 LangChain 这样的重型框架。原因是控制和可调试性。当出现问题时,堆栈跟踪指向团队拥有的代码,而不是不透明的框架内部。许多大型企业都做出相同的选择,在最终离开 LangChain 之前先试用它。

向量 DB 选择基于现有云。对于 AWS 工作负载,Bedrock 知识库或带 OpenSearch 的 pgvector。对于 Azure 工作负载,Azure AI Search。Pinecone 等专业供应商在有令人信服的特定用例时引入,而不是默认。

检索增强使用现成模型供应商。embedding 模型是 OpenAI、Cohere 或 AWS Titan。Rerankers 是 Cohere 或 Voyage,通过云市场。这些是商品决定,不应得到大量架构时间。

工具集成是大多数定制工程发生的地方。Qantas 系统不是 API 优先的。许多核心系统 (预订引擎、frequent flyer 平台、运营调度) 暴露的是 SOAP、专有协议,或没有外部 API。AI 工具的工具集成层通常涉及构建适配器、缓存层和访问控制,这种工程比模型集成多。这一层经常被低估,然后实际占用项目时间的最大部分。

监控和可观察性是经常推迟的层,直到它咬人。一旦系统进入生产,无法分析当出现问题时发生的事情的成本是真实的。成熟的团队从第一天起设置基线的 LLM 调用日志记录、prompt 历史和成本跟踪,即使没有花哨的工具。在 staging 中测试在生产中工作的可观察性,而不是在第一次事件后努力安装它。

对 AI 交付来说,启示是参考栈是企业 AI 系统的共同语言。理解栈,使能够问尖锐的问题: "我们这层使用什么?谁拥有它?它如何被监控?当它失败时会发生什么?"在范围确定中带这种特异性的交付从业者比那些只在抽象级别工作的人更快赢得信任。栈是详细对话发生的基础。
