**Definition**

Latency is the time from user request to user visible response. Streaming sends the response token by token as it generates, so the user starts seeing output within a second instead of waiting for the full answer. Caching stores and reuses previous results to avoid repeated model calls. Together, these three determine whether an AI product feels responsive or slow.

**Why it matters in delivery**

Users abandon AI products that feel slow. A 4 second wait for a chatbot reply destroys the perception of intelligence, even if the answer is perfect. PMs who treat latency and caching as performance features, not optimisations to do later, ship products that feel like magic instead of friction.

**How it works**

| Concept | What it does | Typical impact |
|---|---|---|
| End to end latency | Time from user input to final response | 2 to 30 seconds depending on architecture |
| Time to first token | Time until the user sees the first word | 200ms to 2 seconds, the key UX metric |
| Streaming | Tokens delivered as generated | Cuts perceived latency by 50 to 80 percent |
| Prompt caching | Reuse cached portions of long prompts (system prompt, retrieved docs) | 60 to 90 percent cost reduction on cached input, faster too |
| Semantic caching | Match similar queries to past answers | Avoid repeat calls entirely on common queries |
| Output caching | Cache full responses by input hash | Free repeat answers for deterministic tasks |
| Parallelisation | Run independent calls concurrently | Cuts total latency by N for N parallel calls |

The latency budget for a chat interface is roughly: time to first token under 1.5 seconds (excellent), under 3 seconds (acceptable), over 5 seconds (bad). For agentic tasks, users tolerate longer if you show progress.

**PM decision points**

- What is the target time to first token, and is the team measuring it?
- Is streaming enabled everywhere it can be, including in agent intermediate steps?
- Is prompt caching configured for stable system prompts and frequent retrievals?

**Watch outs**

- Streaming complicates error handling, retries mid stream are messy
- Semantic caching can return stale answers when content has changed, set TTLs
- Some providers charge for cached input, some give it free, check terms

**Takeaway: latency is UX. Stream by default, cache aggressively, design for time to first token, not total time.**

**Qantas story**

Latency in a Qantas AI assistant is not a technical metric, it is a user experience metric, and the difference shows up in adoption rates. Consider a hypothetical Qantas customer service AI tool used by agents during live customer calls. The agent is on the phone with a customer, types a question, and needs a response fast enough to use it in the live conversation. Eight seconds is too long. Three seconds is acceptable. One second feels like magic.

The naive architecture sends the full prompt, waits for the full response, and returns it all at once. With a long system prompt, retrieved content, and a model response of moderate length, that is easily eight to twelve seconds. Unusable for live agent support.

Streaming changes the experience. Time to first token drops to under a second, the rest of the response streams in over the next few seconds, and the agent starts reading and using the answer immediately. Same total compute, dramatically better UX. The agent perceives the system as responsive rather than sluggish.

Caching adds more. The system prompt for an agent support tool is large and stable (instructions, tone guidance, refusal patterns, tool descriptions). The retrieved content for a specific topic is also reused across many agents handling similar customer issues. Both are good caching candidates. Provider prompt caching can reduce input cost by 80 percent or more on cached portions, and also speeds up the first token by avoiding redundant input processing.

The interesting design question is what happens during streaming when an error occurs mid response. The user has seen the first few sentences. A graceful failure pattern shows a clear error message and offers a retry. A poor failure pattern leaves the response hanging or cuts to a generic error. The streaming UX needs to be designed end to end, not just enabled as a feature.

The other consideration is when streaming hurts. For programmatic integrations where the consumer is another system that needs the full response, streaming adds complexity for no benefit. The downstream system has to assemble streamed chunks before processing. For these cases, non streaming is simpler.

For AI delivery, the lesson is that latency is a first class product concern, not an optimisation. The decisions about streaming, caching, and parallel calls should be made during architecture design, not after launch when users complain. Clients sometimes ask "is the AI fast enough" and the right response is to walk them through the latency budget for their specific use case and design for it. Agent support tools have one latency profile. Email summarisation has a different one. Batch processing has a third. Treating these the same way produces products that feel wrong in all of them.

**定义**

延迟是用户从输入到看到回应感觉到的时间。流式传输 (streaming) 是模型一边生成一边一个 token 一个 token 地推送响应,而不是等整个回应生成完再发。缓存是把之前响应的某些部分 (整个回应、检索结果、或者 prompt 前缀) 存起来,这样不用每次重算。这三件事一起,驱动 AI 系统的用户体验和成本。

**为何在交付中重要**

延迟是面向用户的 AI 产品里最容易被低估的设计因素。10 秒的回应感觉就像系统坏了,即便技术上完全正确。3 秒首字 + 7 秒生成的流式响应,感觉是响应迅速的。能优化整张延迟图的 PM,做出来的产品体感会远好于其他 AI 产品。

**运作原理**

| 因素 | 影响 | 缓解 |
|---|---|---|
| 模型大小 | 大模型慢 | 在质量允许的前提下用小模型 |
| Prompt 长度 | 长 prompt 慢 (输入处理) | 裁剪 prompt,用 prompt caching |
| 响应长度 | 长响应慢 (token 生成) | 限制 max_tokens,要求简洁 |
| 检索 | 加 100 到 500ms | 频繁查询做缓存、异步并行 |
| 工具调用 | 每次工具调用都是一次单独的 LLM 调用 + 工具自己的时间 | 工具调用最小化,能并行就并行 |
| 网络 | 看 region 和厂商位置 | 选附近的 region |
| 流式传输 | 不减少总时间,但减少感知时间 | 默认开启 |
| 缓存 | 重复 prompt 或检索能大幅减少 | Prompt caching、语义缓存、KV 缓存 |

Prompt caching 特别强: 大部分厂商现在都允许你在多次调用之间复用 prompt 的前缀部分 (比如稳定的 system prompt 加文档上下文),只为新部分付钱。能砍掉 80% 的 prompt 处理成本和延迟。

**PM 决策点**

- 这个工作流的延迟预算是多少? (实时聊天要 < 3 秒,后台任务可以是分钟级)
- 流式传输有没有开?它对感知延迟的影响有多大?
- 我们在哪里做缓存?缓存命中率多少?

**注意事项**

- 流式传输会"掩盖"长延迟,直到事情真的崩为止。有时候它是糟糕设计的遮羞布。
- 缓存命中率会随时间漂移: prompt 模板一改,缓存就失效。
- 长上下文模型不一定慢,但通常是。要在自己的厂商上实测。

**要点总结: 感知延迟跟真实延迟一样重要。流式 + 缓存 + 简洁性的组合,赢下大部分 UX 战役。**

**Qantas 案例**

设想面向客户的 Qantas AI 助手里的延迟工程。在网站上,客户期望聊天响应在 2 秒内开始流式输出,6 秒内完成。超过这个时间的回应就感觉系统坏了,客户就放弃了。手机 App 上的期望甚至更严。

天真的实现可能要 12 秒。检索 400ms,模型生成 400 token 的响应要 7 秒,工具调用加 3 秒,后处理加 1.6 秒。每一步都是必要的,但总和是糟糕的。

优化路径是这样的。第一,开流式传输,这样用户立刻开始看到 token。光这一步就把感知延迟从 12 秒拉到 1.5 秒 (到第一个 token 的时间)。即便总生成时间一样,感觉完全不同。

第二,Prompt caching。客服 system prompt 超过 2000 tokens,跨所有客户调用是稳定的。Anthropic 或 OpenAI 上的 prompt caching 让这 2000 token 接近免费,把输入处理延迟从约 200ms 砍到约 30ms。

第三,模型选择。最初的实现所有事情都用旗舰模型 (Opus)。但对 70% 的简单查询,Sonnet 在质量上跟 Opus 没法区分,但延迟明显更低。一层路由把简单查询送到 Sonnet,复杂查询送到 Opus,把大部分交互的延迟砍下来。

第四,工具优化。当工具调用必要的时候 (查订单、查航班状态),能并行就并行,不要串行。同时调三个工具花的是 max(t1, t2, t3),不是 t1 + t2 + t3。

第五,响应长度修剪。Prompt 里指导模型对客户问题简洁回答。"用 2 到 4 句话回答" 这一句话就能砍掉 token 生成时间。模型天然倾向冗长,prompt 必须明确给出目标长度。

合起来,12 秒响应能变成 6 秒响应,首字时间 1.5 秒。这是从"坏了"到"响应迅速"。

第六个杠杆是缓存,在合适的地方上。常见问题 ("我的行李额度多少") 的答案做语义缓存,意味着这些查询不用每次都调模型,即便措辞不同。这种查询的延迟降到亚秒,成本降到接近零。语义缓存要谨慎用,因为措辞的细微差异有时候真的有语义差异,但对常见问题它非常强。

往大了说,这件事给 AI 交付的启示是: 延迟工程是 AI 产品的核心 UX 学科。所有面向客户的产品都该如此,但 AI 产品经常忽略它——因为团队被质量和能力本身惊艳到了,愿意接受任何延迟数字。能仔细推延迟图、优化每一层、在主观感受和客观度量上都达标的交付者,做出来的是"感觉好"的产品,不只是"能用"的产品。
