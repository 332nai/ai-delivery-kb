**Definition**

Orchestration frameworks are the glue between the model and everything else. They handle prompt templates, tool routing, agent loops, retrieval pipelines, and state management. The main options are LangChain (broadest, most popular, often over engineered), LlamaIndex (focused on RAG), n8n and similar (low code workflow tools), provider SDKs (OpenAI Agents SDK, Anthropic SDK), and custom code (just Python or TypeScript).

**Why it matters in delivery**

The orchestration framework choice shapes how fast the team can iterate, how easy the system is to debug, and how much lock in there is. The wrong choice creates months of friction. The right choice is often boring: a thin custom layer with explicit code, not a sprawling framework. PMs who can challenge framework choice prevent a common form of over engineering.

**How it works**

| Option | Strengths | Weaknesses | Best for |
|---|---|---|---|
| Custom code | Full control, easy to debug, no lock in | Build it yourself | Production systems with clear requirements |
| LangChain / LangGraph | Huge ecosystem, lots of integrations, agent primitives | Complex, abstractions leak, fast moving API | Prototypes, teams familiar with it |
| LlamaIndex | Strong RAG primitives, good document loaders | Less coverage for agents and tools | RAG focused projects |
| Provider SDKs (OpenAI Agents, Anthropic, Vercel AI SDK) | First party, simple, fewer abstractions | Locked to provider, less flexible | Teams committed to one provider |
| Low code (n8n, Zapier, Make) | Visual, business user friendly, fast | Limited for complex AI logic | Workflow automation, internal tools |
| Enterprise platforms (Microsoft Copilot Studio, Salesforce Agentforce) | Tight integration with existing systems | Lock in, limited flexibility | Enterprises deep in those ecosystems |

The eternal trade off: frameworks promise to speed you up early, then slow you down later. Custom code is slower to start, faster to maintain. Pick based on where the project is in its lifecycle.

**PM decision points**

- Is the project an experiment, a prototype, or a production system, the answer drives the framework choice?
- Does the team have the engineering depth to maintain custom orchestration, or do they need a framework's training wheels?
- How much lock in is acceptable, and can we leave the framework if it goes bad?

**Watch outs**

- Frameworks evolve fast, your code can break on minor version updates
- The first day of a framework is impressive, month six is a different story
- "Everyone uses LangChain" is not a reason, evaluate against your actual needs

**Takeaway: orchestration is glue, not the product. Use the lightest framework that meets requirements, prefer explicit code in production.**

**Qantas story**

The orchestration framework debate plays out at Qantas in predictable ways. Teams new to AI gravitate toward LangChain because it is the most visible option and the documentation is everywhere. Teams that have shipped a few production systems often move away from it.

Consider a hypothetical Qantas internal knowledge assistant. The first version is built on LangChain because the team is learning AI and LangChain has primitives for everything. Eight weeks in, the team is shipping but spending significant time fighting framework abstractions. Debugging is hard because errors come from deep in the framework, not from the team's code. A LangChain version update breaks something subtle that takes three days to diagnose. The framework promised speed and delivered drag.

The team rewrites the orchestration layer in roughly 500 lines of Python around the Anthropic SDK directly. The work takes about a week. The new code is explicit, debuggable, and entirely under the team's control. Error messages are clear. The team's velocity in subsequent weeks is noticeably higher.

The trade off is real. LangChain saved time in the first two weeks, when the team was learning the patterns. It cost time from week three onwards, when the patterns were clear but the abstractions kept getting in the way. The break even point was around four weeks, and the project was scoped for sixteen.

This pattern is so common it is almost predictable. Frameworks promise speed and deliver it in the first sprint. They tax later sprints with abstraction leakage, version compatibility issues, and harder debugging. The right framework choice depends on the stage of the project. Prototypes and proofs of concept benefit from frameworks. Production systems benefit from explicit code.

For AI delivery, the practical lesson is that orchestration frameworks are tools, not commitments. The choice should be driven by the project's stage and the team's depth, not by what is fashionable. For a quick prototype where the team is learning, a framework is fine. For a production system the team will maintain for years, explicit code with the provider SDK is usually better. The provider SDKs (Anthropic, OpenAI Agents SDK, Vercel AI SDK) have become much better at handling common patterns, which has narrowed LangChain's value proposition.

The other practical point is that the framework debate is often emotional. Teams that have invested in LangChain defend it. Teams that have been burned by LangChain reject it. The right delivery posture is neither tribal. Evaluate the framework against the project requirements. Pick the lightest option that meets needs. Be willing to swap if the choice turns out to be wrong. Most importantly, do not let framework debates consume time that should be spent on the actual product. The framework is glue, not the product.

**定义**

编排框架提供构建 AI 应用的现成组件 (chain、agent、内存、工具、检索器)。LangChain 是市场领导者,最近被 LangGraph (来自同一团队) 用于 agent 工作流补充。CrewAI 专注于多 agent 模式。LlamaIndex 起源于 RAG 但已扩展。还有几十个其他的。问题是您是否需要它们或者更简单。

**为何在交付中重要**

框架选择是一个有声誉的决定,经常默认为"团队听说过的"。错误的框架选择可以放慢交付,在依赖中锁定您,或将复杂性引入您不需要的简单工作流。但避免框架也意味着重新发明轮子。能够清楚地思考权衡的 PM 节省团队从早期错误的多月迁移。

**运作原理**

| 选项 | 适合 | 优势 | 劣势 |
|---|---|---|---|
| LangChain | 通用,RAG,简单链 | 大量集成,大社区 | 重型抽象,API 流失,调试痛苦 |
| LangGraph | Stateful agent,工作流 | 显式状态机模型,可调试 | 学习曲线,LangChain 生态系统依赖 |
| LlamaIndex | RAG 重型工作流 | 强大的检索原语 | 在非 RAG 上较弱 |
| CrewAI | 多 agent | 简单的多 agent 抽象 | 早期成熟度,有限的生产实战 |
| Vercel AI SDK | TypeScript / Next.js 应用 | 流式响应,前端集成 | 限于 JS 生态系统 |
| 自定义代码 | 当您需要控制时 | 没有不可见的抽象,容易调试 | 您构建它,您维护它 |

经验法则: 对于简单的单调用 LLM 应用,使用没有框架的提供商 SDK。对于带 3 到 5 步的 RAG,使用轻量级框架或自定义代码。对于 stateful agents,LangGraph 或自定义。对于复杂的多 agent,仔细评估 CrewAI 与自定义。许多生产团队开始使用 LangChain,然后用自定义代码替换部分。

**PM 决策点**

- 我们的实际复杂性级别是什么?简单 RAG 通常不需要框架
- 团队拥有什么样的工程?对自定义代码舒适与不舒服
- 我们将如何随时间维护这个,框架文档质量如何

**注意事项**

- LangChain 的抽象经常使简单事情变得复杂,有时您 fighting 框架而不是构建
- 框架版本以打破现有代码的方式更改,锁定版本并仔细升级
- 团队经常将"我们使用 LangChain"作为成熟度信号说,使评估更难: 不要被那个信号愚弄

**要点总结: 框架是工具,不是要求。从简单开始,当复杂性证明合理时引入框架。**

**Qantas 案例**

考虑 Qantas 团队在编排框架选择上的对话。压力是显著的。LinkedIn 帖子谈到 LangChain。咨询公司推荐它。一些供应商需要它。开发者社区围绕它建立。诱惑是说"是的,我们使用 LangChain"作为现代化的信号。

诚实的工程评估通常较少令人兴奋。LangChain 的强抽象在 3 步检索增强生成 pipeline 中提供有限的杠杆。同样的工作流可以使用 Anthropic 或 OpenAI SDK 直接以更少的代码实现,更可调试的堆栈跟踪,以及更少的依赖更新。LangChain 提供工具的丰富生态系统,但 90% 是 Qantas 不需要的连接器,5% 与企业要求 (审计、访问控制) 不兼容,5% 是相关的,但可以直接实现。

更微妙的案例是 stateful agentic 工作流。这是 LangGraph 等框架开始证明其复杂性合理的地方。状态机模型与 agent 设计很好地映射。可见性比手动状态管理更好。LangGraph 在像之前讨论的中断恢复 agent 这样的用例中可能确实是合理的选择。

但即使在那里,Qantas 工程团队需要评估的不是框架本身,而是采用它的运营负担。框架版本以打破现有代码的方式更改。新框架版本以已弃用的 API 推出。安全漏洞需要快速升级到不一定向后兼容的版本。当框架社区移动时,留在固定版本上变成技术债务。当社区移动时,升级是工程时间。

替代方案是自定义代码,该代码完全做项目需要的事情而没有更多。这看起来不那么时髦,但带来真实的好处。代码完全是团队拥有的。堆栈跟踪指向他们写的代码。没有不可见的抽象。维护是预算的,而不是被框架版本爆发驱动。

许多大型企业团队的演变模式是开始时使用 LangChain (因为它们已经听说过),随着复杂性增长撞到框架边缘,然后逐渐用自定义代码替换部分,直到框架成为 5% 的代码库。如果您从一开始就知道结局,从自定义代码开始通常是合理的选择,框架仅在它清楚地节省时间和复杂性的特定子工作流中引入。

对 AI 交付来说,启示是框架选择不应基于"现代"的感觉做出。它应基于诚实评估特定工作流的复杂性,团队的工程偏好,以及对供应商和运营的现实评估。能够说"是的,我看到为什么 LangChain 看起来吸引人,这里是我们仔细评估它的方式,这是我们的具体选择以及为什么"的交付从业者比那些只是采用最响亮选项的人更快赢得信任。
