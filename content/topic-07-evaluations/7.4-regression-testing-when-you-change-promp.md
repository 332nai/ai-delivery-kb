**Definition**

Regression testing in AI systems means running the golden dataset against the system after every meaningful change (prompt edit, model swap, retrieval tweak, tool change) to catch quality drops before they ship. It is the same concept as software regression testing, but the surface area is bigger because every component affects every other component.

**Why it matters in delivery**

AI systems are uniquely prone to silent regressions. A prompt change that fixes one issue often breaks two others. A model upgrade improves average quality but regresses on edge cases. Without regression testing, these silent regressions accumulate over months and the system slowly gets worse while the team thinks they are improving it. PMs who instil a discipline of regression testing prevent the slow death by a thousand small changes.

**How it works**

A practical regression workflow:

1. Run smoke test (5 to 10 examples) after every prompt iteration during dev
2. Run validation set (50 to 200 examples) before merging changes
3. Run test set (full golden dataset) before any production release
4. Compare results to baseline, flag any drop in pass rate or score
5. Investigate regressions: which examples got worse, why, is the trade off acceptable?
6. Either fix the regression or document it as accepted

| Change type | Regression risk | Required test |
|---|---|---|
| Minor prompt wording | Medium | Validation set |
| Adding new instructions | High | Validation set, possibly test set |
| Model swap (same family) | High | Full test set |
| Model swap (different provider) | Very high | Full test set, possibly new evals |
| Retrieval parameter change | High | Validation set with retrieval focused queries |
| Tool addition or change | High | Validation set covering tool use cases |

Regression testing should be automated, not manual. CI pipelines that block merges on eval regressions are standard in mature teams.

**PM decision points**

- Is regression testing automated, or does it depend on someone remembering to run it?
- What is the threshold for an acceptable regression, where do we draw the line?
- How are regressions tracked over time, are we slowly drifting down?

**Watch outs**

- LLM as judge variance, the same input can score slightly differently across runs, set tolerance bands
- Cherry picked rollouts, deploying a change that works on the dataset but fails on new patterns the dataset does not capture
- Stale baselines, recalibrate after major changes, not every minor one

**Takeaway: regression test every change, automate it, and treat eval regressions like broken tests. Silent drift is the slow killer.**

**Qantas story**

Regression testing for AI systems is something Qantas would learn the hard way the first time a "small prompt change" silently breaks production. The pattern is universal: a team makes a change they think is minor, ships it without rerunning the eval set, and discovers days or weeks later that some behaviour has degraded.

Consider a hypothetical Qantas customer service assistant where the team updates the system prompt to handle a new fare class introduction. The change adds two sentences about how the new fare class interacts with frequent flyer benefits. It looks like a strictly additive change. The team ships without rerunning the eval set, because "we only added text, we did not change anything existing."

In production, the team starts seeing complaints that the assistant is suddenly worse at handling Platinum status questions, an unrelated topic. Investigation reveals that the new sentences about fare class interaction subtly shifted the model's attention patterns, and a category of Platinum questions that previously worked well now produces less precise answers. The change was not strictly additive in its effect, even though it was strictly additive in its text.

If the team had run the regression suite, they would have caught the regression before ship. The eval set includes Platinum benefit questions, and the regression would have shown up immediately. Instead, they shipped and learned about it through customer complaints, which is a much more expensive way to find out.

The discipline that prevents this is automated regression testing as part of every release. The eval suite runs on every prompt change, every model swap, every retrieval configuration change, every tool change. Releases are blocked if regression exceeds tolerance. Tolerances are set conservatively (no more than one or two percentage point drop on any major category, no drop on critical categories like safety adjacent questions).

The interesting failure modes are around tolerance tuning. Set tolerances too tight and the team cannot ship anything because LLM as judge has some inherent variance. Set tolerances too loose and small regressions accumulate over time, slowly degrading the system. The right discipline is tight tolerances on the critical metrics (where a regression would be a real problem) and slightly looser tolerances on general metrics (where some noise is expected). The tolerances themselves need to be reviewed quarterly.

The other failure mode is regression suite staleness. The eval set built in Q1 might not cover behaviour that became important in Q3 (like the new fare class). The suite needs to grow as the system grows. New use cases added to the system mean new eval examples added to the suite.

For AI delivery, the lesson is that regression testing is what turns AI delivery from craft into engineering. Without it, every change is a guess. With it, the team can iterate quickly with confidence. The clients who appreciate this are the ones who have shipped AI without regression testing previously and seen the slow drift. The clients who resist this often have not seen the slow drift yet, and the right move is to show them what it looks like by running their existing system against a freshly built eval set. The results are usually sobering.

**定义**

回归测试是在做完变更之后重新跑 eval、确认"之前能跑通的东西现在还能跑通"的实践。在 AI 项目里,它适用于: 模型版本升级、prompt 修改、工具变更、检索调优、厂商更新。回归测试是 eval 在 AI 项目里产生实际杠杆的主要地方。

**为何在交付中重要**

AI 系统每周都在变,有时候每天都在变。每一次变更都有可能把"之前能跑通的东西"搞坏。在传统软件里,这种问题由单元测试拦截。在 AI 里,eval 起这个作用。没有回归测试,团队就是在把 bug 随机推上生产,然后客户在工程师之前先发现这些 bug。

**运作原理**

给 AI 系统做回归测试的基本 pattern:

1. 维护一份稳定的 eval 数据集 (golden + 对抗性 + 边缘情况)
2. 把生产当前在这份数据集上的分数记下来,作为基线
3. 任何重大变更之后,跑一遍这份数据集
4. 把新分数跟基线对比
5. 分数掉了,合并之前先查清楚

| 变更类型 | 风险 | 推荐的 eval 节奏 |
|---|---|---|
| Prompt 修改 | 高 (小改动可能产生大影响) | 合并之前跑完整套件 |
| 模型版本升级 | 高 (旧 prompt 在新模型上行为可能不同) | 完整套件 + 扩展的边缘情况 |
| 检索变更 (新 chunking、换 reranker) | 高 (检索质量可能悄悄下降) | 检索质量子集 + 端到端 |
| 工具变更 | 中 (新工具可能改变 agent 行为) | 工具相关子集 + 端到端 |
| 配置调优 (temperature、top p) | 中 | 完整套件 |
| 监控面板变更 | 低 (没有功能影响) | 跳过 eval |

回归阈值: 大多数生产团队会设这种政策——核心 eval 上回归 3% 阻止合并,2% 触发评审,1% 在监控面板上标记。

**PM 决策点**

- 哪种变更需要哪一级别的 eval?(每次提交都跑完整套件不现实,但重大变更必须跑)
- 谁拥有 eval 套件?当一次变更暴露出 eval 套件的空缺时,谁负责更新?
- 主要厂商升级模型的时候会发生什么?(很少有团队真的为这一刻准备好了)

**注意事项**

- "看起来一样"是主观感受。对客户来说一个"小变更"可能在 50% 的样本上改了输出,但 eval 数字没动。
- Eval 套件本身会随时间漂移。要确保它仍然代表真实生产。
- 厂商可能在不预警的情况下弃用模型,逼你做一次紧急的 eval 周期。这件事要提前规划。

**要点总结: AI 系统在持续变化。回归测试是让"变更"变成安全动作的工程实践。永远不要在没有回归测试的情况下推 prompt 或模型变更。**

**Qantas 案例**

在像 Qantas 这种航空公司里,回归测试是 AI 系统赢得生产信任、并把信任守住的纪律。设想客服 AI 助手的运营生命周期。

最初推广的头几个月,变更很频繁。新政策上线、新功能加入、新边缘情况被发现、prompt 被调整来处理它们。每一次变更都有可能把已经在工作的东西打掉。回归测试就是防止这种倒退侵蚀信任的盔甲。

具体 pattern 可能是这样的。CI 系统在每一个 pull request 上跑核心 eval 套件 (大约 300 个样本,覆盖主要用例)。跑一次 5 分钟,结果自动报告到 PR 上。分数掉超过 2%,合并被卡住直到查清楚。这能抓住大部分显眼的回归。

完整套件 (1500 个样本,覆盖所有用例,包括对抗性) 在夜间跑,因为它有更多时间。它能抓住核心套件漏掉的细微回归。结果发到内部仪表板,生产负责人可以审阅。任何夜间分数下降,都触发早上的调查。

模型升级会被格外小心对待。当 Anthropic 发布新一版 Claude,系统不会自动升级。新模型先跟当前模型并排在完整 eval 套件上跑一遍。表现按维度做对比。回归被分析。经常的情况是: 模型升级在整体上提升了质量,但在某些具体类目上反而退步了。要不要接受这个取舍,是一个产品决策,不是一个模型决策。

厂商不可避免的弃用是更难的运营挑战。当一个模型版本被宣布弃用,你有 6 到 12 个月的窗口期,然后它就停服了。Eval 套件让 Qantas 在这段窗口期内评估替代模型的能力,挑出最合适的那个,而不是被时间表追着跑。

类似的纪律也适用于检索变更。内容团队更新政策文档的时候,检索 eval 检查相关查询是否仍然能命中正确的政策。新 chunking 策略尝试的时候,检索质量被系统化评估。Vector DB 升级规划的时候,索引迁移先在 staging 上对着 eval 套件验证。

有意思的失败 pattern 是给自己找的借口: "这次变更我们不需要跑 eval。" 当变更感觉很小的时候,这种压力就出现了。"我们只是改了 system prompt 里一个词。" "我们只是从 Claude Sonnet 升到了改进版的 Sonnet。" "我们只是调了 reranker 的阈值。" 每一种听起来都无害,但每一种都可能产生惊人的影响。专业团队即便有直觉说"应该没事"也照样跑 eval,有时候结果会让他们意外。

往大了说,这件事给 AI 交付的启示是: 回归测试纪律,就是"能在 AI 系统上长期可持续运营的团队"和"活在被动救火里的团队"之间的分水岭。每个 PM 都应该能回答这个问题: "在合并我们最后 10 次变更之前,我们跑了什么 eval?" 如果答案是"我们对它们感觉不错",而不是"我们跑了这几个套件、审过结果",这个项目就是在为后面一次痛苦的事件做铺垫。回归测试是机会工程,不是奢侈品。
