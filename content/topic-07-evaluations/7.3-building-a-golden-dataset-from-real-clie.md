**Definition**

A golden dataset is a curated collection of representative inputs paired with verified correct outputs (or graded responses), used as the ground truth against which model and prompt changes are measured. It is the foundation of every serious eval system. Without it, "is this better" is a vibe, not a measurement.

**Why it matters in delivery**

Most AI projects do not have a golden dataset. They have a few example queries the team made up, which they re run after every change and call it eval. PMs who insist on building a real golden dataset from real client data create the only mechanism by which improvement can actually be measured. It also exposes scope problems early because building the dataset forces the team to articulate what good looks like.

**How it works**

A practical golden dataset construction process:

1. **Sample real inputs**: pull 100 to 500 actual queries, documents, or interactions from production or pilot data. Stratify across user types, query types, and difficulty.
2. **Label correct outputs**: have a subject matter expert produce or verify the right answer for each input. This is the slow part.
3. **Cover failure modes**: deliberately include known hard cases, edge cases, ambiguous queries, and adversarial inputs.
4. **Lock it down**: version the dataset, freeze it, do not change it during development.
5. **Hold some out**: split into train, validation, and test. The test set is touched only when promoting a change to production.

| Dataset slice | Typical size | Purpose | Touch frequency |
|---|---|---|---|
| Smoke test | 5 to 10 examples | Quick sanity check during prompt iteration | Every change |
| Validation set | 50 to 200 examples | Tuning prompts, models, retrieval | Daily during dev |
| Test set | 100 to 500 examples | Final pre production evaluation | Only on release |
| Production sample | Ongoing | Continuous quality monitoring | Weekly or daily |

The biggest mistake: building the dataset from synthetic examples or curated demo cases. The dataset must reflect real production distribution, or it lies.

**PM decision points**

- Does the project have a real golden dataset, or just example queries someone wrote up?
- Who is qualified to label correct outputs, and what is the budget for their time?
- Is the dataset stratified across query types, or are 90 percent of examples the easy case?

**Watch outs**

- Dataset contamination, never let the model see test data during prompt iteration, or you measure memorisation not capability
- Stale datasets, refresh quarterly as user behaviour and content evolves
- Synthetic data is fine for augmentation, dangerous as the only source

**Takeaway: a golden dataset is the difference between measured progress and vibes. Build it from real data, lock it down, run it on every change.**

**Qantas story**

A golden dataset is the single most underinvested element of most enterprise AI projects, and Qantas would not be an exception. The temptation is to skip it because building it is slow, expensive, and unglamorous. The cost of skipping it is months of guesswork and rework.

Consider a hypothetical Qantas customer service AI project. The team wants to ship a chatbot that handles routine inquiries. The naive approach is to build the chatbot, do some informal testing, and ship. The disciplined approach is to first build a golden dataset of 200 real anonymised customer inquiries, each paired with the response a senior customer service agent would write. This takes three weeks and AUD 25K in agent time to assemble.

Once the dataset exists, every subsequent decision becomes data driven. Which model to use? Run all candidates against the dataset and pick the one with the best quality at acceptable cost. Which prompt to use? Test prompt variations against the dataset and pick the winner. Which retrieval strategy? Compare retrieval configurations against the dataset and pick the best. The dataset replaces opinion with measurement.

The interesting design questions in dataset construction are non trivial. The 200 inquiries need to be stratified across topic (rebooking, refund, baggage, frequent flyer, special assistance, codeshare, status query, complaint), difficulty (simple lookup vs complex multi step reasoning), customer tone (calm, frustrated, formal, informal), and customer mix (high status, leisure traveller, business traveller, first time customer). The dataset needs to look like real production traffic, not like a polished test suite.

The dataset needs to be split. A smoke test of 10 examples for daily iteration, a validation set of 80 examples for prompt tuning, a test set of 110 examples kept locked away and used only when validating a release candidate. Without the split, the team will tune the system to perform well on the dataset specifically and discover in production that it does not generalise.

The dataset also needs ongoing curation. Customer behaviour shifts over time, new products launch, new policies come into effect. A dataset built in Q1 starts to drift from production reality by Q3. Quarterly refresh cycles, adding new examples from current production traffic, keep the dataset honest.

The organisational reality is that building this dataset requires senior customer service team time, which is expensive and scarce. The investment looks like overhead at the time. The payoff is that every subsequent technical decision is faster, cheaper, and better informed.

For AI delivery, the lesson is that golden datasets are the single highest leverage investment in serious AI delivery work. The clients who appreciate this are the ones who have shipped AI without a dataset previously and discovered the cost. Walking a new client through the dataset construction in week one of a project sets the foundation for everything that follows. It also signals that the team is serious about measurement, which builds credibility with stakeholders who have seen vendors over promise and under deliver.

**定义**

Golden dataset 是给 AI 做 eval 用的、有代表性的输入集合,每个输入都标注了预期的正确输出。它是大部分严肃 AI 工程的真值锚。把一份好的 golden dataset 构建出来,是 AI 项目交付里被低估得最厉害的环节之一。

**为何在交付中重要**

Eval 的质量上限,就是 golden dataset 的质量上限。糟糕的数据集 (太小、不具代表性、标签有错) 产出的 eval 看起来精确,但毫无意义。好数据集很难做,需要领域专业知识、需要迭代、需要持续维护。在这件事上提前投入的 PM,能让团队避免"在不可信的 eval 上做发布决策"这种痛苦。

**运作原理**

| 来源 | 怎么做 | 优势 | 劣势 |
|---|---|---|---|
| 生产流量采样 | 抽真实查询样本,人工标注 | 真实分布、真实边缘情况 | 私有数据问题,需要标注工作量 |
| 合成数据 | 用 LLM 生成代表性输入 | 快、覆盖可控、没有 PII | 可能漏掉真实失败 pattern |
| 领域专家造 | SME 写出他们见过的查询 | 质量高、带专家直觉 | 慢且贵、多样性有限 |
| 历史人工决策 | 找已经做过的人工决策记录 | 已经标注好、量大 | 真值可能不可靠、或者太老 |
| 对抗性 | 刻意构造可能失败的输入 | 在发布前暴露失败 pattern | 不代表正常使用 |

正确的混合通常涉及多个来源。一个代表生产分布的 100 到 500 条核心样本。一组 50 到 100 条对抗性样本,用来测边缘情况和拒答场景。再加 50 到 100 条合成样本,覆盖那些在生产里代表性不足的客户细分。

经验法则: 至少 100 个样本,eval 数字才稳定 (噪声足够低)。低于 50 个,跑两次之间的方差就能盖过真实变化。

**PM 决策点**

- 数据集跟真实生产分布有多接近?这个问题不诚实回答,数据集就是装饰品。
- 谁来标注?标注的一致性怎么保证?
- 它怎么随时间演化?谁拥有它?

**注意事项**

- 工程师自己造的合成数据集,通常会漏掉工程师没想到的失败 pattern。
- 标注一致性需要校准: 同一份 eval 数据,两个不同的人不应该分歧超过 20%。
- Eval 集泄漏到训练或 fine tuning 数据里,整个 eval 就废了。严格隔离。

**要点总结: Golden dataset 是 AI 工程的基础设施。投入它、治理它、让它跟着生产一起演化。**

**Qantas 案例**

在一个假设的 Qantas 客服 AI 系统里,构建 golden dataset 是杠杆最高的活动之一。它不是显眼的工作,但 eval 的大部分价值是在这里产生的。

设想客服意图分类这个用例。第一轮可能是这样: 客服运营团队的一个人,花一周时间,从过去三个月的真实工单里抽出 800 个脱敏过的工单,代表真实流量的自然分布 (重新预订占大头,退款次之,等等)。一位资深坐席给每个工单标注真实意图、紧急程度、以及"是否应该升级给人工"。再找一位独立的资深坐席,对其中 200 个子样本做独立标注,用来度量标注者之间的一致性。

第一轮数据集足够好作为起点,但有空缺。罕见意图代表性不足。某些地理区域 (国际客户) 代表性不足。某些时间段 (重大中断期间) 代表性不足。新出现的问题 (新机舱产品引发的客户问题) 完全缺失。这些都需要补到数据集里,eval 才能真正反映生产表现。

第二轮做补充。在代表性不足的细分上,精挑细选再加 200 条工单。再合成 50 条对抗性输入,用来测试"该拒答的时候有没有拒答"。再从历史中断里加 100 条边缘情况,这些情况下政策应用了一些不寻常的规则。专家把整个集合过一遍,平衡分布、统一标签格式。

数据集变成一份活资产。每次坐席在生产里遇到让人困惑的工单,他们把它加进一个待入数据集的队列。每次新政策上线,新工单类目加进来。每个季度,做一次审查,标签随政策更新,过时的样本被退役。维护成本不大,但是持续的。

类似的数据集存在于每个主要用例: 工程问答有 300 个问题、带专家验证过的答案。Frequent Flyer 政策有 400 个问题、带政策映射。延误通知场景有 200 个场景、带品牌团队验证过的"好"响应。每一份都由拥有该领域的相关 SME 团队维护。

往大了说,这件事给 AI 交付的启示是: Golden dataset 是 AI 项目里"内容工作"和"工程工作"的交叉点。任何一边单独都做不出来。需要工程纪律 (版本控制、跟训练数据严格隔离、可复现的运行) 和内容纪律 (代表性采样、SME 标注、跟生产一起演化)。从一开始就明确在数据集上投入的项目,能扩展到那些把它当事后想法的项目永远做不到的程度。一个能引导客户走完"刻意的数据集策略"的交付者,搭建出来的是一个超越任何单一 AI 项目的长期资产。
